# TaskIndex как ежедневный пульт владельца

Дата: 2026-09-12. Владелец: Дмитрий. Статус: черновик после брейншторма, ждёт
прочтения владельцем. Базовый коммит: `c7ad6ff` (`main`, Node 26, TI-084).

Документ описывает, что нужно добавить и настроить, чтобы владелец вёл в
TaskIndex все свои задачи (агентство, код, личное), а агенты вели их вместе с
ним без единого действия, которого он не просил. Спека самодостаточна:
исполнитель без контекста разговора собирает по ней работу, продуктовые
решения владельца в разделе 2 не пересматриваются.

## 1. Цель и критерии готовности

Цель: владелец открывает `https://tasks.gosling-agency.ru` и видит всё, что
ему нужно сделать, по областям и направлениям, с приоритетами; задачи
заносят и двигают агенты по его слову или он сам; ни один агент и ни одна
рутина не создают и не меняют ничего без явного поручения в текущем чате.

Ежедневное использование начинается после пунктов 1–5; пункт 6 закрывает каналы чатов и идёт отдельной волной (раздел 10):

1. В области «Агентство» лежат все задачи из `/OS/TASKS.md` по шести
   направлениям, P1 отмечены значком, P3 скрыты переключателем; в «Разработка» и
   «Личное» задачи появляются по мере поручений.
2. В Claude Code из `/OS`: на «занеси задачу X в Контент, P1» агент показывает
   карточку целиком (область, направление, название, приоритет, метки,
   срок, заметка), ждёт «да» и только тогда создаёт, отвечая
   идентификатором; «что у меня горит» печатает P1 и задачи с меткой
   `ответ`. Без отдельного «да» агент не пишет ничего.
3. `taskindex-admin agent list` на проде показывает только агентов из таблицы
   раздела 6; у рутин ключей нет.
4. `/OS/TASKS.md` генерируется из TaskIndex скриптом; `scripts/validate.sh`
   зелёный, Пульт задач открывается на сгенерированном файле.
5. Бобр в Telegram на «запиши: сходить к доктору» показывает карточку, ждёт
   «да», создаёт задачу в «Личное» и отвечает, что создал; в крон-сессиях к
   TaskIndex не обращается.
6. Из Claude.ai, приложения Claude на телефоне и ChatGPT доска доступна
   через один удалённый MCP после входа владельца (раздел 9, отдельная спека).

### 1.1. Сквозной сценарий приёмки

Один и тот же сценарий на тестовых задачах прогоняется после переписывания
скилла (волна 2а) в sandbox, затем в каждой среде волны 3. Он проверяет
интерфейс и скилл вместе:

1. Владелец пишет агенту: «занеси задачу „Проверить отчёт“ в Контент, P1,
   метка деньги».
2. Агент показывает карточку целиком и спрашивает «создаю?». Ничего не
   записано: `taskindex digest` показывает прежний `seq`.
3. Владелец правит: «срок завтра». Агент показывает исправленную карточку
   и снова ждёт «да».
4. После «да» задача создана; агент отвечает одной строкой:
   идентификатор и ссылка `https://tasks.gosling-agency.ru/?task=ID`.
5. Владелец открывает доску, видит карточку со значком P1 и чипом «деньги»,
   перетаскивает её в другую колонку и меняет порядок рукой.
6. Владелец пишет агенту: «закрой её». Агент показывает изменение
   («В работе → Готово»), ждёт «да», закрывает, отвечает строкой.
7. В «Активности» видны обе операции: агент создал, владелец перенёс, агент
   закрыл по поручению (поле защищено владельцем, флаг
   `--confirm-owner-fields` в истории).

## 2. Решения владельца (2026-09-12)

- **Ничего не создаётся без «ок создай» в чате, где сидит владелец.**
  Рутины (`hiring-daily`, `customs-daily`, `traffic-daily`, `weekly-os-audit`,
  крон OpenClaw, `bybit-nightly`) ключей не получают: находки идут в их
  бриф, владелец сам просит занести. Причина: «не люблю когнитивный мусор,
  сам попрошу занести, если что». Уточнение 2026-09-13: перед любой записью
  агент показывает точную карточку или изменение и ждёт отдельное «да»,
  даже если поручение звучало как «иди создай эту задачу» («пусть лучше
  спрашивает»).
- **Предложения** (сущность «агент предлагает, владелец принимает кнопкой»)
  допустимы, но не нужны, пока автоматы не пишут: в бэклог, не в эту работу.
- **Канон задач переезжает в TaskIndex.** `/OS/TASKS.md` остаётся, но
  пишется скриптом из TaskIndex в прежнем формате, руками не правится.
  `PROBLEMS.md` остаётся каноном проблем в /OS.
- **Приоритет явный, три уровня P1, P2, P3.** «Разделение приоритетов
  важно». Someday из TASKS.md это P3. Порядок карточек ручной для всех
  уровней, приоритет не сортирует, только помечает и фильтрует
  (подтверждено владельцем 2026-09-13: «ручной с индикаторами»).
- **Направления агентства по функциям**: Найм, Контент, Чатинг, Трафик,
  Финансы, Организационное. **Разработка: одно направление на репозиторий,
  заводится вместе с первой задачей** (живых реп около двадцати пяти,
  все сразу не нужны). **Личное: без направлений** на старте.
- **Бобр (OpenClaw) пишет**, но только по сообщению владельца в Telegram и
  после его «да» на показанную карточку. Крон-сессиям запрещено правилом
  скилла.
- **Чаты подключаются одним удалённым MCP с OAuth**: Claude.ai, приложение
  Claude на телефоне и компьютере, коннектор ChatGPT. Custom GPT и локальный
  MCP не делаем.
- **В /OS только агентство.** В сгенерированный `TASKS.md` попадает только
  область «Агентство»; задачи «Разработки» и «Личного» в /OS не пишутся.
- **Переключатель «Без P3»** на доске и в списке принят; хранится на сервере
  как предпочтение владельца, одинаково на всех устройствах.
- **Не редизайн.** Доска, колонки статусов, сайдбар, Focus, редактор
  остаются; добавляются поля и элементы на карточке (BACKLOG «Уже принятые
  продуктовые решения»).

## 3. Что не делаем

- Сущность «предложение» и scope `propose` (бэклог).
- Проблемы (`PROBLEMS.md`) как сущность TaskIndex; связь через поле `closes`.
- Исполнитель, назначение задачи агенту, планировщик запусков агентов.
- Двустороннюю синхронизацию с `TASKS.md`: файл только читается всеми и
  пишется только скриптом.
- Импорт задач из `issues.md` и бэклогов реп: они
  переносятся по одной по поручению владельца, когда он до них дойдёт.
- Ретушь Пульта задач: он продолжает работать на сгенерированном файле.
- Gosling Control удалён по решению владельца 2026-09-15: локальный проект
  убран в Корзину. Его данные не импортируются; совместимость с его
  коллектором не требуется.

## 4. Модель данных

Три новых поля задачи. Всё остальное без изменений (`src/shared/domain-schemas.ts`).

| Поле | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `priority` | `'p1' \| 'p2' \| 'p3'` | `p2` | P1 горит, P2 обычная, P3 когда-нибудь |
| `labels` | массив слагов из каталога, до 8, без повторов | `[]` | Метки для «что горит» и фильтров |
| `closes` | слаг `^[a-z0-9-]{1,80}$` или `null` | `null` | Проблема из `/OS/PROBLEMS.md`, которую закрывает задача |

Каталог меток `LABELS` в `src/shared/model.ts` рядом с `AREAS` и `STATUSES`:

Примечание реализации 2026-09-13 (TI-086): каталог меток и приоритетов вынесен в `src/shared/labels.ts`, как уточнено в плане волны 1.
`id`, `name`, `description`, `color`. Схема `labels` это `z.enum` по каталогу,
неизвестная метка отклоняется как `invalid`. Каталог отдаётся в
`/api/context`, чтобы агенты выбирали по описанию. Стартовый набор:

| id | Название | Описание для агентов |
|---|---|---|
| `otvet` | ответ | Нужен ответ или решение владельца кому-то: человеку, подрядчику, кандидату |
| `dengi` | деньги | Платёж, долг, приз, финансовое решение; при оплате строка в ledger |
| `5-min` | 5 мин | Делается за несколько минут, годится в просвет |
| `lora` | Lora | Касается модели Lora |
| `lily` | Lily | Касается модели Lily |
| `ari` | Ari | Касается модели Ari |

Примечание 2026-09-17: метка `otvet` снята решением владельца (миграция `0006_drop_otvet_label`, формат экспорта 6, `counts.otvet` удалён из digest, «что горит» = `counts.p1` и `--today`): кому нужен ответ, говорит название задачи, а неотвеченные чаты берутся из Telegram.

Теги `[найм]` и `[код]` из TASKS.md метками не становятся: `[найм]` это
направление «Найм», `[код]` это область «Разработка». `[сегодня]` это срок
«сегодня», не метка.

Новая метка это правка каталога и релиз, не команда. Это осознанно: набор
меток должен быть маленьким и одинаковым для всех агентов.

### 4.1. Права и защита

- `priority`, `labels`, `closes` предметные поля (`isSubjectField`) с той же
  защитой, что у остальных полей задачи (решение TI-027): прямая команда
  агента над полем, которое владелец менял сам (`ownerFields`), требует
  `--confirm-owner-fields`; поле, которого владелец не касался, агент меняет
  по поручению без флага. `task sync` после первого касания владельца не
  перезаписывает `priority` (как статус, архив, проект и область), а
  `labels` и `closes` только если владелец их менял. Пример: агент создал
  задачу, владелец поправил только заметку; агент по поручению ставит P1
  прямой командой без флага, `task sync` P1 не тронет, метки обновит.
  (Уточнено 2026-09-13 по ревью Codex: прежняя формулировка обещала защиту
  всех трёх полей после любого ручного сохранения, код так не работает и
  меняться не будет.)
- Порядок меток не несёт смысла: сервер хранит их в порядке каталога, тот же
  набор в другом порядке не считается изменением.
- Владелец и агент ставят их одинаково (паритет по плану v2 §1).

### 4.2. Команды

Новых команд нет. Поля добавляются в `taskFieldsSchema`
(`src/shared/schemas.ts`), значит попадают в `task.create`, `task.update`,
`task.save`, `task.sync` и в CLI-флаги сами (`src/cli/spec.ts` строит их из
схемы). Чек-лист «как добавить команду» из плана 04 применяется к полям:
схема, `applyCommand`, `isSubjectField`, подписи истории, справка, SKILL,
тесты.

CLI: `--priority p1`, `--closes lora-km-of-vacancy`, `--labels otvet,dengi`.
Массивы в CLI сейчас принимаются только JSON (`spec.ts`, тип `json`); для
`labels` добавляется разбор списка через запятую, JSON остаётся.

История («Активность», TI-032): «Приоритет: P2 → P1», «Метки: +ответ,
−деньги», «Закрывает: lora-km-of-vacancy» (и «снято»).

### 4.3. Чтение

- `/api/tasks` и `taskindex tasks`: фильтры `priority` (`p1|p2|p3`),
  `label` (один слаг), `closes` (слаг); порядок страниц и курсор без
  изменений. Порядок карточек в колонке остаётся ручным (`orderKey`) для
  всех приоритетов: приоритет это значок и фильтр, не сортировка.
  Перетаскивание никогда не меняет `priority`; приоритет меняется только
  явным действием: меню карточки, редактор, команда.
- `/api/digest`: блок `counts` получает `p1` (незавершённые P1 без архива) и
  `otvet` (незавершённые с меткой `otvet`). Это ответ на «что горит» без
  обхода списка.
- Снапшот, экспорт: поля входят; формат экспорта становится 5 (4 уже
  существует: `exportSchema`, `formatVersion: z.literal(4)`), форматы 1–4
  читаются с значениями по умолчанию, не пишутся.

### 4.4. Миграция

`0005_priority_labels_closes`: `priority TEXT NOT NULL DEFAULT 'p2'`,
`labels TEXT NOT NULL DEFAULT '[]'` (JSON-массив, как чеклист),
`closes TEXT NULL`. Индекс по `priority` не нужен: сортировки по нему нет,
фильтр по `priority` укладывается в существующий `(area, status)`. `schemaVersion()` растёт сам, тест
`tests/api/migrations.test.ts` дополняется.

### 4.5. Интерфейс

2026-09-15 (TI-091, решение владельца): доска и список показывают пять колонок/групп P1 / P2 / P3 / В работе / Готово. Перенос между P1–P3 меняет приоритет и ручную позицию атомарным `task.save`; перенос в работу/готово меняет статус, возвращение в P1–P3 возвращает в очередь с выбранным приоритетом. Создание внутри P1–P3 сразу задаёт приоритет. «Жду» удалена из элементов управления и Focus; прежние waiting-задачи показываются в очереди своего приоритета, исходные поля сохранены для совместимости. Миграция базы не требуется.

2026-09-15 (TI-092): порядок колонок В работе / P1 / P2 / P3 / Готово по слову владельца; порядок фиксированный, без хранения в `appearance`.

2026-09-15 (TI-093): минимум ширины колонки 200 px и зазор 16 px, чтобы пять колонок помещались на экране 1440 px.

- Карточка: значок приоритета слева от названия: `P1` красным, `P2` не
  показывается, `P3` серым; чипы меток после направления; чип
  `закрывает: slug` серым с моноширинным слагом.
- Редактор: строка «Приоритет» (три кнопки-сегмента) под «Состоянием»;
  «Метки» как набор переключателей из каталога; «Закрывает проблему»
  текстовое поле со слагом.
- Меню карточки: «P1», «P2», «P3» одной командой `task.update`.
- Доска и список: переключатель «Без P3» рядом с «На сегодня»; состояние
  хранится в предпочтении владельца (`appearance.update`, новое поле
  `hideP3: boolean`), чтобы одинаково работало на маке, винде и телефоне.
  Включённый переключатель убирает задачи P3 из колонок доски и из списка
  текущей области; счётчики колонок считают видимые; рядом подпись
  «скрыто N», чтобы скрытие не было молчаливым. Поиск, Focus, архив,
  `digest` и CLI переключатель не учитывают.
- Focus, поиск, архив без изменений. Стол Focus сортирует `next` как раньше.

## 5. Направления

### 5.1. Агентство

Создаются одним пакетом `batch` по подтверждению владельца.

| id | Название | Цвет | Описание (агентам для выбора) |
|---|---|---|---|
| `hiring` | Найм | `#9661bf` | Вакансии, кандидаты, доски объявлений, HR-аккаунты, кампании постинга |
| `content` | Контент | `#397faf` | Съёмки, ТЗ моделям, кастомы, FYP-производство, диск, бренд-буки, Notion-зеркала |
| `chatters` | Чатинг | `#a97928` | Смены, сетка покрытия, регламенты и SOP, контроль работы, доступы чаттеров |
| `traffic` | Трафик | `#39816d` | Каналы привлечения и их подрядчики: Instagram, Reddit, YouTube, реклама, паки |
| `finance` | Финансы | `#d4642a` | Выплаты, долги, призы, закрытия месяца, всё с строкой в ledger |
| `operations` | Организационное | `#737c92` | Остальное по агентству: сервисы, доступы, документы, инструменты |

Правило выбора в скилле: по описанию; если задача про деньги за найм, она
в «Найм» с меткой `dengi`. Сомнение решает владелец, агент спрашивает.

Примечание 2026-09-15: направление `chatters` называется «Чатинг» (решение
владельца при разборе переноса задач), id без изменений.

### 5.2. Разработка

Одно направление на репозиторий, имя как папка в `~/code` (`Hub`,
`fansly-ext`, `of-desktop`, `ContentOps`, `tg-assistant`, `traffic-control`,
`otraffparse`, `TaskIndex`, …), описание одна строка из `~/code/INDEX.md`.
Заводится вместе с первой задачей: агент говорит «направления `X` нет,
завести вместе с задачей?», владелец отвечает. Ветки-копии
(`hub-manual-ping`, `of-desktop-spenders`) направлениями не становятся.

### 5.3. Личное

Без направлений. Задача лежит в области без проекта. Направление появится,
когда владелец попросит.

| Чаты через MCP | `claude-chat`, `chatgpt-chat` | `write` | ключ выдаёт MCP-сервер после входа владельца (раздел 9) |

`write` нужен, чтобы заводить направления вместе с задачей; Бобру
направления заводить не нужно, поэтому `tasks`. Рутины и крон-джобы ключей
не имеют. Проверка: `taskindex-admin agent list` показывает ровно эти
идентичности; лишний агент это находка.

Правило поведения одно для всех, оно живёт в скилле (раздел 7), не в
сервере: запись только по явной просьбе владельца в этом разговоре.
Сервер по-прежнему защищает поля владельца и не даёт отменять его операции
(TI-027).

## 7. Скилл

`skills/taskindex/SKILL.md` переписывается: поведение первым разделом,
техника вниз. Структура:

1. **Что это и кто тут главный.** Доска владельца; агент ведёт задачи по его
   слову. Две строки.
2. **Правило записи.** Любая команда записи (`task create|update|save|move|
   archive|restore|sync`, `checklist.*`, `project.*`, `undo`, `batch`) только
   после явной просьбы владельца в этом разговоре, и всегда в два шага:
   агент показывает точную карточку (для создания: область, направление,
   название, приоритет, метки, срок, заметка) или точное изменение (что
   было, что станет), затем ждёт отдельное «да». «Иди создай эту задачу»
   это просьба, не подтверждение. Несколько изменений показываются одним
   списком и подтверждаются одним «да». Если владелец правит показанное,
   подтверждение нужно заново на исправленную версию. Находка без просьбы:
   сказать в чате, не писать.
   Сессия без сообщения владельца (крон, изолированный запуск): только
   чтение. Ответ после записи: одна строка с идентификатором, тем, что
   изменилось, и ссылкой на карточку `https://tasks.gosling-agency.ru/?task=ID`.
3. **Что куда.** Области, направления с описаниями из `context`,
   приоритеты (P1 горит, P2 обычная, P3 когда-нибудь; по умолчанию P2, P1
   ставит только владелец словами), метки из каталога, `closes` для задач,
   которые закрывают проблему из `/OS/PROBLEMS.md`. «Оформи» значит
   заполнить заметку и шаги у существующей задачи; «продумай» значит
   ответить в чате, писать только после «ок».
4. **Как отвечать на «что у меня горит».** `digest`, затем `tasks --priority
   p1` и `tasks --label otvet`; форма ответа: направление, название, срок,
   чего ждём.
5. **Комментарии.** Комментарий это тоже запись: только в рамках поручения.
   Отчёт о том, что владелец просил сделать, идёт в `comment add`, не в
   заметку. Вопрос без поручения задаётся в чате, комментарием не пишется.
6. Далее без изменений по смыслу: чтение и курсоры, источники и `task sync`,
   правки и `--base-revision`, отмена и focus, восстановление и коды.

Варианты одного скилла:

- Claude Code и Codex: полный файл, установка симлинком как сейчас.
- OpenClaw: тот же каталог ставится `openclaw skills install <каталог> --as
  taskindex`; во frontmatter добавляется `metadata.openclaw.requires`
  (`bins: ["taskindex"]`, `env: ["TASKINDEX_URL", "TASKINDEX_TOKEN"]`), чтобы
  `openclaw skills check` показывал готовность. Раздел 2 дополняется одной
  строкой: сообщение владельца в Telegram это и есть просьба; в крон-сессии
  просьбы нет.
- MCP: описания инструментов строятся из тех же разделов (раздел 9).

Другие скиллы (`tg`, `tg-hiring`, `audit-customs`, `finance`, `hub`, `ydisk` и
рутины) в TaskIndex не пишут и скилл `taskindex` не вызывают сами: найденную
задачу они называют в ответе одной строкой, запись идёт через скилл
`taskindex` после «да» владельца.

Репозитории кода не получают по скиллу каждый: одна строка в
`~/code/AGENTS.md` (правила workspace, подхватываются каждой сессией):
задачи по коду ведутся в TaskIndex через скилл `taskindex`, область
«Разработка», направление называется как папка репозитория; направления
нет, агент предлагает завести его вместе с задачей.

Граница ответственности: скилл задаёт поведение агента, сервер не знает,
было ли «да» в чате. Сервер гарантирует только то, что проверяет сам:
scope ключа, защиту полей владельца, запрет отмены его операций и полную
историю в «Активности». Кто написал без «да», виден там и отменяется.

`CLAUDE.md` TaskIndex дополняется ссылкой на эту спеку и на правило записи.

Примечание 2026-09-14 (волна 2а, TI-089, по решениям владельца): скилл
разделён на `SKILL.md` (правило записи, что куда, «что горит», шпаргалка) и
`reference.md` рядом (источники, курсоры, восстановление, коды); правило записи
строгое для всех команд, включая `comment add` («2» на вопрос про отчёт по
поручению), а «выполни задачу X» показывает изменения карточки одним списком в
конце работы; перед карточкой на создание агент проверяет дубли (`tasks -q`),
«что горит» включает просроченные (`tasks --today true`); Codex читает скилл из
`~/.agents/skills` (документация Codex), не из `~/.codex/skills`; ключи на маке
лежат в `~/.config/taskindex/<agent>.env` (0600), обёртка `~/.local/bin/taskindex`
выбирает ключ по `CLAUDECODE`, `CODEX_THREAD_ID` или `TASKINDEX_AGENT`, `op run`
при каждом вызове не используется; установка `scripts/agent/install-mac.sh`.
В сценарии §1.1 шаг 2 проверяется по `activity --actor agent:ID` (у агента нет
операций до «да»), а не по общему `seq`, который могут сдвинуть другие участники.

## 8. /OS

### 8.1. Правило

В `/OS/CLAUDE.md` и `AGENTS.md` пункт «Задачи» Write-rules заменяется:
задачи ведутся в TaskIndex через скилл `taskindex`; `TASKS.md` пишет
`scripts/render_tasks_md.py`, руками не правится; обновляется по правилам
раздела 8.5, сессия в /OS его не редактирует и не обязана рендерить. Таблица канонов: строка «Задачи» указывает на TaskIndex,
`TASKS.md` помечается как зеркало для чтения. Пункт про «дашборд
productivity-плагина» заменяется предупреждением: правки файла любым
инструментом теряются при следующем рендере, задачи закрываются и двигаются
только в TaskIndex.

### 8.2. Скрипт `render_tasks_md.py`

Вход: `taskindex tasks --all` (JSON-строки страниц) плюс `taskindex context`
для имён направлений; ключ `claude-mac` через `op run`. Выход: `TASKS.md` в
формате, который проверяет `validate.sh` (только `# `, `## `, строки
`- [ ]`/`- [x]`, пустые строки). Правила:

| Из TaskIndex | В файл |
|---|---|
| Область `agency`, не архив | попадает; `development` и `personal` никогда |
| `done`, `updatedAt` не старше 7 дней | секция `Done` как `- [x] ~~**Название**~~ (YYYY-MM-DD) — заметка`, без `closes` |
| `waiting`, любой приоритет | секция `Waiting On`, порядок по `followUp`, затем `orderKey` |
| `todo` или `doing`, P3 | секция `Someday`, порядок по `orderKey` |
| `todo` или `doing`, P1 или P2 | секция `Active`, порядок по `orderKey`, как на доске |
| `due` = сегодня | тег `[сегодня]` в начале названия |
| метки `otvet`, `dengi`, `5-min` | теги `[ответ]`, `[деньги]`, `[5 мин]` |
| направление `hiring` | тег `[найм]` |
| `closes` у незавершённой задачи | `closes \`slug\`` в конце строки; у `done` не пишется (раздел 8.6) |
| `note` | после ` — `, переносы строк заменяются на `; `, `[[вики-ссылки]]` сохраняются |
| `waitingFor` | в начале контекста как `ждём: …` |

Строки таблицы применяются сверху вниз: статус решает секцию раньше
приоритета, поэтому задача `waiting` с P3 идёт в `Waiting On`. Дата в
`Done` берётся из `updatedAt`, потому что момент завершения отдельно не
хранится; это допустимо, секция чистится еженедельно. Скрипт печатает `diff`
с прежним файлом; при недоступном сервере или ошибке ответа файл не
трогает и завершается кодом 1.

### 8.3. Разовый импорт

Сессия Claude Code в `/OS` с ключом `claude-mac`, по поручению владельца:

1. Разобрать текущий `TASKS.md` в список команд `task.create` по обратной
   таблице: `Active` → `todo`, P2; `Waiting On` → `waiting`, `waitingFor`
   из контекста; `Someday` → `todo`, P3; `Done` не переносится. Теги
   `[ответ] [деньги] [5 мин]` → метки; `[найм]` → направление «Найм»;
   `[код]` → область «Разработка», направление по названию репозитория в
   строке (сомнение → вопрос владельцу), в файл эти задачи больше не
   возвращаются; `[сегодня]` → `due` сегодня;
   `closes` → поле `closes`; контекст → `note` целиком. Направление для
   остальных задач агентства по описаниям из раздела 5.1, сомнительные
   строки в вопрос владельцу списком.
2. Показать владельцу таблицу «строка → область, направление, приоритет,
   метки», дождаться «да», выполнить `batch`.
3. Владелец сам расставляет P1 и порядок на доске.
4. Выполнить `render_tasks_md.py`, показать `diff` с исходным файлом.
   Приёмка: отличия только в порядке, форматировании и в ушедших из файла
   строках `[код]`, содержательных потерь нет. Закоммитить сгенерированный файл и правку правил.

### 8.4. Кто читает файл

`validate.sh` (формат и `closes`), `render_tasks_panel.py` и Пульт задач,
шаг 6b `weekly-os-audit`: все читают
файл прежнего формата и правок не требуют при соблюдении 8.2 (без
`closes` в `Done`) и 8.5 (свежесть). `hiring-daily`, `customs-daily`,
`traffic-daily`, `bybit-nightly` к `TASKS.md` не обращаются.

### 8.5. Свежесть файла

Задачу могут закрыть в браузере, с winpc или через Бобра, без сессии в
/OS. Поэтому файл обновляют не сессии, а два механизма:

- Читатель обновляет перед чтением: `weekly-os-audit` первым шагом и
  `render_tasks_panel.py` перед сборкой Пульта вызывают
  `render_tasks_md.py`; при коде 1 работают со старым файлом и пишут в
  отчёт «TASKS.md не обновлён, последний рендер <дата коммита>».
- Страховка по расписанию: launchd-задание на маке (по образцу
  `ru.gosling-agency.taskindex-backup`) раз в час рендерит и, если есть
  `diff`, коммитит `chore(tasks): рендер из TaskIndex <UTC>` и пушит.
  Без изменений ничего не коммитит. Сбой пишет в свой лог и не повторяется
  чаще раза в час.

Возраст файла всегда виден по `git log -1 --format=%cd -- TASKS.md`.
Любой читатель, для которого важна актуальность, обязан либо отрендерить,
либо назвать дату последнего рендера. Кэша «последний список» ни у одной
рутины нет.

### 8.6. Завершение задачи с `closes`

Закрыть задачу можно на доске, в CLI или через Бобра; ни один из этих путей
`PROBLEMS.md` не трогает, потому что проблемы остаются каноном /OS и
правятся только в сессии /OS по слову владельца. Сценарий:

1. Задача с `closes: slug` переходит в `done`. Рендер пишет её в `Done` без
   `closes`, поэтому `validate.sh` остаётся зелёным и до, и после снятия
   проблемы.
2. Проблема живёт, пока её не снимут. Сессия /OS и первым шагом
   `weekly-os-audit` перечисляют завершённые задачи, чей `closes`
   указывает на живую проблему (`taskindex tasks --status done --all` и
   срез `PROBLEMS.md`), и спрашивают владельца по каждой: снять, обновить
   `next:` или оставить. Правка `PROBLEMS.md` только после ответа.
3. Если задачу вернули из `done` (undo или перенос), `closes` снова
   попадает в строку файла, проблема к этому моменту либо жива, либо владелец
   уже решил её судьбу.

## 9. Каналы

### 9.1. winpc

Node 26 (проект перешёл на него, TI-084), пакет `npm pack` из релизного
коммита, `npm i -g` из архива; скилл копируется в `~/.claude/skills/taskindex`
и в каталог скиллов Codex; ключи `claude-winpc`, `codex-winpc` в переменных
окружения сессии. Проверка: `taskindex me` печатает актора, `taskindex digest`
отвечает. Инструкция в `README.md`, раздел «Агенты».

### 9.2. Бобр

CLI глобально на маке из того же архива; ключ `openclaw` попадает в
окружение шлюза через включённый плагин `onepassword` OpenClaw (как токен
Telegram), не файлом в workspace; скилл установкой из каталога репозитория
(раздел 7). Проверка: в Telegram
«что у меня горит» отвечает списком; «запиши: …» показывает карточку, после «да» создаёт задачу и
подтверждает; в `openclaw cron` джобах вызовов `taskindex` нет
(проверяется чтением промптов джобов).

### 9.3. Удалённый MCP с OAuth

Отдельная спека и отдельная работа; здесь только границы, чтобы не
разъехались:

- Один сервер `/mcp` на том же VPS за Nginx, авторизация по OAuth 2.1 с
  PKCE и динамической регистрацией клиента, как требуют Claude.ai и
  ChatGPT; единственный пользователь это владелец, вход тем же паролем, что в
  веб.
- Каждый клиент после входа получает свою идентичность агента
  (`claude-chat`, `chatgpt-chat`) со scope `write`; история показывает
  агента, не владельца, поля владельца защищены как для любого агента.
- Инструменты: `context`, `digest`, `tasks`, `task_get`, `task_create`,
  `task_update`, `task_move`, `comment_add`, `focus`; описания берутся из
  спецификации CLI и разделов 2–5 скилла. Правило записи в описание каждого
  пишущего инструмента: только по просьбе владельца в этом чате и после
  его «да» на показанную карточку или изменение.
- Кода в `src/shared` и `src/server` MCP не меняет; ходит в API как CLI.
