# Приёмка агентского цикла

Использовать отдельную тестовую базу, URL и два ключа разных агентов: sandbox
(`eval "$(npm run -s sandbox)"`, агенты `claude` со scope `write` и `codex` со
scope `tasks`) или выделенное тестовое окружение. Production не использовать.
Зафиксировать сборку, generation и идентификаторы операций. Проверить один и
тот же сценарий из настоящих сессий Claude Code и Codex; не считать эту
инструкцию отчётом о выполненной проверке.

Автоматизированная часть: `npm run agent-cycle` поверх работающего sandbox
(`scripts/agent-cycle.mts`) печатает JSON-строку на шаг
`{step, ok, operationIds, details}` и итог `{ok, passed, failed, manual}`; код
выхода 0, когда все автоматизированные шаги прошли. Ручные шаги описаны ниже
с тем, что открыть, что нажать и что увидеть.

1. **Автоматизировано (`agent-cycle`, шаг 1).** Оба агента читают context и
   digest. Первый создаёт проект с описанием. Второй находит его через
   context, затем оба вызывают sync с одинаковым origin и настоящей версией
   источника: одна задача, автор определён ключом (`createdBy: agent:claude`),
   второй получает `skipped: all, reason: stale`. Источник без версии: первый
   sync создаёт, следующий даёт `freshness_unknown` без события.
2. **Автоматизировано (шаг 2).** Владелец переносит задачу в другой проект и
   закрывает. Агент синхронизирует более новую версию источника: закрытый
   статус и выбранный проект сохраняются; `skipped` объясняет результат
   (`reason: owner`), `applied` содержит `note`. Оба агента добавляют
   комментарии одновременно с сохранением заметки владельцем: `commentCount`
   2, заметка сохранена. На экране после SSE одна задача.
3. **Вручную.** Владелец открывает карточку в браузере (пароль в `owner.json`
   каталога sandbox) и набирает текст в заметке. Агент меняет другое поле
   (`taskindex task update ID --base-revision N --due 2026-09-30`): карточка
   обновляется через SSE, черновик остаётся в поле. Затем оба меняют одно
   поле (агент `--note`, владелец ту же заметку): сохранение устаревшего
   варианта должно вернуть conflict с `current`, текст формы не теряется.
   Частично покрыто e2e `tests/e2e/workspace.spec.ts`.
4. **Автоматизировано (шаг 4).** Агент создаёт batch из трёх задач;
   активность показывает одну операцию с `taskCount: 3`. Владелец отменяет её
   целиком; отмена создания задачи после поздней правки её поля даёт
   `conflict`; ключ `tasks` не может отменить `project.update` владельца
   (`forbidden`, код 4). Перед шагом агент фиксирует курсор
   (`cursor commit SEQ --operation-seq N` по `digest`), после — `activity
   --since last` идёт по журналу операций (`after=<operationSeq>`) и содержит
   отклонённый undo с `ok: false`: операция без событий видна только там
   (TI-008).
5. **Покрыто vitest.** Прокси принимает POST /api/commands, передаёт его
   серверу, затем разрывает ответ после commit; `operation get ID` возвращает
   сохранённый результат, `operation resume ID` ничего не дублирует:
   `tests/cli/agent-cycle.test.ts` (перехват транспорта, настоящие Hono,
   Better Auth и SQLite). Не заменять этот сценарий отказом сети до отправки.
6. **Частично автоматизировано (шаг 6).** Автоматически: агент B открывает
   `/api/events/stream` своим ключом (с текущим `generation`, иначе сервер
   сразу отвечает `event: reset` и закрывает поток), владелец отзывает ключ B
   через `admin-run agent-key revoke`, агент A создаёт задачу — доставка
   перепроверяет доступ и закрывает поток B `event: revoked`; следующее чтение
   отозванным ключом даёт код 4 (TI-001, TI-036). Вручную: запустить sandbox с
   `--writes held --deployment d2`; CLI делает четыре попытки с одинаковым
   конвертом, сохраняет его после 503 и выходит с кодом 1
   (`tests/cli/cli.test.ts`, «keeps a held operation…»). Выполнить
   `DATABASE_PATH=<sandbox>/sandbox.db TASKINDEX_DEPLOYMENT=d2 npm run admin -- open-writes`,
   затем `taskindex operation resume`: ровно одно изменение. Перезапуск того
   же deployment оставляет `writes: open` (`/health`); следующий deployment
   стартует held.
7. **Частично автоматизировано (шаг 7).** Перезагрузка вкладки с
   неподтверждённой отправкой и черновиком: вручную, проверить выяснение
   операции без нового ID. `mark-restored` на базе sandbox с сохранённым
   старым конвертом: `operation resume` получает `generation_changed`
   (код 3); по правилу подтверждения (TI-004) окончательный отказ снимает
   конверт с очереди, повторять его нельзя, нужен свежий контекст и новая
   оценка действия. Тексты черновиков в браузере остаются доступны для
   ручного переноса.
8. **Вручную (экспорт).** `taskindex export --out backup.json` на базе sandbox:
   в файле `formatVersion: 3`, у каждой операции есть `operationSeq`, в
   `settings` есть `schema_version`, и присутствует массив `appearance` ровно с
   одной записью (`id: owner`, `mode`, `skinId`, `revision`). Импорт этого
   файла в пустую базу (`npm run admin -- import`) проходит `validateExport`;
   экспорт прежних форматов (1 — без `operationSeq`, 2 — без `appearance`)
   импортируется с подстановкой значений по умолчанию, но сервер их не пишет
   (`tests/api/migration-compat.test.ts`, `tests/fixtures/export-schema-2.json`).

Результат записать отдельно: кто выполнял, URL тестового окружения, build,
generation, operationId каждого существенного шага (из вывода
`agent-cycle`), ответы и снимки экрана, пройденные шаги и точная причина
непройденных. Секреты не включать.
