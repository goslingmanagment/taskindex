## Причина и наблюдаемое поведение

Непредвиденная ошибка логируется как объект Error без явных message/stack/code и идентификатора запроса; JSON может потерять содержимое. LOG_LEVEL объявлен в compose, но не управляет наблюдаемым поведением. Сбой становится трудно связать с конкретной операцией.

## Что изменится и зачем

Один сбой можно проследить по requestId и operationId от ответа до серверного stack, не раскрывая ключи, cookies и тексты задач.

## Шаги реализации

1. Добавить небольшой единый structured logger с level, time, event, requestId и нормализацией Error. Проверить реальный output, а не только переданный объект.
2. Присваивать/безопасно принимать requestId на HTTP-границе и возвращать его в error response/header. Некорректный входной ID ограничить по длине и допустимым символам.
3. Для executor добавлять operationId/generation и безопасную категорию actor, но не сырой envelope, bearer key, cookie или произвольный пользовательский note.
4. Разделить expected domain rejection, transport/protocol failure и unexpected internal. На сервере сохранить диагностическое сообщение/stack, клиенту дать стабильный безопасный текст.
5. Подключить LOG_LEVEL и описать поддерживаемые значения. Проверить, что ошибки остаются видимыми при production уровне и не пишутся дважды соседними catch.
6. Сверить retryable с фактической известностью результата. Не менять все internal ошибки на окончательные лишь для удобства вывода: outcome должен учитывать точку сбоя относительно commit.

## Проверки

- [ ] Искусственная ошибка с cause/SQLite code создаёт читаемую JSON-запись с stack и correlation.
- [ ] В запросе есть тестовые секреты/текст задачи — их нет в логах и клиентском internal response.
- [ ] Error boundary и executor не дублируют один сбой; LOG_LEVEL реально фильтрует разрешённые уровни.

## Критерий готовности

По одному requestId восстанавливается причинная цепочка сбоя; безопасный формат проверен автоматическим тестом и примером runbook.

## Зависимости и границы

Жёстких зависимостей от других планов нет; работать от актуального snapshot исходников.

Stack/message некоторых ошибок содержат SQL или значения. Санитизацию проверить на реальных ошибках библиотек; структурированный JSON сам по себе не обеспечивает приватность.
