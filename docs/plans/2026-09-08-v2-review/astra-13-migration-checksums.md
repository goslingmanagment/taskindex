## Причина и наблюдаемое поведение

Runner запоминает имя SQL-файла, но не его содержимое. Если ранее применённый файл поменять, старая база пропустит его, новая получит другую схему под тем же набором имён. Проверка schema_version этого не обнаруживает.

## Что изменится и зачем

Одна история миграций соответствует одному содержимому. Изменение применённого SQL обнаруживается до выполнения новых мутаций базы.

## Шаги реализации

1. Определить стабильный checksum точных bytes миграции и хранить его в журнале runner. Зафиксировать правила encoding/line endings, чтобы checkout не менял смысл сравнения.
2. Перед применением новых миграций проверить всю уже применённую цепочку: наличие файлов, порядок, совпадение checksum и поддерживаемую версию схемы.
3. Для существующей БД без checksum подготовить явную процедуру baseline: сверить её с неизменёнными историческими SQL и эталонной схемой. Не принимать произвольный текущий файл за историческую истину молча.
4. Изменения схемы оформлять только новыми миграциями. Объяснить порядок генерации Drizzle, review SQL, применения и обновления версии.
5. Проверять drift до writes и до запуска новой версии; ошибку делать диагностируемой, с именем миграции без содержимого секретных данных.
6. Добавить сохранённую предыдущую DB fixture и процедуру проверки upgrade, повторного запуска и отказа запуска слишком старого приложения.

## Проверки

- [ ] Повтор неизменённой цепочки идемпотентен; изменённый/пропавший старый SQL останавливает runner до новых записей.
- [ ] Новая миграция применяется один раз; ошибка откатывает допустимую транзакционную часть, состояние журнала соответствует БД.
- [ ] Legacy fixture проходит baseline только по проверенной процедуре; unknown/newer schema отказывается открываться для записи.

## Критерий готовности

Нельзя получить две разные схемы под одинаковой принятой историей незаметно; runner и инструкция запрещают редактирование применённых SQL.

## Зависимости и границы

Жёстких зависимостей от других планов нет; работать от актуального snapshot исходников.

Не считать переход на стандартный Drizzle migrator автоматическим решением: нужно проверить его реальное поведение при изменённом checksum. Никакого schema push на рабочую базу.
