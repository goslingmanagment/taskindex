## Причина и наблюдаемое поведение

CLI принимает произвольный JSON с HTTP 200 за успех команды. На ответ {"status":"maintenance"} он возвращает exit 0 и удаляет outbox, хотя сервер не подтвердил нужную операцию. HTTP-успех и доказательство завершения команды сейчас смешаны.

## Что изменится и зачем

Конверт удаляется только после проверенного окончательного результата именно этой операции. Неизвестный или несовместимый ответ оставляет возможность безопасно узнать результат или повторить исходный конверт.

## Шаги реализации

1. Разделить транспортный успех, валидный command-result и чтение stored-operation. Использовать общие Zod-схемы, проверять operationId, generation и ожидаемый вид результата.
2. Описать таблицу outcome → exit code → состояние outbox: success, окончательный сохранённый отказ, retryable, unknown, malformed response и несовместимый протокол.
3. Не считать GET operation успешным выполнением команды только потому, что чтение прошло с HTTP 200: внутри может находиться сохранённый rejected result.
4. При неизвестном ответе сохранить исходные bytes/поля envelope и ID, показать команду проверки результата. Повтор не должен генерировать новую операцию.
5. Обрабатывать пустой body, HTML, не-JSON, схему другой версии и несовпадающий ID как ошибку протокола, а не как пользовательский доменный отказ.
6. Согласовать ошибки и документацию CLI с политикой durable outbox; чтения без изменения данных не должны зависеть от успешного завершения чужой pending-операции.

## Проверки

- [ ] HTTP 200 maintenance, пустой body, success с чужим ID, чужая generation и неизвестный discriminant сохраняют конверт и не дают ложный exit 0.
- [ ] Настоящий success и сохранённый domain rejection корректно завершают состояние; повтор того же envelope идемпотентен.
- [ ] После обрыва между commit и ответом CLI находит stored result и не создаёт второй эффект.

## Критерий готовности

Исходный probe больше не удаляет envelope; все способы подтверждения проходят одну функцию классификации и имеют точные exit-коды.

## Зависимости и границы

Жёстких зависимостей от других планов нет; работать от актуального snapshot исходников.

Окончательный отказ не следует бесконечно повторять. Его нужно отличать от HTTP-ответа посредника, который лишь похож на ошибку приложения. Валидацию файлов outbox реализует отдельный план 22.
