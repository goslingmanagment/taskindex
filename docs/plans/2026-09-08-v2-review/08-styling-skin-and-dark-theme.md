Статус: предложение, 2026-09-08. Источник: сводное ревью v2 (см. `README.md` в этой папке), решение владельца от 2026-09-08: два стилевых мира остаются, ручной CSS оформляется как скин поверх примитивов shadcn/Base UI.
Приоритет: P1 (не блокирует рабочее переключение, но каждый новый экран без этого плана увеличивает долг). Оценка: M, 3–4 дня чистой работы, из них день на замену цветов токенами. Главная архитектурная ошибка в каскаде, а не в наличии двух миров. Tailwind 4 раскладывает всё в `@layer theme, base, components, utilities`. Ручной CSS лежит вне слоёв. По правилам каскада нелэйерные обычные объявления побеждают любой слой независимо от специфичности. Поэтому скин выигрывает у утилит случайно, а не по объявленному правилу, а 27 `!important` появились в борьбе с этой неявностью. Для `!important` порядок слоёв обратный: нелэйерные важные объявления проигрывают важным объявлениям из слоёв, что делает поведение ещё менее предсказуемым.

Вторая ошибка: скин не проходит через токены. Смена `--primary` перекрашивает примитивы из `src/web/ui`, но не `.area-button` (`#3763df` зашит в `styles.css:173`). Тёмная палитра существует, но её нельзя включить, а если включить, ручной CSS останется светлым.

## 2. Цель и критерии приёмки

Цель: ручной CSS становится скином в строгом смысле. Скин это набор правил, которые потребляют только токены и опираются на публичный контракт примитивов; замена файла токенов перекрашивает оба мира одновременно, без правок в правилах.

Критерии приёмки:

1. В `src/web/skin/**/*.css` нет ни одного hex-, rgb- или hsl-литерала цвета. Проверяется линт-правилом (шаг 8), падение `npm run check`.
2. В скине нет `!important`. Единственное исключение: блок `prefers-reduced-motion` (`styles.css:855-862`), он переезжает в `@layer base`.
3. Один `:root` и один блок тёмной темы, оба в `src/web/tokens.css`. Второго определения любого токена в проекте нет.
4. Слои объявлены явно одной строкой в `styles.css`: `@layer theme, base, components, utilities, skin;`. Все правила скина находятся внутри `@layer skin`.
5. Внутрь примитивов скин обращается только через `[data-slot=…]` и `[data-sidebar=…]` либо через собственный класс, переданный компоненту в `className`. Селекторов вида `.something button`, `.something input`, `.something h3` в скине нет, кроме собственной разметки приложения (не компонентов `ui/*`).
6. Брейкпоинты берутся из темы: в CSS через `@variant md` или `theme(--breakpoint-md)`, в `use-mobile.ts` то же значение читается из `getComputedStyle(document.documentElement).getPropertyValue('--breakpoint-md')`. Числа `767`, `1000`, `1100`, `1200`, `1600` в CSS отсутствуют.
7. `workspace-overview.css` удалён, его правила в скине.
8. Дублей селекторов и мёртвых классов нет (метрика из отчёта по качеству: 93 и 25 должны стать 0).
9. Визуальный эталон сохранён: e2e-скриншоты (9 сцен, desktop и mobile) до и после фазы A совпадают побайтно там, где рендер детерминирован (board, list, editor, focus), и в пределах допуска `maxDiffPixelRatio 0.001` там, где присутствуют относительные времена (activity, discussion). Фаза B (сведение близких оттенков) допускает изменения, каждое подтверждается владельцем по диффу скриншотов.
10. Размер собранного CSS не больше текущего: сейчас 109 217 байт (20 071 gzip); ожидается заметно меньше после удаления второй палитры, дублей и мёртвых классов.
11. Тёмная тема: либо работает от `prefers-color-scheme` и `color-scheme` для обоих миров, либо удалена полностью вместе с `@custom-variant dark` и 33 вариантами `dark:`. Промежуточное состояние «есть палитра, нет переключателя» не допускается. Выбор за владельцем, раздел 3.4.

## 3. Решение

### 3.1. Три слоя вместо двух миров

| Слой | Файлы | Что содержит | Правила |
|---|---|---|---|
| Токены | `src/web/tokens.css` | `:root` светлая палитра, блок тёмной, `@theme inline` (переехавший из `styles.css:7-49`), радиусы, шрифты, брейкпоинты | Единственное место с литералами цветов. Имена семантические, не по компонентам |
| Примитивы | `src/web/ui/*`, Tailwind, `tw-animate-css`, `src/web/vendor/shadcn-base.css` | Сгенерированные компоненты shadcn base-nova поверх Base UI | Не редактируются руками; обновляются через `npx shadcn@latest add`; потребляют только токены через утилиты |
| Скин | `src/web/skin/*.css` внутри `@layer skin` | Композиция экранов: `.workspace-sidebar`, `.task-card`, `.editor-body`, `.activity-*`, `.auth-*` | Только `var(--…)`; в примитивы только через `data-slot`/`data-sidebar` или `className`; без `!important` |

Порядок слоёв объявляется явно и один раз в `src/web/styles.css`:

```css
@import 'tailwindcss' source('./');
@import 'tw-animate-css';
@import './vendor/shadcn-base.css';
@import './tokens.css';

@layer theme, base, components, utilities, skin;

@import './skin/base.css' layer(skin);
@import './skin/sidebar.css' layer(skin);
@import './skin/board.css' layer(skin);
@import './skin/editor.css' layer(skin);
@import './skin/activity.css' layer(skin);
@import './skin/dialogs.css' layer(skin);
@import './skin/auth.css' layer(skin);
```

Скин ставится после `utilities`. Это сохраняет сегодняшнее поведение один в один (сейчас нелэйерный скин побеждает утилиты) и делает его правилом. После этого все `!important` становятся лишними и снимаются. Альтернатива «скин между `components` и `utilities`» академически чище (утилита на элементе всегда побеждает), но потребует пересмотреть каждое из 78 мест, где скин переопределяет размеры примитивов (`.editor-footer button { height }` против `h-8` у `Button`), и изменит внешний вид. Приложение использует утилиты в трёх местах (`Skeleton` в `shell.tsx:574-576`), так что потеря возможности «перебить скин утилитой» ничего не стоит. Если понадобится, отдельный класс в скине это делает явно.

Разбивка скина по экранам, а не по одному файлу, нужна для навигации агентов: «где стилизуется редактор» отвечает имя файла. Vite объединяет всё в один CSS, порядок внутри слоя не важен, потому что дубли селекторов запрещены.

### 3.2. Семантические токены вместо 126 оттенков

Набор shadcn (`--background`, `--card`, `--muted-foreground`, `--border`, `--primary`, `--destructive`, `--sidebar-*`) покрывает примитивы, но скину не хватает ролей. По контексту использования 126 оттенков делятся на группы:

| Роль | Примеры текущих литералов | Новые токены |
|---|---|---|
| Приглушённый текст | `#7d899e`, `#7b89a0`, `#738199`, `#738197`, `#748197`, `#748196`, `#748198`, `#7a879c`, `#7e899a`, `#78859a`, `#8390a3`, `#8090a5` (12 оттенков одного серого) | `--muted-foreground` (есть), `--text-faint` для более светлого |
| Линии и разделители | `#e3e8f1`, `#e3e8f0`, `#e5eaf2`, `#e8ecf3`, `#e8ecf2`, `#e0e5ee` | `--border` (есть), `--line-soft` для внутренних разделителей |
| Поверхности | `#fff`, `#fcfdff`, `#fbfcff`, `#fafbfd`, `#f9fbfd`, `#f0f3f8`, полупрозрачные `#ffffff90`, `#e8edf5a8` | `--card` (есть), `--surface-raised`, `--surface-overlay` |
| Акцент | `#3763df`, `#3b5ccc`, `#e9eefa`, `#5471b5`, тени `#3763df22`, `#3763df15` | `--primary`, `--accent`, `--accent-foreground` (есть), `--primary-shadow` |
| Ожидание, срок, предупреждение | `#fffbf2`, `#fff8e9`, `#fcf8ef`, `#fcf3df`, `#896a36`, `#efe2c7`, `#eddfbb` | `--warning`, `--warning-foreground`, `--warning-soft`, `--warning-border` |
| Успех, сделано | `#eff8f3`, `#f2f6f2` | `--success-soft`, `--success-foreground` |
| Ошибка мягкая | `#fff2f2` | `--destructive-soft` (у shadcn только `--destructive`) |

Работа делится на две фазы, и это принципиально для критерия 9:

- Фаза A, механическая: каждый литерал заменяется на токен с тем же точным значением. Там, где значение уникально, токен получает это значение. Скриншоты обязаны совпасть побайтно. Так появляется до 126 токенов, часть из них временные.
- Фаза B, сведение: близкие оттенки одной роли сливаются в один токен (12 серых в один). Каждое слияние меняет пиксели, поэтому идёт отдельными коммитами с диффом скриншотов, и владелец подтверждает результат. Это единственная часть плана с визуальным риском, и она отделена намеренно.

Правило именования: токены называют роль (`--text-faint`), а не место (`--sidebar-footer-color`) и не значение (`--grey-500`). Токен-по-месту допустим только в `--sidebar-*`, потому что так устроен shadcn.

### 3.3. Контракт с примитивами

78 селекторов вида `.wrapper button` переписываются одним из двух способов:

- Если целевой элемент это корень или слот примитива shadcn, используется `[data-slot='…']`. Список слотов стабилен и виден в `src/web/ui/*.tsx` (`data-slot="button"`, `"dialog-title"`, `"tabs-trigger"`, `"empty-description"`, `"checkbox"` и т. д.).
- Если целевой элемент это собственная разметка приложения (`<button className="complete-circle">`), он получает свой класс, и селектор становится одноуровневым.

Причина: внутренняя разметка примитива (`<button>` внутри `DropdownMenuTrigger`, `<input>` внутри `Input`) может смениться при обновлении shadcn или Base UI, а `data-slot` это объявленный публичный контракт, и он же используется самими примитивами для стилизации.

### 3.4. Тёмная тема: решение владельца

Сегодня тёмная тема это мёртвый код: две палитры `.dark`, 33 варианта `dark:` в примитивах и ни одного места, где класс `.dark` ставится на `<html>`. Варианты:

| Вариант | Что делать | Плюсы | Минусы |
|---|---|---|---|
| A. Системная тема без тумблера (рекомендуется) | В `tokens.css` тёмный блок под `@media (prefers-color-scheme: dark) { :root:not([data-theme='light']) { … } }` и под `:root[data-theme='dark']`; `@custom-variant dark (&:where([data-theme='dark'], [data-theme='dark'] *))` плюс медиа-ветка; `color-scheme: light dark` на `:root`; `theme-color` в `index.html` двумя тегами с `media`. Тумблер не делается, `data-theme` остаётся точкой расширения | Оба мира перекрашиваются токенами, ничего не нужно писать в JS; палитра уже нарисована | Нужно один раз пройти скин глазами в тёмной теме: после фазы A все цвета токенизированы, так что дефекты будут только там, где токен подобран неверно |
| B. Удалить тёмную тему | Убрать оба блока `.dark`, `@custom-variant dark`, `dark:`-варианты из `ui/*` при следующей регенерации не трогать (они безвредны, но можно вычистить) | Меньше CSS, меньше проверок | Потеря готовой палитры; при возврате придётся рисовать заново |
| C. Ручной тумблер | Как A плюс переключатель в футере сайдбара с сохранением в localStorage и `data-theme` на `<html>` | Полный контроль | Новый элемент интерфейса, что противоречит решению «не редизайн»; сохранение темы это ещё одно per-viewer состояние |

Рекомендация: A. Она бесплатна по коду, проверяется в e2e через `colorScheme: 'dark'` в Playwright и не добавляет интерфейса. Вариант C возможен позже одной правкой атрибута, потому что A уже использует `data-theme`.

Что нельзя оставлять: текущее состояние. Палитра без переключателя вводит в заблуждение и агентов, и владельца.

### 3.5. Что не меняется

- Tailwind 4 остаётся движком примитивов, `@tailwindcss/postcss` не заменяется на `@tailwindcss/vite` в рамках этого плана (см. `07-web-client-fixes-and-structure.md`).
- `class-variance-authority`, `tailwind-merge`, `clsx`, `tw-animate-css` остаются, потому что их используют 18 примитивов (`cn()` 93 раза, `cva()` 4 раза, анимации в 5 файлах).
- Приложение не переводится на утилиты. Это и есть решение владельца о двух мирах.

## 4. Шаги

Все шаги в отдельном worktree. После каждого шага: `npm run check`, затем e2e-скриншоты в scratch-каталог и сравнение с эталоном (шаг 1).

0. **Вынести базовый CSS shadcn.** Скопировать `node_modules/shadcn/dist/tailwind.css` в `src/web/vendor/shadcn-base.css` с шапкой «сгенерировано shadcn 4.18.0, не редактировать, обновлять копированием». В `styles.css:3` заменить импорт. Убрать `shadcn` из `devDependencies` и `overrides.undici` из `package.json` (если план 09 уже сделал это, шаг пропускается). Проверка: `npm run build` даёт тот же CSS с точностью до порядка правил, `npm ls undici` пуст.

1. **Зафиксировать эталон.** Прогнать `TASKINDEX_E2E_ARTIFACT_DIR=<scratch>/before npm run e2e` (после того как план 10 переведёт артефакты в `test-results/`, переменная не нужна). Дополнительно снять те же 9 сцен с `colorScheme: 'dark'`, чтобы задокументировать текущее состояние тёмной темы (ожидается светлый рендер: класс не ставится). Сохранить хеши.

2. **Одна палитра.** Удалить первый `:root` (`styles.css:55-86`) и первый `.dark` (`:87-114`): их полностью перекрывает блок «Minimal» (`:1608-1660`), который и является действующей палитрой. Перенести действующую палитру и `@theme inline` (`:7-49`) в `src/web/tokens.css`. Переименовать `--font-geist-sans`/`--font-geist-mono` в `--font-sans-stack`/`--font-mono-stack` (три места: `:10-11`, `:51`, `:83-85`) и убрать дублирующее `body { font-family }` на `:51`, оставив `@layer base { html { @apply font-sans } }`. Проверка: скриншоты совпадают побайтно, потому что действующие значения не менялись.

3. **Слои.** В `styles.css` объявить `@layer theme, base, components, utilities, skin;`. Обернуть весь оставшийся ручной CSS в `@layer skin { … }` одним блоком (на этом шаге ещё не разрезая на файлы). Влить `workspace-overview.css` в конец этого блока и удалить импорт в `overview.tsx:6`. Снять все 27 `!important`, кроме блока `prefers-reduced-motion`, который переносится в `@layer base`. Проверка: скриншоты совпадают. Если какой-то `!important` окажется действительно нужным, это значит, что правило спорит с другим правилом скина, а не с примитивом; такой конфликт решается специфичностью или удалением дубля, не восстановлением `!important`.

4. **Дедупликация.** Для каждого из 93 повторно определённых селекторов оставить последнее по каскаду определение, объединив свойства (последнее объявление каждого свойства побеждает, так что слияние делается механически: собрать все объявления селектора в порядке файла, оставить последние значения). ## 6. Риски и откат

- **Визуальные регрессии при снятии `!important` и дедупликации.** Смягчение: скриншоты после каждого шага; шаги 3 и 4 делаются отдельными коммитами, откат это revert одного коммита.
- **Слияние дублей по правилу «последнее побеждает» ошибётся там, где дубли стояли под разными медиазапросами.** Смягчение: скрипт дедупликации учитывает контекст `@media`; ручная проверка 11 медиаблоков.
- **Фаза B меняет внешний вид.** Это ожидаемо и делается только с подтверждением владельца, по одной роли за коммит.
- **Tailwind не эмитит кастомный `--breakpoint-*` в `:root`, и `use-mobile.ts` получит пустую строку.** Смягчение: `@theme static` для блока брейкпоинтов и fallback `48rem` в хуке, тест на это.
- **Обновление shadcn изменит `data-slot`.** Смягчение: `check-skin.mjs` сверяет слоты, используемые скином, со слотами, объявленными в `src/web/ui/*.tsx`, и падает при расхождении.
- **Тёмная тема (вариант A) выявит нечитаемые сочетания в токенах фазы A.** Это нормальный результат шага 10, правится в `tokens.css`, скин не трогается. Именно так проверяется, что скин действительно стал скином.

Откат целиком: план не меняет разметку компонентов, кроме добавления `className` на шаге 9, поэтому возврат к одному файлу `styles.css` возможен в любой момент через `git revert` серии коммитов.
