## Причина и наблюдаемое поведение

Undo-тест использует production isSubjectField как oracle. Если важное поле исчезнет из реализации и из сравнения одновременно, тест останется зелёным. Генераторы в основном покрывают owner, актуальную revision и успешные короткие последовательности.

## Что изменится и зачем

Тесты проверяют независимые предметные инварианты и трудные переходы, а не повторяют набор решений production-кода.

## Шаги реализации

1. Определить явную тестовую модель значимых полей/состояния независимо от production isSubjectField. Обосновать исключённые технические поля.
2. Собрать небольшую reference model для undo и конфликтов, где ожидаемый результат следует из записанной истории намерений, а не из того же reducer.
3. Добавить генераторы owner/tasks/write/read, устаревших revision, origin.version, owner touches, поздних правок и batch с отвергаемой командой.
4. Для транзакционных свойств запускать настоящий executor на isolated SQLite: state/events/result согласованы, rejected batch не меняет предметное состояние, повтор не создаёт эффект.
5. Проверять монотонность seq/revision, целостность диапазона операции, сохранность незатронутых полей и явный conflict при невозможной отмене.
6. Настроить воспроизводимый seed и shrinking; добавлять минимальный regression из найденного counterexample. Увеличение numRuns без новых состояний не считать улучшением.

## Проверки

- [ ] Контрольная мутация, удаляющая восстановление одного значимого поля, действительно роняет независимый тест.
- [ ] Генераторы достигают rejected/conflict/noop/unknown-boundary сценариев, а не отбрасывают их фильтрами.
- [ ] Counterexample сохраняется компактно и воспроизводится одной командой.

## Критерий готовности

Oracle независим от проверяемого классификатора; новые свойства ловят хотя бы показанную контрольную мутацию и проходят на корректном коде.

## Зависимости и границы

Жёстких зависимостей от других планов нет; работать от актуального snapshot исходников.

Полная вторая реализация продукта станет таким же источником ошибок. Reference model должна быть маленькой, с явно ограниченным набором правил. Политику owner/agent после решения плана 27 проверять отдельно.
