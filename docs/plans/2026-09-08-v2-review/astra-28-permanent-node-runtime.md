## Причина и наблюдаемое поведение

В зафиксированной проверке обычный node и Homebrew node@24 фактически запускают Node 26.7.0, несовместимый с установленным SQLite native ABI и контрактом >=24.11.0 <25. Рабочий Node 24.20.0 доступен только через временный /tmp PATH.

## Что изменится и зачем

Чистый терминал в проекте использует поддерживаемый Node 24 без временного каталога и без изменения runtime других проектов.

## Шаги реализации

1. Повторно проверить command -v, realpath, node --version и process.versions.modules в новом терминале. Не считать имя symlink node@24 доказательством версии.
2. Выбрать уже используемый у владельца manager или постоянный project-scoped runtime. Добавить один явный version pin и инструкцию активации; не ставить несколько менеджеров параллельно.
3. Добавить ранний preflight версии для dev/check/build/admin, чтобы ошибка возникала до загрузки native SQLite и объясняла способ исправления.
4. Выполнить npm ci/rebuild только под поддерживаемой версией с сохранением lockfile-контракта. Не пересобирать модуль под Node 26 ради обхода engines.
5. Проверить новый shell, npm run check/build и локальный start на искусственной БД. Dev setup не должен создавать/сбрасывать рабочую БД.
6. Согласовать версию с Docker/CI и записать постоянные команды в README. Убрать зависимость инструкции от /tmp, но не удалять чужие временные каталоги в рамках настройки.

## Проверки

- [ ] Новый терминал без ручного PATH на /tmp запускает реальный Node 24.
- [ ] SQLite загружается, check/build проходят; запуск другим Node даёт понятный preflight отказ.
- [ ] В соседнем проекте глобальные symlink/PATH не были перезаписаны; Docker/CI используют совместимый major.

## Критерий готовности

Разработка воспроизводима из нового терминала по README, версия проверяется автоматически, временный runtime не нужен.
