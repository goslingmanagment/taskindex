## 2. Цель и критерии приёмки

Измеримые критерии; каждая строка проверяется тестом из раздела 5 или командой.

1. **B-04.** После перезагрузки с конвертом чужого поколения панель показывает имя команды и извлечённые тексты (`title`, `note`, `text`, `name`, `fields.*`) и кнопку «Убрать». Клик удаляет ключ `taskindex/ops/<id>` и запись из `pending`; вторая перезагрузка панель не показывает. `WorkspaceStore.dismiss(id)` публичный. `PendingOperation.attempts` удалён, `PendingOperation.message` читается панелью.
2. **B-06.** `POST project.create` с именем существующего проекта возвращает `current.id` существующего проекта; `project.update` с переименованием в занятое имя тоже. Диалог создания при 409 показывает «Такое направление уже есть: <имя>» и кнопку «Открыть существующее», после которой сохранение идёт как `project.update` по `current.id`.
3. **B-07.** Без `navigator.locks` пять перезагрузок оставляют один scope и исходное число ключей черновиков. ## 3. Решение

### 3.1 B-04: явное завершение операции чужого поколения

Выбрано: публичный `dismiss(id)` в store, содержимое конверта в панели, кнопка «Убрать». Чистая функция `describeEnvelope(envelope)` в новом `src/web/app/pending.ts` извлекает подписи команд и человеческие тексты (`title`, `note`, `text`, `name`, `description`, `waitingFor`, `fields.title`, `fields.note`) для одиночных команд и пакетов.
Отвергнуто: автоматический перенос конверта в черновик задачи. Черновик привязан к `taskId` и `baseRevision` прежнего поколения, у `task.create` id может не существовать; ручной перенос с видимым текстом честнее и покрывает все команды. Отвергнуто: автоудаление при загрузке, потому что владелец потеряет текст молча (план §7, `2026-09-08-taskindex-v2.md:488-490`, требует показать текст для ручного переноса).

### 3.2 B-06: `current` это запись, которую не меняли

Выбрано: `assertInvariants(state, changedIds?: ReadonlySet<string>)`; при конфликте `current` это участник пары, которого нет в `changedIds`, иначе первый встреченный. `applyCommand` передаёт `new Set(effects.map((e) => e.entityId))` (эффекты уже собраны к моменту `:655`). Правило одно для имён проектов, `orderKey` и `origin`. Правка живёт в `src/shared/commands.ts`, потому что то же значение читают CLI и агенты.
UI: в `ProjectDialog` состояние `id` становится изменяемым; при 409 в режиме создания (`project === undefined`) панель показывает «Такое направление уже есть: <name>» и «Открыть существующее» (`setBase(current); setId(current.id)`), после чего форма работает как редактирование существующего проекта с введёнными владельцем описанием и цветом. Режим редактирования сохраняет текущую кнопку «Совместить и проверить».
Отвергнуто: `Map<nameKey, Project>` с «ранее встреченной» записью (предложение отчёта). Оно верно для `create`, но при `project.update` с переименованием в занятое имя ранее встреченной может оказаться именно изменяемая запись.

### 3.3 B-07: переиспользование scope и сборка мусора

Выбрано: без `navigator.locks` перезагрузка использует `previous` из sessionStorage без копирования; новая вкладка без `previous` создаёт scope и копирует из самого свежего кандидата (сохраняется обещание плана §7 `:480-481`). После выбора scope запускается GC: для каждого кандидата, кроме своего и `legacy`, если маркер старше `DRAFT_SCOPE_TTL_MS` (30 дней; `at === 0` считается старым) и он не занят (при наличии locks `claim` успешен и сразу освобождается; без locks занятость проверить нельзя, поэтому удаляются только просроченные), удалить ключи `taskindex/drafts/<scope>/*` и маркер. Логика выбора выносится в экспортируемую `chooseScope(deps)` с инъекцией `storage`, `session`, `locks`, `now`, чтобы тесты воспроизводили репро без jsdom.
Отвергнуто: удалять scope сразу при закрытии вкладки (`pagehide`): событие ненадёжно, а восстановление после закрытия вкладки это заявленная функция (`2026-09-08-taskindex-v2.md:477-478`).

### 3.4 B-08: два режима чтения URL

Выбрано: `parseLocation(search: string): LocationState` и `serializeLocation(state): string` как чистые функции в `url.ts`; инициализатор `useState(() => parseLocation(location.search || savedLocation()))`, обработчик `popstate` вызывает `parseLocation(location.search)` без fallback.

### 3.5 V5: переподключение по `readyState`

Выбрано: в `onerror` проверять `stream.readyState === EventSource.CLOSED` → обнулить `stream`/`identity`, запланировать `connect` через `min(1000 * 2 ** attempt, 30000)`; `onopen` сбрасывает `attempt`; в минутном таймере вызывать `connect()` если `stream === null`; в `connect` условие раннего выхода дополняется `stream.readyState !== EventSource.CLOSED`. ### 3.6 Ж3: перечитывать только события своей задачи

Выбрано (вариант A, малый): `StoreState.snapshotEpoch` инкрементируется в `loadSnapshot`; `TaskDiscussion` зависит от `relevantSeq = max(seq of lastEvents where entityId === task.id || taskId === task.id)` и `snapshotEpoch`, а не от `seq`. Отложено (вариант B): проекция комментариев в store (`store.loadComments(taskId)` заполняет `confirmed.comments` для задачи, `applyEvent` держит их актуальными, UI читает `data.comments`). До тех пор `confirmed.comments` остаётся внутренней структурой `applyEvent` для подсчёта `commentCount`.

### 3.7 Границы: `request(path, schema)`

## 6. Риски и откат

- **Регресс поведения при декомпозиции.** Смягчение: шаги 10-14 переносят код без изменения логики, e2e по ролям не трогаются; переименования только те, что перечислены. Откат: каждый шаг отдельный коммит, `git revert` по одному.
- **`useDraft` меняет момент записи черновика.** Условие `enabled` может отложить запись на один рендер; тест `regressions.spec.ts:58` B01 ждёт «Есть изменения» перед сохранением в другой вкладке, это остаётся верным. Смягчение: e2e B01-B03 обязаны пройти после шага 9.
- **GC черновиков удалит нужное.** Порог 30 дней и требование незанятости; без locks удаляются только просроченные. Откат: `DRAFT_SCOPE_TTL_MS = Infinity`.
- **Переподключение SSE в цикле при 401.** После истечения сессии каждый `connect` получит 401 и `CLOSED`; backoff до 30 с ограничивает частоту; `AuthGate` по `session.isPending`/`refetch` отвечает за выход. Смягчение: при `CLOSED` сначала `request('/api/me', actorSchema)`; 401 → `setConnected(false)` без переподключения до события `online`/успешного `refresh`.
- **`request(path, schema)` начнёт отклонять ответы старого сервера при рассинхроне релизов.** Это и есть цель; деплой атомарный (один образ), риск только в dev с несовпадающими ветками.
- **Ленивые чанки при потере сети.** `lazy()` при ошибке загрузки чанка бросает; `Suspense` не ловит ошибки. Смягчение: `ErrorBoundary` вокруг ленивых компонентов с кнопкой «Обновить страницу»; после плана `11` чанки кэшируются `immutable`.
- **`manualChunks` меняет порядок инициализации Base UI/React.** Проверяется e2e; откат: убрать `manualChunks`, оставить `lazy`.

### Расхождения и решение
- Тяжесть. A-01: Astra P2, сверка низкая-средняя (данные не теряются, текст остаётся в форме, но тупик переживает закрытие карточки). Решение: все три исправляются в P1-блоке рядом с шагами 1-7, потому что правки дешёвые.
- Способ для B-08. `astra-06` предлагает адаптер хранилища с состояниями available/unavailable/write-failed и запрет отправки; здесь запрет `submit` при `storage === undefined` плюс постоянный баннер, по аналогии с уже существующей веткой квоты (`store.ts:304-312`). Переход на IndexedDB и memory-only outbox не делаются (с этим согласна и Astra).
- Способ для A-01. `astra-07` шаг 2: блокировать зависимый submit, пока pending той же задачи не завершён. Здесь: база из `confirmed` и сброс базы при отказе. Решение: база из `confirmed` это корневая правка, блокировка не нужна: сервер сливает по полям через `assertMerge` (`commands.ts:133-145`), поэтому сохранение с подтверждённой базой при незавершённом move либо применяется (поля не пересекаются), либо получает `conflict` (пересекаются), но не «из будущего». Вместо блокировки индикатор pending по задаче. Предупреждение Astra о безусловном rebase учтено: автоматического повтора с самой свежей revision нет, полевая панель конфликта остаётся.
- Способ для B-02. `astra-03` шаг 2: один механизм, либо удерживать события на время refresh и воспроизводить их после snapshot, либо игнорировать устаревший snapshot с обязательным догоном. Здесь второй вариант. Разведение «соединение открыто» и «состояние догнано» (`astra-03` шаг 6) не делается: `connected` остаётся признаком потока, `loading` покрывает refresh; записано как вне объёма.
- Q-06. Наблюдение Astra точнее нашего списка дублей: `QuickCreate` берёт новый `operationId` при любом `retryable:false` (`src/web/app/dialogs.tsx:100-101`), `InlineCreate` обнуляет намерение (`src/web/app/board.tsx:204`), `TaskDiscussion` сохраняет его (`src/web/app/activity.tsx:390-392`), а сервер хранит доменные отказы и на повтор с тем же id и другим payload отвечает `operation_mismatch` (`src/server/operations.ts:51-82`).
