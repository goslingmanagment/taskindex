## Причина и наблюдаемое поведение

Каждая команда читает state и весь журнал. readState повторно фильтрует checklist/comments по задачам, writeState линейно ищет каждую прежнюю задачу, lookup операции читает все результаты с дополнительными запросами. Страницы формируются после полной загрузки, SSE backlog не ограничен. Синтетический замер 50 000 событий дал около 250 мс на правку и 1 039 мс на lookup; это не производственный SLA.

## Что изменится и зачем

Сохранить SQLite и единый transactional executor, но привязать стоимость точечной операции к затронутым данным, а страниц — к размеру страницы.

## Шаги реализации

1. Сохранить воспроизводимый baseline на корректных доменных fixtures: разные размеры задач, комментариев и истории; отдельно read, command, operation lookup, feed и catch-up. Измерять SQL count, память и время, не только общий npm test.
2. Сначала заменить одиночные lookup и ленты индексными SQL-запросами, выбирать summary без полного JSON результата; проверить EXPLAIN QUERY PLAN и индексы actor/cursor/filter.
3. Убрать повторные фильтрации через группировку checklist/comments по taskId и Map прежних записей. Это промежуточное улучшение, не закрывающее чтение всего журнала.
4. Определить для каждой команды минимальный набор state/history, включая сложные save, sync и undo. Подготовить reader интерфейс для executor, сохраняя чистый reducer и единый источник доменных правил.
5. Сохранять эффекты операции по затронутым сущностям вместо сравнения всего state. Убедиться, что связанные counters, ownerFields, ревизии и событие остаются в одной транзакции.
6. Пагинацию делать на SQL-границе с явным курсором и стабильной верхней границей. SSE catch-up читать ограниченными пакетами, учитывать backpressure и отмену соединения; live-события не терять на стыке.
7. Повторить замеры на дисковой SQLite с текущим durability режимом. Не улучшать цифры выключением synchronous=FULL, fsync или снятием атомарности.

## Проверки

- [ ] Тесты идемпотентности, конфликтов, undo цепочек, batch rollback и import/export дают те же результаты.
- [ ] Lookup одного operation не загружает все operations; feed не материализует весь result JSON; ограниченный backlog не блокирует обработку нового запроса.
- [ ] Сравнить масштаб 1×/10× истории и количество прочитанных строк. Целевой бюджет задержки определить по baseline и рабочему профилю, не выдавать микробенчмарк за SLA.

## Критерий готовности

Задокументировано, какие полные сканы устранены, какие остались обоснованно; метрики и regression suite подтверждают улучшение без ослабления гарантий.

## Зависимости и границы

Жёстких зависимостей от других планов нет; работать от актуального snapshot исходников.

Срез history должен содержать всё необходимое для конфликтов и undo. Неполный history может ускорить код ценой неверных разрешений. Выполнять частями; формат operation cursor согласовать с планом 08, смена СУБД не входит в план.
