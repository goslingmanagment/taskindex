## (a) Вердикт

1. По фактам обе стороны сходятся в главном: стек оставить, единственная системная проблема реализации это полная загрузка состояния и журнала на каждую команду (наши D1/K1, их S-01/A-02). Оба бенчмарка воспроизводимы и согласованы между собой: рост линейный, наклон 5-10 мс на 1 000 событий в зависимости от размера `changes`, плюс квадратичная составляющая по числу задач в `writeState`.
2. Уникальные находки Astra по этой оси подтверждены все, кроме одной детали: S-02 (нет постоянного сигнала о здоровье репликации; `heartbeat-url` есть в Litestream 0.5.12, в `deploy/litestream.yml` не задан), S-03 (мигратор хранит имя без checksum), A-03 (строгий импорт ломается после любой миграции данных без событий), A-04 (rollback использует compose/litestream.yml/скрипты кандидата), S-06 (нет CI и preflight), A-01 (оптимистичная ревизия как предпосылка). S-05 подтверждён частично: WebKit в матрице нет, но «touch drag не проверен» неверно.
3. Уникальные находки нашей стороны у Astra отсутствуют: две записи в БД на каждую проверку ключа агента с обходом `writes: held` (S1/V3), открытые маршруты `/api/auth/api-key/*` (V8), курсор, инвалидируемый любой записью (V1), EventSource без переподключения после фатального закрытия (V5), Drizzle как маппер и дрейф `COLLATE BINARY` (D2), OpenAPI без потребителей (S3), два стилевых мира и `shadcn` как зависимость сборки (F1/F2), отсутствие `Cache-Control`/gzip/HTTP/2 (F3/P3), сборка образа на VPS (P1), `dryRun` в хеше (Ж4), `ownerFields` для всего чеклиста (Ж7). Astra при этом прямо рекомендует оставить api-key плагин и утверждает, что OpenAPI потребляется агентами, что коду не соответствует.
4. Наша ошибка: V7 (review-2) объявил `/health` источником постоянных fsync и WAL-кадров; повторный замер сегодня дал 0 байт WAL на 20 холостых `UPDATE settings SET value=value`. Review-1 это уже опровергал, README планов противоречие снял. Astra стоимости `/health` не утверждала.
5. Кто лучше по этой оси. По стеку (выбор и использование библиотек, сборка, зависимости) наша сторона сильнее: больше проверенных по коду находок, меньше фактических ошибок, рекомендации конкретнее (таблица keep/simplify/replace с причинами, замеры бандла и заголовков). По эксплуатации и жизненному циклу схемы сильнее Astra: три её уникальных пункта (S-02, A-04, A-03) по цене последствий дороже любого нашего уникального пункта, кроме S1/V3. В сумме перевес за нашей стороной по объёму и точности, но все уникальные пункты Astra подлежат включению в планы; без них наш раздел «Развёртывание» (P4/P5) выглядит незаслуженно хвалебным.

## (c) Разбор уникальных и спорных пунктов

### Бенчмарки: согласованность и методология

Оба измерения сделаны на `:memory:` без fsync и сети, оба зовут настоящий `executeOperation` после `migrate`. Различия:

- Наш `bench-events.ts` (review-2): 300 задач, заметка 1 КБ, журнал растёт правками заметки, поэтому каждое событие несёт from/to по 1 КБ (`changes` 0,7 → 10,2 МБ). Наклон около 10 мс на 1 000 событий. Наш `repro/perf.mts` (review-3, B-03): через `app.request` с тестовым `authorize`, 2 010 задач, заметки 200 байт, 4 010 событий: 3,3 мс при пустой базе → 35,7 мс; `/api/operations?limit=50` 95 мс; `/api/operations/{id}` 88 мс; digest 108 мс.
- Их `01-stack-bench.ts`: (1) N задач через `writeState` без истории, `task.update` одной задачи: 1,3 / 8,5 / 63 мс при 100 / 1 000 / 5 000 задач; (2) одна задача, история засеяна копиями seed-события и seed-операции через `INSERT`: 4,8 / 45 / 250 мс при 1 000 / 10 000 / 50 000; «operation lookup» это `readOperations(db).find(...)`, то есть ровно путь `/api/operations/{id}` (`app.ts:736`): 21 / 229 / 1 039 мс.
- Мой повтор их скрипта из scratch: 1,7 / 8,8 / 65,8 мс; 5,4 / 48 / 253,7 мс; lookup 24 / 238 / 1 106 мс. Расхождение до 7%, числа честные.
- Согласованность: их наклон около 5 мс на 1 000 событий при мелких `changes` (копия create-события небольшой задачи), наш 10 мс при `changes` около 2 КБ; на 4 000 событий их модель даёт около 20 мс, наш B-03 даёт 32 мс сверх базы при 2 010 задачах, куда входит и квадрат по задачам (по их же кривой около 20 мс на 2 000 задач). Всё сходится. Стоимость lookup операции у обоих 21-24 мс на 1 000 операций (N+1 по заголовкам). Экстраполяция «50 000 событий это 250-500 мс на команду» корректна; их 250 мс это нижняя граница для журнала без крупных заметок.
- Особенность их посева: все 50 000 событий принадлежат одной задаче, поэтому фильтр `assertMerge` (`commands.ts:133-141`) перебирает максимальное множество; в реальном пространстве события распределены по задачам. Это не меняет вывода: доминирует `readEvents` с JSON-парсингом `changes`.
- Что дали только они: масштабирование по числу задач без истории (63 мс при 5 000) и явное указание на O(T²) в `db.ts:191-196`. Что дали только мы: стоимость через HTTP-слой и конкретные эндпоинты (digest, operations, history), зависимость от размера `changes`, замер `readState` отдельно.

### S-02 Litestream без постоянного сигнала: ПОДТВЕРЖДЕНО, приоритет оправдан

- `deploy/litestream.yml:1-20`: `logging`, `snapshot`, `shutdown-sync-timeout`, `socket`, `dbs`; нет `heartbeat-url`, `heartbeat-interval`, `addr`. `deploy/litestream.local.yml` то же. `compose.yml:41-59`: у сервиса `litestream` нет healthcheck, только `restart` и ротация логов. `app.ts:408-423`: `/health` ничего не знает о реплике. `deploy/common.sh:39-49` `confirmed_sync` вызывается только из `deploy.sh`/`rollback.sh`/drill. README, `deploy/README.md`, план v2 и BACKLOG не упоминают мониторинг, оповещение или dead-man switch (grep по «мониторинг|наблюд|оповещ|heartbeat|alert|prometheus»: только SSE-heartbeat и UI `alert-dialog`).
- Возможности пина 0.5.12: в `cmd/litestream/main.go` тега v0.5.12 есть поля `HeartbeatURL string yaml:"heartbeat-url"`, `HeartbeatInterval *time.Duration yaml:"heartbeat-interval"` с минимумом 1 минута и проверкой `http(s)://`, а также `Addr string yaml:"addr"` для Prometheus-метрик. Документация датирует heartbeat версией 0.5.6. Пинг уходит только если все базы успешно синхронизировались в пределах интервала, то есть это именно сигнал «реплика жива», а не «процесс жив».
- Значимость: для продукта, у которого единственная защита от потери VPS это Litestream, тихий отказ репликации (истёкшие ключи S3, закрытый bucket) остаётся невидимым до аварии. Цена закрытия: две строки в `litestream.yml`, переменная `LITESTREAM_HEARTBEAT_URL` в `.env.example`/`compose.yml`, внешний получатель (healthchecks.io или самодельный timer на хосте). Ограничение: контейнеру `litestream` нужен исходящий доступ к URL получателя. Их P1 «до рабочих данных» обоснован. Наш P5 («верный выбор») и P4 это пропуск: мы проверили конфигурацию репликации и не задали вопрос «кто узнает, что она сломалась».

### S-03 checksum миграций: ПОДТВЕРЖДЕНО

- `db.ts:69-71` таблица `__taskindex_migrations(name TEXT PRIMARY KEY)`; `:75-76` отклоняет неизвестные имена; `:77-87` применяет файлы, которых нет по имени. Содержимое применённого файла не сверяется. `tests/api/migrations.test.ts` сверяет снапшот Drizzle со схемой и имена файлов с журналом, но не содержимое с базой.
- Наш V6 накрывает соседнюю проблему (ручная `SCHEMA_VERSION`, два описания одного набора), но не правку применённого SQL под тем же именем. Значимость средняя: сейчас один baseline и README запрещает правку, однако защита стоит одну колонку `sha256` и одну проверку. Их оговорка «штатный мигратор Drizzle тоже надо проверить на checksum» верна: `drizzle-orm/better-sqlite3/migrator` хранит hash, но сверяет по нему только идентичность записи, а не отказ при изменении файла; это отдельная проверка.

### A-03 контракт совместимости events/results/import: ПОДТВЕРЖДЕНО, с уточнением рамок

- Проба Astra воспроизведена из scratch: после `UPDATE tasks SET note=...` без события `/health` зелёный, экспорт строится, `importWorkspace` отказывает «состояние записей не совпадает с журналом событий» (`admin.ts:354-360`). Механизм: `applyEvent` (`commands.ts:658-700`) собирает запись только из `changes`, поэтому любое поле, появившееся в таблице без события (data-миграция, новая колонка с default), делает replay неравным таблицам. `admin.ts:369-373` дополнительно требует точного совпадения `schema_version`, то есть импорт экспорта старой версии уже невозможен по замыслу; неучтённый случай это импорт экспорта той же версии после миграции данных.
