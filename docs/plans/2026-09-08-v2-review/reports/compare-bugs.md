## (a) Вердикт

1. Обе стороны нашли только реальные дефекты: из 25 различных функциональных претензий (после дедупликации) ни одна не опровергнута; 24 подтверждены кодом и/или воспроизведением, одна (наш B-12) осталась PLAUSIBLE.
2. Пересечение маленькое: полностью совпали только стоимость O(N) на команду (наш B-03 / их S-01, A-02) и неограниченный SSE-хвост (наш B-11 / пункт их S-01). Частично: их B-06 `none`/`all` (у нас это code smell в review-4, а не функциональный баг) и их B-03 (у нас общая формулировка «клиент не валидирует ответы» в review-4 §4).
3. Только у нас: 14 претензий (B-01, B-02, B-04..B-10, B-12, V3, V5, V8, A1 из review-5), в том числе две самые значимые для продукта: агент со scope `tasks` отменяет решения владельца и ставит `focus`, и общий outbox, из которого `operation resume` второго агента исполняет чужой конверт. Только у них: 9 претензий (B-01..B-05, B-07, B-08, A-01, плюс функциональная часть B-06), все реальные, все мы пропустили, и три из них лежат в зонах, которые наш review-3 отметил как проверенные без замечаний («SSE сходится», «Auth/скоупы», «Снимок и курсоры»).
4. По тяжести Astra систематически завышает: 7 из 9 их пунктов на деле низкой тяжести (краевые id, редкие браузерные режимы, гонка с самовосстановлением). Их P1 «отозванный ключ держит SSE» реален, но для этого продукта не главный дефект: поставляемый CLI не открывает SSE вовсе (`events --follow` опрашивает `/api/events` раз в секунду, `run.ts:387-390`), отзыв через CLI действует за секунду; наш «агент отменяет владельца/ставит focus» срабатывает на штатном пути основных операторов и важнее.
5. Итог по оси: небольшой перевес нашей стороны по охвату (14 уникальных против 9), по продуктовой значимости топ-находок и по калибровке тяжести; Astra сильнее в глубине проверки границ контракта и sync-протокола (валидация ответов, гонка snapshot/SSE, путь ZodError, семантика `since`, коллизии id), где мы поставили зелёные галочки. Ни одна сторона не закрыла ось одна: объединённый список даёт 25 пунктов, из них 5 средней тяжести (наши B-01, B-02, A1, B-05 CLI и их B-01), остальное низкая.

## (c) Разбор уникальных и спорных пунктов

### Их B-01 (P1): отозванный ключ держит открытый SSE. CONFIRMED, тяжесть средняя, не P1

Код: авторизация выполняется один раз в middleware `app.ts:305-308` (`authorizeRequest`); замыкание `send` (`app.ts:810-823`) не знает актора и проверяет только локальный `closed`; `subscribers.add(send)` (`app.ts:847`); heartbeat каждые 25 с (`app.ts:839-845`) держит соединение под nginx `proxy_read_timeout 1h` (`deploy/nginx/taskindex.conf:35`) неограниченно; `revokeAgentKey` (`admin.ts:200-212`) лишь ставит `enabled=false`. Тест `tests/api/auth.test.ts:182-186` проверяет отзыв только для нового запроса (`/api/me`), поток не покрыт.

Перезапуск их probe (копия, реальный Better Auth): `{"freshRequestStatus":403,"mutationStatus":200,"receivedPostRevocationTitle":true}`.

Почему не P1 для этого продукта: (1) поставляемые клиенты агентов не открывают `/api/events/stream`: `taskindex events --follow` опрашивает `/api/events` раз в секунду (`run.ts:387-390`), и после отзыва получает 403 на следующем опросе; уязвим только самописный SSE-клиент или `curl` по OpenAPI; (2) окно ограничено жизнью процесса (`closeStreams()` на SIGTERM, рестарт контейнера); (3) эффект только чтение новых событий, запись проверяется на каждом POST. Это реальный пробел контроля доступа и его надо закрыть до того, как ключи начнут раздаваться за пределы собственной машины владельца, но он уступает нашим B-01/B-02, которые срабатывают на штатном пути через штатный CLI без чьего-либо злого умысла. Важная связка: наша рекомендация V3 (кэш `verifyApiKey` на 30-60 с) расширяет то же окно; проектировать вместе.

### Наши B-01/B-02 против их B-01: что важнее

Наш repro перезапущен: `agent(tasks) undo of owner archive -> 200 {"ok":true}`, `task archived after agent undo: false`, `agent-synced focus:true task lands in group: selected`, `agent task.update focus:true -> 200 true`. Код: `requireScope` (`commands.ts:65-68`) проверяет только scope и вид сущности; в ветке `undo` (`commands.ts:329-335`) проверка автора есть только для комментариев; `focus` разрешён во всех task-командах (`schemas.ts:82`), в `task.sync` блокируется лишь при `ownerTouchedAt` (`commands.ts:561-573`). Это нарушение обещания продукта «решения владельца защищены от агентов» на основном рабочем пути. Решение: наши B-01/B-02 выше их B-01. Astra их не нашла, хотя объявила проверенными «Undo», «сохранение owner fields» и «проверки scope» (03-bugs.md:231, 236).

### Наш A1 (review-5): общий outbox и `operation resume` чужого конверта. CONFIRMED, средняя, у них нет

Воспроизведено сегодня `shared-outbox.mts` через настоящий `runCli` и in-process приложение с двумя ключами при одном `XDG_STATE_HOME`: конверт агента A (`a-op-1`) лежит в outbox; агент B запускает `operation resume` без id и получает `{"ok":true,"operationId":"a-op-1",...}`; `task.createdBy = agent:codex`, `stored operation actorId: agent:codex`; конверт удалён из outbox; последующий `operation resume a-op-1` агента A даёт `invalid_arguments: Сохранённый конверт не найден` (exit 2). Код: `Outbox` строит путь только из `XDG_STATE_HOME` (`outbox.ts:47-53`), `list` фильтрует по `baseUrl`, не по актору (`:83-98`), `run.ts:212-221` печатает чужие `pendingOperations`, `:232-244` пересылает все. Это ровно конфигурация владельца (Claude Code и Codex под одним пользователем macOS). Astra перечислила `resume` и outbox как проверенные (03-bugs.md:232) и пропустила.

### Их B-02 (P2): старый snapshot стирает SSE. CONFIRMED, тяжесть низкая

Код: `loadSnapshot` (`store.ts:155-169`) безусловно заменяет `confirmed`/`seq` и чистит буфер; `refresh` (`:170-191`) применяет ответ, начатый раньше; `sync.ts:11` не пересоздаёт поток при той же generation; UI-триггер «Обновить данные» `shell.tsx:520`. Их probe перезапущен: `afterEvent {seq:1,tasks:1}` → `afterSnapshot {seq:0,tasks:0,connected:true}`.

Моё расширение (`extra-probes.mts` (c)): при следующем живом событии (seq 2) `ingest` не находит seq 1, буферизует и вызывает `catchUp` → `/api/events?since=0` → состояние восстанавливается: `{"seq":2,"tasks":2}`. То есть устаревание временное, до первого следующего события в пространстве; на активной доске с агентами это секунды, на пустой доске до ручного действия. Дефект реальный (UI при `connected=true` показывает откат), но без потери данных и с самоизлечением. Исправление дешёвое: в `refresh` после `loadSnapshot` вызывать `catchUp()`, либо в `loadSnapshot` при той же generation и `snapshot.seq < state.seq` не заменять состояние, а догонять.

### Их B-03 (P2): CLI принимает произвольный 2xx JSON. CONFIRMED, низкая

Код: `exitCode` (`client.ts:41-43`) возвращает 0 для любого 2xx с `body.ok !== false`; `send` (`:144-148`) по этому признаку удаляет конверт. Probe перезапущен: `{"reply":{"status":200,"body":{"status":"maintenance"}},"exitCode":0,"outboxExists":false}`. Требуется upstream, отвечающий JSON 200 не от TaskIndex (ошибочный `TASKINDEX_URL`, чужой прокси); nginx-заглушка HTML уже ловится `invalid_response`. Вероятность низкая, но нарушение гарантии durable outbox настоящее, а исправление одна проверка: `operationSuccessSchema.safeParse(body)` и совпадение `operationId`/`generation` перед `remove`. Наш review-4 §4 назвал общую причину («клиент не валидирует ответы», `ApiReply.body: Record<string, unknown>`), но не довёл до следствия с удалением конверта: здесь Astra точнее.

### Их B-04 (P2): `since` теряет no-op и отказы. CONFIRMED, низкая

Код: `app.ts:717` и `:963` фильтруют `(o.lastSeq ?? 0) > since`; у операций без событий `lastSeq=null`. Моя проверка показывает асимметрию: `operations?until=1` → `["rejected","noop","initial"]`, `operations?since=0` → `["initial"]`, `digest` по умолчанию → `["initial"]`. То есть `since=0` не эквивалентен «всё», а digest никогда не покажет отказы и no-op. Это несогласованность контракта, а не потеря данных: полная лента и UI их показывают, а собственные отказы агент получил в ответе. Для агента, читающего только `digest`, невидимы чужие отказы (например, владельца), что имеет ограниченную ценность. Правильное направление их же: отдельный монотонный курсор операций (`rowid`/`createdAt`), минимум: `since=0` возвращать всё и задокументировать.

### Их B-05 (P2): инвариант чеклиста бросает ZodError. CONFIRMED и расширен, низкая

Код: `assertInvariants` вызывает `checklistSchema.parse(t.checklist)` (`commands.ts:217`); все остальные инварианты идут через `fail()` (DomainError); executor сохраняет только DomainError (`operations.ts:124`), остальное летит в `app.onError` → 400 `invalid` без записи (`app.ts:262-271`). Их probe перезапущен: 400, `operation get` 404, повтор того же id другой командой 200.

Моё расширение (`extra-probes.mts` (a)): тот же путь достижим без 101 пункта: `checklist.add` с `id`, уже существующим в этой задаче, нарушает refine уникальности → `{"status":400,"code":"invalid"}`, `operation get` 404, чужая команда с тем же id → 200. Это реалистичнее для агента (повтор шага с тем же id). Последствие всё равно ограничено: клиент получает окончательный `retryable:false`, конверт удаляется, база не тронута; страдает только идемпотентный контракт. Исправление: в `assertInvariants` заменить `parse` на явные `fail('invalid', …)` для длины и дублей.

### Их B-06 (P2) и B-07 (P2): коллизии id. CONFIRMED, оба низкая

`queries.ts:118-122` трактует `all`/`none` как фильтры; `shell.tsx:124` повторяет; `idSchema` (`schemas.ts:3`) допускает оба. `app.ts:593` регистрирует статический `/api/tasks/by-origin` раньше `/api/tasks/{id}` (`:609`), и Hono отдаёт первый совпавший маршрут, который падает на валидации query. Их probe перезапущен: проект `none` создан (200), `?project=none` возвращает только `unassigned`; задача `by-origin` создана (200), `GET /api/tasks/by-origin` → 400. Моя проверка сузила B-07: `/api/tasks/by-origin/history`, `/comments` и поиск работают, ломается только одиночный GET. Оба требуют, чтобы кто-то намеренно выбрал служебное слово как id; агенты обычно получают UUID. Наш review-4 §2 отметил sentinel-строки как проблему читаемости и типов (14 сравнений в 7 файлах), но не как функциональную ловушку с воспроизведением: здесь Astra довела до бага, мы остановились на smell. ### Их B-08 (P2): недоступный localStorage. CONFIRMED, низкая

`browserStorage()` (`drafts.ts:8-14`) превращает SecurityError в `undefined`; `persist` (`store.ts:118-124`) с optional chaining «успешно» ничего не пишет; `submit` (`:304-312`) блокирует только исключение. Probe перезапущен: 4 POST, pending 1 до перезагрузки, 0 после, черновик не переживает экземпляр. Getter бросает в редких режимах (Firefox с выключенным storage, sandbox-iframe, политики блокировки site data); на собственном телефоне владельца это маловероятно; при квоте (`setItem` бросает) поведение уже корректно, что они честно отметили. Не путать с нашим B-07 (рост scope черновиков без Web Locks): разные дефекты одного слоя. Исправление: при `storage === undefined` либо отказывать в `submit` с понятным сообщением, либо показывать постоянный баннер деградации.

### Их A-01 (P2): оптимистичная revision как база редактора. CONFIRMED и расширен, низкая-средняя

Код: превью через `applyCommand` поднимает `revision` (`store.ts:88`, `commands.ts:256`); редактор берёт `task` из `data` (оптимистичной проекции) в `saved` (`editor.tsx:114-118`); `taskSaveCommand` ставит `baseRevision: base.revision` (`use-workspace.ts:24`); сервер отвергает `base > record.revision` как `invalid` (`commands.ts:132`).
