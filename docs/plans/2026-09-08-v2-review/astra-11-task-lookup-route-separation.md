## Причина и наблюдаемое поведение

Задача с допустимым ID by-origin создаётся, но GET /api/tasks/by-origin попадает в статический поиск по источнику и возвращает 400. Маршрутизатор забирает адрес существующей сущности.

## Что изменится и зачем

GET задачи работает для всех допустимых ID, а поиск по origin имеет отдельный недвусмысленный адрес.

## Шаги реализации

1. Перенести поиск по источнику на новый маршрут с дополнительным сегментом, например /api/tasks/lookup/by-origin. Проверить, что ни один допустимый одночастный ID не может с ним совпасть.
2. Описать совместимость старого адреса: запрос с полным набором legacy origin-параметров направлять в поиск, запрос без них трактовать как GET буквального ID. Невалидные смешанные параметры отклонять явно.
3. Обновить OpenAPI, типизированные клиенты, CLI-команду lookup и агентские инструкции.
4. Просмотреть остальные статические маршруты рядом с /{id}; составить таблицу разрешения маршрутов, включая неизвестный ID и query-параметры.
5. Сохранить поддерживаемые ID в импорте и записи. Не удалять/переименовывать by-origin в пользовательской базе ради маршрута.

## Проверки

- [ ] Создание и GET task by-origin возвращают ту же запись; обычные ID работают как раньше.
- [ ] Новый lookup и legacy-запрос с origin находят одну задачу; неполный legacy query получает понятный ответ.
- [ ] Проверки API/CLI и OpenAPI-пример не расходятся; encoded path не создаёт новой неоднозначности.

## Критерий готовности

Исходный probe проходит; таблица адресов однозначна, миграция предметных данных не требуется.

## Зависимости и границы

Жёстких зависимостей от других планов нет; работать от актуального snapshot исходников.

Простое переставление маршрутов местами сломает старый lookup. Совместимость должна определяться явно, а не случайным порядком регистрации.
