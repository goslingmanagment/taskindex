## Причина и наблюдаемое поведение

request<T> возвращает тип через приведение, а SSE принимает распарсенный JSON без полноценной проверки контракта. Существование TypeScript-типа не проверяет реально пришедшие bytes. Несовместимый ответ может попасть в confirmed, обработку pending или интерфейс.

## Что изменится и зачем

Каждый входящий snapshot, event, operation-result и справочный ответ проверяется до изменения состояния; endpoint определяет тип результата, а не произвольный generic вызывающего кода.

## Шаги реализации

1. Составить реестр реально используемых endpoint и SSE-сообщений с соответствующими shared-схемами. Отделить JSON бизнес-ответы от auth API и потокового framing.
2. Заменить произвольный request<T> на методы endpoint с выведенными типами; использовать существующий Hono AppType/hc там, где он действительно сохраняет тип маршрута.
3. На runtime-границе добавить safeParse общих схем. Проверять связность generation/seq/operationId дополнительно к форме объекта; не дублировать заново доменную модель.
4. В SSE разбирать тип сообщения и валидировать payload до вызова store. Необратимо неправильные сообщения должны запускать понятный протокольный recovery, а не оставлять connected=true.
5. Определить пользовательскую ошибку несовместимого клиента: сохранить черновики и pending, предложить обновление после безопасного сохранения; не стирать данные ради чистого запуска.
6. Обновить тестовые transport-заглушки, чтобы они соответствовали реальным schema/result contracts. Не прятать несовместимые fixtures за as unknown as.

## Проверки

- [ ] Malformed snapshot/events не меняют confirmed/seq и не завершают pending.
- [ ] Схема валидна, но generation/ID неверны — ответ отвергается на уровне корреляции.
- [ ] Валидные ответы проходят без второй несовместимой трансформации; ошибки сети, протокола и домена различимы в UI и тестах.

## Критерий готовности

Все входные пути store покрыты валидацией; создание нового endpoint требует явного контракта; сохранность черновиков проверена при protocol mismatch.
