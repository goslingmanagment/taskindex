## 2. Цель и критерии приёмки

Цель: сервер обеспечивает записанную политику прав, а не только текст скилла; `/api/context.rules`, SKILL.md и тесты говорят одно и то же.

Критерии:

1. Матрица прав (раздел 3.1) закреплена табличным тестом `tests/api/permissions.test.ts`: каждая ячейка проверяется отдельным `it` через реальное Hono-приложение с `:memory:` SQLite (`tests/api/helpers.ts`).
2. Агент (`tasks` и `write`) получает `403 forbidden` на `undo` операции или события, среди событий которой есть хотя бы одно с `actorId !== actor.id`; состояние не меняется, операция сохраняется как отклонённая (как сегодня для 403). Владелец отменяет любые операции без изменений в поведении.
3. Агент получает `403 forbidden` на `task.create`, `task.update`, `task.save`, содержащие `focus`; `task.sync` с `focus` возвращает `skipped: [{field: 'focus', reason: 'owner'}]` независимо от `ownerTouchedAt` и не пишет `focus`. Группа Focus `selected` содержит только задачи с `focus`, выставленным владельцем.
4. Команда владельца без предметных изменений не создаёт события, не меняет `revision`, `ownerTouchedAt` и `ownerFields`; ответ `200` с `firstSeq: null`, `events: []`.
5. `task.sync` для существующей задачи принимает `fields` без `area` и `title`; для новой задачи их отсутствие даёт `400 invalid` с сообщением `Для новой задачи из источника нужны area и title.`. В ответе `skipped` содержит только поля, чьё входящее значение отличается от текущего; совпадающие поля перечислены в новом необязательном `unchanged: string[]`; `applied` содержит только записанные поля.
6. `orderKey` не попадает в `ownerFields` (при этом `ownerTouchedAt` перетаскиванием по-прежнему ставится).
7. Решение по чеклисту принято владельцем и записано в разделе 3.4; при выборе поэлементной защиты проходят тесты шага 13.
8. Тексты `/api/context.rules` (`app.ts:897-905`) и SKILL.md (план 12) описывают ровно эту политику; тест `tests/api/permissions.test.ts` проверяет наличие ключевых фраз в `rules`.
9. Property-тесты `tests/property/commands.test.ts` и `tests/property/undo.test.ts` генерируют актора из `{owner, agent write, agent tasks}` и проверяют инварианты раздела 5.
10. `npm run check` зелёный: `tsc`, oxlint, oxfmt, vitest (75 текущих тестов плюс новые). `npm run e2e` зелёный (18 тестов): UI владельца поведения не меняет.

## 3. Решение

### 3.1 Матрица прав (целевая; в скобках текущее поведение, если отличается)

| Команда | owner | agent `write` | agent `tasks` | agent `read` |
|---|---|---|---|---|
| GET `/api/*` чтение | да | да | да | да |
| `project.create`, `project.update` | да | да | 403 | 403 |
| `task.create/update/save/move/archive/restore` без `focus` | да | да | да | 403 |
| те же команды с `focus` в payload | да | 403 (было: да) | 403 (было: да) | 403 |
| `task.sync` | да | да; `focus` всегда в `skipped` (было: применялся до касания владельца) | да, так же | 403 |
| `checklist.add/update/remove/reorder` | да | да | да | 403 |
| `comment.add` | да | да | да | 403 |
| `comment.remove` своего комментария | да | да | да | 403 |
| `comment.remove` чужого комментария | да | 403 | 403 | 403 |
| `undo` своей операции или своего события | да | да | да, кроме групп с проектами: 403 | 403 |
| `undo` операции другого агента | да | 403 (было: да) | 403 (было: да) | 403 |
| `undo` операции владельца | да | 403 (было: да) | 403 (было: да) | 403 |
| `undo` операции, где есть `project.create` | 409 `not_undoable` | 409 (своя) или 403 (чужая) | 403 | 403 |
| `batch` | правила применяются к каждой команде; первая ошибка отклоняет пакет целиком с `commandIndex` (как сегодня) | | | |

Порядок проверок в `undo`: (1) есть ли события цели, иначе `not_undoable`; (2) авторизация актора на все события цели (`forbidden`); (3) `project.create` внутри цели (`not_undoable`); (4) по группам: `requireScope`, чужой комментарий (`forbidden`), поздние правки (`conflict`). Авторизация раньше семантики, чтобы агент не узнавал о содержании чужой операции через разные коды ответа.

### 3.2 Политика undo (решение владельца, рекомендация)

Варианты:

- **A. Агент отменяет только свои операции.** Проверка: все события цели имеют `actorId === ctx.actor.id`. Владелец отменяет любые. Рекомендуется: правило формулируется одной фразой, совпадает с уже существующим правилом для комментариев, минимальная матрица тестов; ошибку другого агента исправляют прямой командой с `baseRevision` (это остаётся видимой операцией с верной атрибуцией) или владелец через «Активность».
- **B. Агент отменяет любые операции, кроме операций с событиями владельца.** Позволяет агенту-ревьюеру чистить за другим агентом через undo. Минус: доверие владельца к «Активности» ниже, коллизии двух агентов, отменяющих друг друга; правило длиннее.
- **C. Агент не отменяет события, затрагивающие поля из `ownerFields`.** Самое тонкое, но объяснить агенту сложно, а `ownerFields` пополняется и после отменяемой операции, что даёт неочевидные отказы.

Сводный `README.md` этой папки записывает рекомендацию «только свои; операции владельца никогда» (вариант A). Ниже шаги написаны для A; переход на B это замена одного предиката на шаге 3.

### 3.3 Политика focus

`focus` это личный шорт-лист владельца. Прямые команды агентов с `focus` отклоняются `403 forbidden` («Поле focus меняет только владелец.»), а не игнорируются молча: агент должен получить сигнал, а не считать задачу выбранной. В `task.sync` поле не отклоняет весь вызов (sync по контракту терпим к частичному применению), а всегда идёт в `skipped` с `reason: 'owner'`. Альтернатива «убрать `focus` из схем для агентов» отвергнута: Zod-валидация в Hono выполняется до того, как известен актор, а две версии схем усложнят `/api/context.commands`. Проверка в чистом редьюсере одна для сервера и для превью в браузере.

Следствие для CLI: `taskindex task focus ID` для агентов теряет смысл и удаляется из справки (план 03). Для владельца в браузере ничего не меняется: превью использует актора `owner` (`src/web/app/store.ts:100-105`).

### 3.4 Гранулярность `ownerFields` (решение владельца)

- `orderKey`: исключить из `ownerFields`. `task.sync` не принимает позицию, `assertMerge` защищает порядок через список `keys` (`commands.ts:647`), а не через `ownerFields`. `ownerTouchedAt` от перетаскивания сохраняется: владелец, тронувший карточку, действительно «занялся» задачей, и блокировка `status/archived/focus/projectId/area` для sync остаётся по плану §5.
- `checklist`, вариант **A (документировать как есть)**: одно ручное касание чеклиста замораживает его для sync навсегда; правило записывается в `/api/context.rules` и SKILL.md: «после ручной правки чеклиста источник его не обновляет; новые шаги добавляйте `checklist.add` по поручению». Усилие S.
- `checklist`, вариант **B (поэлементная защита)**: в `ownerFields` пишутся `checklist:<itemId>` для шагов, которые владелец добавил, изменил или удалил, и `checklist:order` при перестановке; sync сливает список поэлементно (раздел 3.5). Усилие M, шаги 11-13. Сводный `README.md` рекомендует B. Рекомендация этого плана: сначала выполнить шаги 1-10 (A в качестве временного состояния с документированием), затем B отдельным коммитом, чтобы P0-часть не ждала.

### 3.5 Слияние чеклиста при sync (для варианта B)

Входящий список `incoming` из источника, текущий `current`, множество защищённых `protected = {id | 'checklist:'+id in ownerFields}`, флаг `orderLocked = 'checklist:order' in ownerFields`. Правила:

1. Шаг с `id` из `protected`: остаётся в версии владельца (текст, `done`); если владелец его удалил (id в `protected`, но в `current` нет), шаг из источника не добавляется. В `skipped` попадает `{field: 'checklist:<id>', reason: 'owner'}`, только если версия источника отличается.
2. Шаг не из `protected`, есть в `incoming`: upsert текста и `done`. Шаг не из `protected`, отсутствует в `incoming`: удаляется.
3. Порядок: если `orderLocked`, порядок `current` сохраняется, новые шаги добавляются в конец; иначе порядок `incoming`, а защищённые шаги, отсутствующие в `incoming`, остаются на своих местах относительно соседей (по индексу в `current`).
4. Итоговый список проходит `checklistSchema` (лимит 100, уникальные id) до записи; превышение даёт `invalid`.
5. Владелец пополняет `ownerFields` так: `checklist.add` → `checklist:<newId>`; `checklist.update` → `checklist:<itemId>`; `checklist.remove` → `checklist:<itemId>`; `checklist.reorder` → `checklist:order`; `task.save` с `checklist` → разница по id между `before` и `after` (добавленные, удалённые, изменённые) плюс `checklist:order`, если изменился порядок общих id. Ключ `checklist` целиком в `ownerFields` больше не пишется.
6. Совместимость: существующие записи с `checklist` в `ownerFields` трактуются как «все шаги защищены и порядок заблокирован» (эквивалент сегодняшнего поведения); миграция данных не нужна.

### 3.6 Пустая команда владельца и сигнатура `emit`

`emit` сначала вычисляет `changes`; при пустых изменениях возвращает их до касания. Только непустые предметные изменения делают задачу «тронутой». Это отклонение от буквы плана §4 («owner_touched_at ставится первой командой владельца по задаче») в пользу смысла: команда без эффекта не является решением.

### 3.7 Сигнатура ответа `task.sync`

`commandResultSchema` (`src/shared/domain-schemas.ts:157-184`) получает необязательное `unchanged: string[]`. `applied` = записанные поля; `skipped` = поля, которые источник хотел изменить, но владелец имеет приоритет; `unchanged` = поля с совпадающим значением, в том числе защищённые. Ничего не отбрасывается молча, а шум для агента исчезает.

## 6. Риски и откат

- **Агент по поручению владельца хочет отменить действие владельца.** Политика A это запрещает; путь: прямая команда с `baseRevision` (`task.restore`, `task.move`). Скилл и `rules` называют этот путь явно. Если владелец сочтёт ограничение лишним, переключение на B это один предикат на шаге 3.
- **Существующие клиенты с `focus` в payload.** Только CLI `task focus` (удаляется в плане 03); браузер работает от владельца.
- **`unchanged` в ответе.** Дополнительное необязательное поле; `commandResultSchema.strict()` уже допускает его после расширения схемы; старые сохранённые `operations.result` без него валидны.
- **Изменение `emit` (шаг 7).** Затрагивает все команды; страховка: property-тест `projection == state` и `numRuns` временно поднять до 300 при локальном прогоне.
- **Поэлементный чеклист (B).** Расхождение между слиянием и ожиданиями источника возможно; смягчение: `unchanged`/`skipped` перечисляют каждый шаг, e2e не затрагивается (владелец работает через `task.save`).
- Откат: изменения локализованы в `src/shared/commands.ts`, `schemas.ts`, `domain-schemas.ts`, `app.ts:897-905` и тестах; `git revert` одного коммита возвращает прежнее поведение, данные в базе совместимы в обе стороны.

### Расхождения и решение
- Дефект или политика. Astra: «открытая продуктовая политика, не подтверждённое нарушение принятого контракта» (`ASTRA-INDEX.md`, строка плана 27); реестр TI-027: P2, РЕШЕНИЕ. Здесь: P0, средняя тяжесть, главный дефект по продукту (сверка по багам, строки 1-2 матрицы претензий). Решение: и то, и другое. Поведение противоречит текущему тексту правил (`app.ts:902`) и модели «владелец проверяет агентов» из плана v2, поэтому это дефект контракта; выбор между вариантами A/B/C (3.2) остаётся решением владельца и записывается отдельно, как требует `astra-27`.
- «Запрет только undo оставляет обход через move/save» (`ASTRA-VS-FABLE.md` §4.8, `astra-27` «Что изменится»). Раздел 7 сознательно оставляет прямые команды над `ownerFields` разрешёнными при верной `baseRevision`: сервер не различает автономную правку и исполнение поручения. Решение: согласиться, что это одна матрица, и внести строку явно (шаг 16), но не задерживать P0-часть (шаги 1-10) до решения по прямым командам: у undo решений владельца и у агентского `focus` нет легитимного сценария, у прямого `task.move` по поручению есть.
- Astra `astra-27`, шаг 4: «строка `actor.label` или произвольный флаг в payload не доказывают поручение владельца». Вариант (ii) раздела 7 предлагает флаг `confirmOwnerFields`. Решение: флаг допустим только как след в «Активности» и явное признание агентом, что он трогает решение владельца; доказательством поручения он не является, что и записывается в тексте варианта (шаг 16).
- Пропуски сторон. Astra объявила Undo и owner fields проверенными и пропустила оба сценария; сверка по багам (раздел «Уступки») относит B-01/B-02 к главным пропускам Astra. К этому плану из находок Astra относится только B-04 как ограничение контракта (шаг 17).

- Ж7, Ж8, Ж9 (`ASTRA-VS-FABLE.md` §5). Astra переоценивает три наших пункта о семантике `ownerFields` и `task.sync`, и переоценка принимается. Ж7: защита чеклиста целиком это принятая гранулярность плана v2, а не сломанный алгоритм; поэлементная защита это изменение продукта, остаётся решением владельца (раздел 3, вариант с поэлементной защитой помечается «решение владельца», не «дефект»). Ж8: первое пустое «Сохранить» владельца пишет событие только с `ownerTouchedAt`; по плану это реальное действие «владелец коснулся», поэтому событие не удаляется без решения о смысле касания, а исправляется подпись в «Истории» (текст события «Владелец просмотрел карточку»; реализация подписи в плане 07, `activity.tsx`). Ж9: обязательный `fields.area` в `task.sync` и ответ `skipped: area locked` после переноса задачи владельцем это шум в контракте, а не потеря корректности; упрощение контракта (сделать `area` необязательным при наличии `origin`) идёт в план 04 как изменение схемы, не как исправление бага.

## Решение владельца (2026-09-10, делегировано Fable)

- Запреты без ожидания матрицы: агент любого scope не отменяет операции, содержащие события владельца, и не ставит `focus`/`focusPosition`; в `task.sync` оба поля всегда `skipped: owner`. Шаги 1–10 и 4 плана 13.
