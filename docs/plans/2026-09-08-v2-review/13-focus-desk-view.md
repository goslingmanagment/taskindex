Зависимости: `02-agent-permissions-and-sync-semantics.md` (агент не ставит `focus`, порядок фокуса тоже владельческий), `04-api-contract-and-schemas.md` (чек-лист «как добавить команду», генерация union, `LIMITS`), `08-styling-skin-and-dark-theme.md` (слой скина, куда ложится CSS вида; палитра «Фокус» как скин каталога), `01-performance-history-and-pagination.md` (стоимость `/api/focus`), `12-ai-readiness-and-docs.md` (SKILL и CLAUDE.md), `astra-29-focus-counter-semantics.md` (счётчик Focus), `astra-25-dark-theme.md` (контракт предпочтений аккаунта, если стартовый экран станет настраиваемым).

## 1. Проблема

Экран Focus сегодня это четыре группы карточек в сетке: «Выбрано мной», «Новое от агентов», «Срок», «Ожидания с наступившей датой» (`src/shared/queries.ts:64-92`, `src/web/app/overview.tsx`). Он отвечает на вопрос «что попало в фокус», но не на вопрос «что я делаю сейчас и что дальше». Макет «Фокус» отвечает именно на него: одна текущая задача занимает главное место, внутри видны следующий шаг и прогресс, ниже два кандидата «потом», справа ожидания от других людей и «легко вернуться», всё остальное за ящиком «Все контексты».

Что макет требует от модели и чего в ней нет, проверено по `src/shared/domain-schemas.ts` и `src/shared/schemas.ts` 2026-09-10:

| Элемент макета | Есть в модели | Нет в модели |
|---|---|---|
| Текущая задача | `focus: boolean` (`domain-schemas.ts:51`), выбор владельца | Порядок среди задач в фокусе: `focus` не упорядочен, «текущая» неопределима детерминированно |
| Следующий шаг и прогресс | `checklist` (`domain-schemas.ts:53`): первый неотмеченный пункт и доля отмеченных | Ничего |
| «Небольшой объём работы» (в макете `minutes`) | Ничего | Оценка времени. В модель не вводится, см. раздел 3.4 |
| «Потом, один из двух» | Те же задачи в фокусе | Порядок, см. выше |
| «Жду от других»: человек и дата возврата | `status: 'waiting'`, `waitingFor` (`:45`), `followUp` (`:46`) | Ничего |
| «Легко вернуться»: недавно снятые с фокуса | Ничего | Момент выхода из фокуса. Из журнала событий вычислимо, но это полный скан (план 01) |
| «Все контексты» с фильтрами по проекту и состоянию | Список задач, фильтры `area`, `project`, `status` (`queries.ts:100-130`, `/api/tasks`) | Ничего |
| «Отложенные контексты» (в макете `parked`) | Фильтр `status=todo&focus=false` даёт то же множество | Отдельного флага не нужно |
| «Требует решения» (в макете `decision`) | Комментарии агентов как канал отчётов, группа «Новое от агентов» | Флага нет. В модель не вводится, см. раздел 3.4 |

Паритет: любая новая операция вида обязана быть доступна агенту через API и CLI (решение владельца из плана v2, BACKLOG «Полный доступ агентов»). Сегодня CLI умеет `task focus ID` только как `task.update {focus: true}` (`src/cli/run.ts:431-433`), `focus` читает `/api/focus` с группами (`run.ts:281-283`).

Отношение к скинам: макет показывает вид «Стол» и палитру «тёплая бумага, зелёные чернила, терракота» одновременно. Это два независимых слоя. Палитра это скин каталога по плану 08 (десять переменных макета `--paper`, `--ink`, `--warm`, `--green`, `--serif` ложатся на токены), вид работает в любом скине. Данный план про вид.

## 2. Цель и критерии приёмки

Цель: экран Focus получает раскладку «Стол» из макета, с детерминированной текущей задачей, очередью «потом», ожиданиями и недавним возвратом, при полном паритете владельца и агента.

Критерии приёмки:

1. Порядок фокуса хранится на сервере и виден агентам: у задачи в фокусе есть `focusKey`, текущая задача это минимальный `focusKey`. Инвариант `focus === (focusKey !== null)` и уникальность `focusKey` проверяются `assertInvariants` и property-тестом.
2. `/api/focus` без параметров отдаёт форму «стола»: `current`, `next` (до двух), `waiting` (все `status: 'waiting'` в фокусе и с наступившей `followUp`, отсортированы по `followUp`), `recent` (до трёх задач с `focusLeftAt` за последние 14 дней), `counts` и прежние `groups` для совместимости. Форма описана Zod-схемой в `src/shared/domain-schemas.ts`, а не в `app.ts`.
3. CLI: `taskindex focus` печатает ту же форму; `taskindex task focus ID [--first | --after ID | --before ID]` ставит задачу в фокус на позицию; `taskindex task focus ID --off` снимает. Справка и SKILL описывают все три.
4. Интерфейс: текущая задача показывает название, проект, первый неотмеченный шаг, прогресс `отмечено/всего`, первые строки заметки и срок; шаги отмечаются прямо на столе одной командой `checklist.toggle`; «Взять в фокус» у задачи из «Потом» и из ящика меняет `focusKey` одной командой; прежняя текущая получает `focusLeftAt` и появляется в «Легко вернуться».
5. Ящик «Все контексты» это существующий список с фильтрами `project`, `status`, `area`, открытый поверх стола; «Отложенные контексты» открывает его с фильтром `status=todo&focus=false`. Новых компонентов списка не появляется.
6. Мобильная раскладка: одна колонка, стол, потом, ожидания, возврат; e2e-скриншоты desktop и mobile добавлены в эталон явным режимом публикации (план 10), не обычным прогоном.
7. Клавиатура: Space отмечает шаг, N берёт первую задачу из «Потом», Esc закрывает ящик; фокус клавиатуры не теряется при смене текущей задачи.
8. Удаление, архивирование, завершение текущей задачи (`task.move done`, `task.archive`) снимают её с фокуса и назначают следующую текущей без дополнительной команды; undo этих операций восстанавливает `focusKey` и `focusLeftAt` (property-тест undo расширен).
9. Стоимость `/api/focus` не зависит от размера журнала (никаких чтений `events` для «Легко вернуться»).
10. Доска остаётся стартовым экраном (решение BACKLOG). Настраиваемый стартовый экран, если понадобится, идёт как предпочтение аккаунта по контракту `astra-25`, не через localStorage.

## 3. Решение

### 3.1. Модель: два поля, ноль новых сущностей

- `tasks.focus_key TEXT NULL COLLATE BINARY`, уникальный частичный индекс `WHERE focus_key IS NOT NULL`. Ключ порядка через `fractional-indexing`, как `orderKey` (`src/shared/commands.ts:154-176`). `focus: boolean` сохраняется как производное поле для совместимости API и CLI, сервер держит инвариант.
- `tasks.focus_left_at TEXT NULL`: момент последнего выхода из фокуса; ставится при `focus: true → false` любым путём (команда, завершение, архивирование), очищается при возврате в фокус. Это даёт «Легко вернуться» без сканирования журнала.

Отвергнуто: (а) клиентский порядок в localStorage: агенты его не видят, паритет нарушен; (б) переиспользование `orderKey`: он уникален в паре область и статус (план v2 §4), а фокус пересекает области; (в) вычисление «недавно снятых» из `events`: полный скан на каждый показ, план 01 как раз убирает такие пути.

### 3.2. Команды: расширение вместо новых имён

- `task.update` и `task.save` получают поле `focusPosition: { first: true } | { after: id } | { before: id }` рядом с `focus`. `focus: true` без позиции ставит в конец очереди (как сегодня по смыслу). Только владелец: агентам `focus` и `focusPosition` запрещены (план 02, B-02).
- `task.move status=done`, `task.archive` снимают фокус внутри `applyCommand`, событие несёт `focusKey: null`, `focusLeftAt`. Undo восстанавливает оба поля через обычную инверсию `changes`.
- `checklist.toggle` уже есть, стол использует его.

Новых команд не появляется, поэтому чек-лист «как добавить команду» из плана 04 применяется только к полям: схема payload, `applyCommand`, `isSubjectField` (оба поля предметные), `activity.tsx` подписи, справка CLI, SKILL, тесты.

### 3.3. Чистый селектор `focusDesk`

`src/shared/queries.ts`: `focusDesk(tasks, today): { current, next, waiting, recent, counts }`, без обращений к серверу и DOM, покрыт unit-тестом. `focusGroups` остаётся для `digest` и совместимости. Правила:

- `current`: задача в фокусе с минимальным `focusKey`, не архивная, статус не `done`.
- `next`: следующие две по `focusKey`.
- `waiting`: задачи со `status: 'waiting'`, сначала те, у кого `followUp <= today`, затем по `followUp`; независимо от фокуса, как в макете.
- `recent`: задачи с `focusLeftAt` за 14 дней, не в фокусе, не архивные, до трёх, новые сверху.
- `counts`: `focus` (всего в фокусе), `parked` (`status=todo && !focus`), `waiting`.

Счётчик Focus в сайдбаре берёт `counts.focus`, что закрывает `astra-29` (сегодня `focusCount` считает только «Новое от агентов», `src/web/app/shell.tsx:304-311`).

### 3.4. Что из макета намеренно не переносится

- Оценка «минут». Поля нет, вводить его ради одной подписи не стоит; на столе показывается «осталось N шагов». Если владелец захочет оценки, это отдельное поле `estimateMinutes` со своим решением.
- Флаг «требует решения». Канал отчётов агентов это комментарии; «Новое от агентов» уже выделяет непросмотренное владельцем. Отдельный флаг это продуктовое решение вне этого плана.
- Демонстрационные данные и логика макета (`takeFocus`, `parked` как флаг) не переносятся, переносится раскладка и взаимодействия.

### 3.5. Интерфейс

Компоненты в `src/web/app/desk/`: `Desk` (контейнер и клавиатура), `DeskCurrent`, `DeskNext`, `DeskRail` (ожидания и возврат), `ContextsDrawer` (обёртка над существующим списком с фильтрами через URL). Стол заменяет `WorkspaceOverview` на экране Focus; сетка групп остаётся только в `digest`. CSS вида это файл `src/web/skin/desk.css` в `@layer skin` по плану 08, только токены, без hex. В скине Classic стол выглядит как остальной интерфейс; в скине Focus (каталог плана 08) получает бумагу, чернила и книжную типографику из макета. Никаких `!important` и селекторов элементов внутрь примитивов.

## 6. Риски и откат

- Расползание объёма: соблазн перенести из макета оценки времени и флаг решения. Ограничено разделом 3.4; любое новое поле это отдельное решение владельца.
- Смена стартового экрана: макет предполагает стол стартовым. Здесь стартовый экран не меняется; иначе нарушается решение BACKLOG без обсуждения. Настройка идёт как предпочтение аккаунта.
- Зависимость от плана 02: если политика `focus` для агентов не принята, стол покажет задачи, выбранные агентами, как «текущие» владельца. Шаг 4 обязателен.
- Миграция с двумя полями в первой рабочей базе: выполнять по правилам планов 06 и 09, с фикстурой экспорта.
- Откат: поля nullable, старый интерфейс читает `focus` как прежде; вернуть `WorkspaceOverview` на экран Focus одной правкой `shell.tsx`.

## 7. Вне объёма

- Палитра и типографика макета как скин: план 08, каталог; шаг 11 здесь только ссылка.
- Стартовый экран по выбору владельца: предпочтение аккаунта по `astra-25`, с API и CLI.
- Остальные три варианта интерфейса (`atlas`, `dispatch`, `evolution` в той же папке `docs/reference/visions-2026-09-08/`): сохранены как справка, решений по ним нет.
- Оценка времени задачи и флаг «требует решения»: отдельные продуктовые решения.
- Уведомления о наступившей `followUp`: не в этом плане.
