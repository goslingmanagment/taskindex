## Причина и наблюдаемое поведение

В CSS уже есть две :root-палитры и две .dark-палитры; последние определения перекрывают первые. Переключатель/контроллер режима отсутствует, часть состояний имеет фиксированные светлые цвета, theme-color в HTML постоянный. Это заготовка, а не проверенная тёмная тема. Подсчёт hex сам по себе не показывает итоговый computed style: нужно учитывать каскад.

## Что изменится и зачем

Предложение: три понятных режима «Как в системе», «Светлая», «Тёмная»; выбранный режим сохраняется и доступен через UI/API/CLI. Классический внешний вид и поведение доски остаются эталоном. Общая основа сразу допускает skinId=classic; дополнительные скины добавляет план 26.

## Предлагаемый контракт предпочтения

Два независимых понятия: пользовательский `mode: system | light | dark` и вычисленный на устройстве `resolvedMode: light | dark`. `system` не является третьей палитрой. Подготовить `skinId`, первоначально только `classic`, чтобы план скинов не создавал вторую систему настроек.

Каноническое предпочтение предлагается хранить для аккаунта владельца и синхронизировать между устройствами. Режим `system` при этом разрешается отдельно на каждом устройстве. Индивидуальные исключения «на этом устройстве» и отдельный экран плотности в первый этап не входят.

Предлагаемый контракт записи — `appearance.update` с `mode`, `skinId`, `baseRevision`, обычными `operationId`/`generation`. Чтение — типизированный endpoint и поле snapshot. CLI получает `appearance get` и `appearance set --mode … --skin …`; это описание будущего интерфейса, сейчас таких команд нет. Чтение разрешается существующему `read`; запись по базовой модели — owner/`write`, `tasks` не может менять оформление. Окончательную матрицу прав сверить с планом 27 перед реализацией.

Рекомендуемая модель — одна запись `appearance_preferences` владельца с mode, skinId, revision и timestamps. Не прятать её в Task и не инкрементировать revision задач. Если используется общий command/event pipeline, расширить EntityKind, WorkspaceState, snapshot, event/result schema, import/export и replay; запретить молчаливое игнорирование новой сущности старым клиентом. История показывает «Оформление: Тёмная, Классический» в собственной категории. Семантику Undo определить до выпуска: предпочтительно обычная отмена этой записи с проверкой её revision, не затрагивающая задачи.

## Инициализация без вспышки и гонок

1. Минимальный bootstrap в head читает только версионированный appearance cache, проверяет разрешённые значения и вычисляет тему через `matchMedia`.
2. До CSS/React выставляет нужные атрибуты на html, `color-scheme` и `theme-color`. Он не ждёт `initializeDrafts()` и сетевого запроса.
3. После входа controller получает подтверждённую preference, сверяет revision и обновляет cache. Cache не отправляется на сервер автоматически как новое намерение.
4. Пользовательское изменение проходит через обычный persisted operation; если durable outbox недоступен, можно показать локальный preview с честным статусом, но нельзя обещать сохранение.
5. Late API response, storage event другой вкладки и событие SSE не должны перебивать более новую подтверждённую preference или незавершённый пользовательский preview. После смены generation применяется общий recovery.
6. При выходе очистить auth-sensitive данные. Допустимо оставить только безопасную локальную подсказку цветов страницы входа; она не даёт доступа к аккаунту.

## Структура CSS и ответственность

Предлагаемые части: базовые семантические токены, Classic Light/Dark values, component/state rules. Точные имена файлов выбрать при реализации; отдельный файл на каждую кнопку не нужен. Порядок CSS layers объявить явно и согласовать с Tailwind utilities, чтобы будущий скин не требовал наращивания `!important`. Примитивы оформлять через стабильные class/data-slot/state hooks, а не глубокие селекторы случайного DOM.

Статусы `todo/doing/waiting/done`, области и сохранённые `project.color` — предметные данные. Для статусов допускается web mapping id → semantic visual token; исходные enum и подписи не меняются. Произвольный пользовательский цвет проекта остаётся сохранённым цветом: в тёмной теме можно менять обводку/подложку цветной точки и обеспечить текстовую подпись, но нельзя переписывать project.color ради контраста.

## Доступность и визуальная приёмка

Обычный текст — ориентир контраста не ниже 4.5:1, крупный текст при условиях WCAG — 3:1. Существенные индикаторы состояния и элементы управления — 3:1 к соседним цветам; это не требование контраста каждой декоративной границы. Проверять placeholder, ошибки, muted текст, выбранный пункт и focus ring на реальных поверхностях. Отключённое управление имеет исключения в критериях, но должно оставаться понятным.

Проверять при ширине 320 px и шире, увеличении текста/масштаба, keyboard navigation, открытых порталах и drag overlay. Часть состояний видна только при сетевом отказе или конфликте — обычного скриншота доски недостаточно. До измерений не заявлять полное соответствие WCAG.
