## Причина и наблюдаемое поведение

Сейчас несколько исторических наборов CSS перекрывают друг друга, но явного реестра скинов, независимого skinId и полного контракта токенов нет. Простое добавление третьего блока overrides увеличит долг и оставит часть экранов в старой палитре.

## Что изменится и зачем

Скин меняет оформление через проверяемый набор визуальных токенов и поддерживает светлый/тёмный режимы. Он сохраняет навигацию, статусы доски, порядок задач и все гарантии редактирования.

## Шаги реализации

1. Определить строгий SkinDefinition: стабильный id, русское имя/описание, версия схемы токенов, обязательные light/dark palettes и ограниченные визуальные параметры. Не смешивать skinId с режимом system/light/dark.
2. Оформить Classic как первый полноценный skin с эталонами из плана 25. Registry должен проверять полноту токенов и уникальность ID на build/typecheck границе.
3. Подготовить второй встроенный вариант как проверку архитектуры — предложение «Графит»: нейтральные поверхности и сдержанный accent при той же геометрии. Финальные оттенки выбрать после просмотра реальных сцен; третий вариант не обязателен.
4. Добавить каталог скинов в диалог «Оформление»: название, короткая характеристика, мини-preview, выбранное состояние. Режим темы расположен отдельно и действует для любого выбранного скина.
5. Реализовать локальный preview и явное применение. Cancel/Esc возвращают предыдущую подтверждённую настройку без записи; Apply отправляет одну appearance.update через готовую инфраструктуру.
6. Обновить schema/API/CLI перечнем допустимых встроенных ID; агент может прочитать каталог и изменить выбор по тому же контракту, без доступа к произвольному CSS.
7. Проверить все token consumers, порталы, native controls, drag overlays и произвольные цвета проектов. Новый скин не должен добавлять исключение в каждый компонент.
8. Запустить визуальную матрицу Classic/второй skin × Light/Dark и smoke system mode. Сравнить поведение, клавиатуру, сохранение формы и контраст; затем отдельно принять внешний вид.

## Что именно может менять скин

| Разрешено в первой версии | Остаётся общим поведением |
|---|---|
| Палитры поверхностей, текста, акцента и семантических состояний | Доска как стартовый экран, sidebar, Focus, поиск |
| Обводки, тени и ограниченные радиусы через токены | Состав и порядок статусных колонок |
| Проверенные значения толщины/контраста визуальных индикаторов | Сортировка, drag-and-drop semantics, API-команды |
| Небольшие параметры шрифта в пределах общего системного стека, если они не ломают метрики | Тексты, поля, действия, права, черновики и история |

Плотность, другая навигация и новый dashboard — отдельные продуктовые изменения. Они не включаются автоматически в слово «скин». Не вводить настройку каждого радиуса и каждой краски: первый этап — небольшой каталог завершённых вариантов.

## Реестр и каскад

Предлагаемая структура: общие метаданные каталога в shared, web-реестр `appearance/registry.ts`, `appearance/tokens.css` с ролями и небольшие palette-файлы. Сервер и CLI читают ID/названия/возможности из общих метаданных, без импорта CSS или React. Конкретные имена выбрать при реализации с учётом структуры после плана 25. Режим и скин задаются на html единственным controller: `.dark` сохраняется для текущих Tailwind variants, `data-skin` выбирает palette. Не держать конфликтующие значения одновременно на body, shell и порталах.

Разделить проверку чтения и записи: в ответе `skinId` проверяется как строковый идентификатор допустимого формата, а неизвестный этому клиенту ID обрабатывается renderer fallback. При записи сервер принимает только ID своего текущего каталога. Если ответ валидировать старым enum из одного `classic`, добавление скина сломает весь snapshot вместо предусмотренного fallback. Некорректный формат строки по-прежнему является ошибкой протокола, а не новым скином.

Реестр не загружает URL, JS или стороннюю таблицу CSS из пользовательских данных. Значения server preference выбирают только известный встроенный ID. Обязательные tokens проверяются типами/сборкой; запретить fallback к случайному светлому hex внутри компонента. Fallback к Classic используется для целиком неизвестного skin, а не скрывает неполноту нового skin при разработке.

Правила компонентов остаются общими. `Button`, input, dropdown и modal получают стабильные hooks/variants, а не индивидуальный skin-specific JSX. Если второму скину требуется много структурных исключений, остановить его добавление и пересмотреть границу; это признак нового дизайна поведения, а не недостаточного количества overrides.

## Работа пользователя

1. В «Оформлении» видны текущий режим и текущий скин. Превью карточки показывает один и тот же небольшой фрагмент интерфейса, чтобы различия были сравнимы.
2. Выбор другого скина немедленно даёт локальный preview на текущем экране. Открытая задача и несохранённый текст остаются на месте.
3. «Применить» создаёт одно намерение сохранения. Повторный клик не создаёт новый operationId; неизвестный ответ отображается как ожидающий проверки.
4. «Отмена»/Esc до применения возвращают исходный вид и ничего не записывают. Если запись уже отправлена, UI не обещает отменить её локальным закрытием окна: действует обычный lifecycle результата.
5. При внешнем изменении preference во время preview показывается актуальное подтверждённое состояние и возможность применить своё намерение с проверкой revision. Молчаливого last-write-wins поверх чужой записи нет.

## Режимы отказа и совместимость

- Недоступен localStorage: чтение и временное сравнение скинов допустимы; сохранение следует запрету send без durable envelope из плана 06.
- Старый клиент не знает skinId: использовать безопасный Classic и не переписывать серверное значение на default автоматически. Объяснить, что для отображения выбранного скина требуется обновление.
- Skin удаляется из следующего выпуска: предпочтительно сначала пометить deprecated и предложить replacement. Если нужен обязательный переход, оформить явную миграцию preference; не менять историю заданий.
- Error при загрузке локального chunk/palette: вернуть рабочий Classic, сохранить выбранный ID и возможность повторить. Для двух маленьких palettes предпочтительна включённая в build статика без отдельной сети.
- Restore generation: preference приходит из восстановленной базы; cache старой generation не должен самопроизвольно восстановить более позднюю настройку как новую запись.
