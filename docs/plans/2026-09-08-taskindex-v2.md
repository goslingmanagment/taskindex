# TaskIndex v2. Итоговый план переписки

Дата решения: 2026-09-08. Владелец: Дмитрий. Решения владельца зафиксированы.
Статус: реализовано и проверено локально; рабочее переключение и приёмка
владельцем остаются отдельно. Результаты — в [отчёте](2026-09-08-taskindex-v2-review.md).

Документ самодостаточен: исполнитель без контекста обсуждения должен по нему
собрать приложение целиком. Что не описано здесь, берётся из исходного кода
(раздел 8.5) или уточняется у владельца (раздел 16).

## 1. Решения владельца

- **Полная переписка в этом же репозитории.** Новое дерево построено в отдельном
  worktree, затем по поручению владельца перенесено в основную папку на `main`.
  Временная ветка и worktree удалены. Старый код (vinext, D1, Sites, шаблонные
  компоненты) доступен в истории git; `.wrangler/state` и незакоммиченные макеты
  сохранены вне проекта в проверенном архиве из `README.md`.
- **Не редизайн.** Интерфейс воспроизводится один в один по визуальному
  эталону: сайдбар «Все задачи» и проекты области с цветными точками, доска и
  список, Focus, глобальный поиск, архив, редактор карточки. Эксперименты из
  `public/visions/` и `docs/proposals/` в объём не входят.
- **Импорт данных не нужен.** База стартует пустой, задачи и проекты позже
  заполняют агенты через CLI и API. Сида и флага `demo` в приложении нет.
- **Размещение: VPS, Docker Compose, Nginx.** Cloudflare Workers, D1 и Sites
  не используются.
- **Полный доступ агентов.** Паритет операций человека и агента обязателен
  для каждой функции, включая будущие. Требование закреплено в `BACKLOG.md`,
  раздел «Уже принятые продуктовые решения».
- **Роли.** Почти всё управление задачами делают агенты: создают из внешних
  источников, обновляют, перемещают, закрывают. Владелец ставит поручения,
  проверяет работу агентов и отменяет ошибки. Отсюда дедупликация по внешней
  ссылке, `task.sync` с приоритетом ручных решений, описания проектов,
  пакетное создание, комментарии как канал отчётов агентов, отмена целой
  операции, компактная лента активности и сводка `digest`. Добавления к
  интерфейсу сверх эталона ограничены четырьмя: группа «Новое от агентов» и
  метка автора на карточке, пункт «Активность» в сайдбаре с раскрываемыми
  операциями, комментарии и история внутри редактора карточки. Лента не
  становится главным экраном без проверки удобства владельцем.
- **Идентичность агента отделена от ключа.** Агент это запись с устойчивым
  id и меткой, ключи доступа принадлежат агенту и ротируются без потери
  атрибуции. Механизм занятия задачи агентом на исполнение не входит в
  первую версию: он нужен, только если агенты будут исполнять задачи, а не
  вести их, решение владельца отложено, раздел 16.

## 4. Модель данных

Все таблицы в одной базе SQLite. Идентификаторы: строки `[A-Za-z0-9_-]{1,80}`,
по умолчанию UUID v4, клиент вправе передать свой. Моменты времени ISO-8601 в
UTC. Календарные даты `due` и `followUp` остаются строками `YYYY-MM-DD` без
пояса, пустое значение `null`.

Инварианты, проверяются сервером внутри транзакции:

- `tasks.area` равен `projects.area` при непустом `project_id`. Область
  проекта неизменяема, команды на её смену нет.
- Имя проекта уникально в области без учёта регистра по правилам русского.
- Ключ порядка уникален в паре область и статус, архивные задачи ключ
  сохраняют.
- Пункты чеклиста принадлежат задаче, изменение пункта поднимает `revision`
  задачи и пишет событие на задачу.
- `origin_system` и `origin_ref` либо оба заданы, либо оба пусты.
  `origin_url` без них не принимается. Значения `origin_system` это короткие
  слаги источников, например `telegram`, `hub`, `hiring`, `manual`.
- Лимиты полей из раздела 8.5.

`generation` это случайная строка, создаётся при инициализации базы и меняется
при восстановлении или импорте. `revision` записи растёт на единицу на каждое
событие этой записи. Проекция текущего состояния хранится в таблицах,
`events` это журнал, а не источник для перестроения.

## 5. Команды

Все изменения проходят через `POST /api/commands`. Интерфейс и CLI используют
один и тот же набор.

```json
{ "operationId": "uuid", "generation": "g_…", "command": "task.move", "payload": { ... }, "dryRun": false }
```

| Команда                        | Payload                                                                                                                                                                                                                                                     | Поля записи, которые трогает                                                                                                                                                                                                                                                     |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `project.create`               | `id?`, `area`, `name`, `color`, `description?`                                                                                                                                                                                                              | новая запись                                                                                                                                                                                                                                                                     |
| `project.update`               | `id`, `baseRevision`, `name?`, `color?`, `description?`                                                                                                                                                                                                     | `name`, `color`, `description`                                                                                                                                                                                                                                                   |
| `task.create`                  | `id?`, `area`, `projectId?`, `title`, `status?` (по умолчанию `todo`), `note?`, `due?`, `waitingFor?`, `followUp?`, `focus?`, `checklist?`, `origin?` (`{system, ref, url?, version?}`), `position?` (`{before}` или `{after}`, по умолчанию конец колонки) | новая запись                                                                                                                                                                                                                                                                     |
| `task.sync`                    | `origin` (`{system, ref, url?, version?}`), `fields` как у `task.create` без `id`, `origin` и `position`                                                                                                                                                    | повторная обработка источника агентом с сохранением решений владельца; обновление существующей задачи только при известной более новой версии источника, правила ниже                                                                                                            |
| `task.update`                  | `id`, `baseRevision`, любые из `area`, `title`, `note`, `due`, `waitingFor`, `followUp`, `projectId`, `focus`                                                                                                                                               | перечисленные; смена области и проекта проверяется атомарно                                                                                                                                                                                                                      |
| `task.save`                    | `id`, `baseRevision`, `fields?` как у `task.update`, `status?`, `position?`, `checklist?` полным списком пунктов                                                                                                                                            | объединение затронутого. Одна атомарная команда для кнопки «Сохранить» в редакторе: статус, поля и чеклист либо сохраняются вместе, либо вместе получают `conflict`. | `task.move`                    | `id`, `baseRevision`, `status`, `before?` или `after?`                                                                                                                                                                                                      | `status`, `orderKey`                                                                                                                                                                                                                                                             |
| `task.archive`, `task.restore` | `id`, `baseRevision`                                                                                                                                                                                                                                        | `archived`                                                                                                                                                                                                                                                                       |
| `checklist.add`                | `taskId`, `baseRevision`, `id?`, `text`, `position?`                                                                                                                                                                                                        | `checklist`                                                                                                                                                                                                                                                                      |
| `checklist.update`             | `taskId`, `baseRevision`, `itemId`, `text?`, `done?`                                                                                                                                                                                                        | `checklist`                                                                                                                                                                                                                                                                      |
| `checklist.remove`             | `taskId`, `baseRevision`, `itemId`                                                                                                                                                                                                                          | `checklist`                                                                                                                                                                                                                                                                      |
| `checklist.reorder`            | `taskId`, `baseRevision`, `itemIds[]`                                                                                                                                                                                                                       | `checklist`                                                                                                                                                                                                                                                                      |

| `undo`                         | `seq` либо `operationId`                                                                                                                                                                                                                                    | поля отменяемого события или всех событий операции                                                                                                                                                                                                                               |

Дедупликация при создании. Если у `task.create` задан `origin` и задача с
той же парой `system` и `ref` уже есть, включая архивную, команда возвращает
её с `existing: true`, ничего не меняет и событие не пишет. Агент сам решает,
обновить её или восстановить. Владелец в интерфейсе `origin` не заполняет.

Пакет. `POST /api/commands/batch` принимает тот же конверт
`{ operationId, generation, dryRun?, commands: [{ command, payload }, ...] }`
до 100 команд без собственных `operationId`. Поколение и идемпотентность
проверяются один раз на пакет. Весь пакет исполняется в одной транзакции,
ошибка любой команды откатывает все, ответ содержит `results` по позициям и
все созданные `events`, либо одну ошибку с индексом отказавшей команды.
`dryRun` откатывает весь пакет и возвращает `results` без событий. Повтор
пакета с тем же `operationId` возвращает сохранённый ответ.

Повторная обработка источника. `task.sync` это команда для агентов, которые
регулярно перечитывают Telegram, Hub или другой источник. `revision` от
затирания ручных правок здесь не защищает: агент читает свежую запись и
честно её перезаписывает. Поэтому сервер применяет `task.sync` по правилам:

- `origin.version` передаётся только когда источник даёт версию, которая
  монотонно упорядочивает его состояния: момент изменения ISO-8601 с поясом
  либо неотрицательное целое. Сравнение хронологическое или числовое без
  потери точности. Агент не подставляет время наблюдения (`observedAt`),
  ETag или хеш: они не доказывают, какое состояние источника новее;
- задачи с таким `origin` нет: создать как `task.create`, в том числе при
  неизвестной версии; переданную упорядоченную версию сохранить;
- существующая задача и входящая либо сохранённая версия отсутствует:
  ничего не менять, ответ `skipped: all, reason: freshness_unknown`, события
  нет. Для осознанной правки остаются `task.update` и `task.save` с
  `baseRevision`; новая дата наблюдения не разрешает автоматическую перезапись;
- форматы входящей и сохранённой версий не совпадают или значение не
  разбирается: ничего не менять, ответ
  `skipped: all, reason: version_incomparable`, события нет;
- `origin.version` не новее сохранённой `origin_version`: ничего не менять,
  ответ `skipped: all, reason: stale`, события нет;
- `owner_touched_at` пуст: применить все переданные поля;
- владелец уже касался задачи: поля из `owner_fields` пропустить, поля
  `status`, `archived`, `focus`, `projectId`, `area` не менять никогда,
  остальные применить. Закрытую владельцем задачу источник не откроет.

После обработки более новой сопоставимой версии `origin_version` продвигается
до неё в той же транзакции, даже если предметные поля защищены владельцем.
Изменение только этой метаинформации тоже пишет событие и поднимает `revision`,
но не считается ручной правкой и не создаёт отменяемого предметного эффекта.
После Undo версии, не новее этой отметки, по-прежнему получают `stale`:
повторная обработка того же источника не возвращает только что отменённые поля.

Ответ содержит `applied[]` и `skipped[{ field, reason: owner | locked }]` для
обработанных полей либо `skipped: all` и общую причину `stale`,
`freshness_unknown` или `version_incomparable`,
чтобы агент видел, что именно не принято. Приоритет решений владельца
реализован на сервере, а не в скилле, и не зависит от аккуратности агента.
`task.update` и `task.save` этих ограничений не имеют, ими агент правит
задачу осознанно, с `baseRevision`.

Первая команда владельца по задаче ставит `owner_touched_at`. Команды агентов
это поле не трогают.

Исполнение команды, одна синхронная транзакция better-sqlite3:

0. Сверить `generation` конверта с текущим. Расхождение даёт
   `generation_changed` до любых записей.
1. `INSERT OR IGNORE` в `operations`. Если запись уже была: при совпадении
   `command_hash` вернуть сохранённый `result` с тем же статусом, иначе ошибка
   `operation_mismatch`.
2. Прочитать текущую запись. `baseRevision` больше текущей `revision` это
   `invalid`. Если `baseRevision` меньше текущей, собрать поля, изменённые
   событиями этой записи после `baseRevision`. Если пересечения с полями
   команды нет, команда применяется к текущему состоянию. Иначе ошибка
   `conflict` с актуальной записью.
3. Вычислить результат через общий `applyCommand(state, command, {now, ids, actor})`
   из `src/shared`. Клиент считает этой же функцией оптимистичный превью.
   Сервер передаёт актора из авторизации, клиентское превью прав не даёт.
4. Проверить инварианты результата. При создании задачи и прямом изменении
   её области, статуса или позиции сервер вычисляет ключ по актуальным
   соседям; это относится к `task.move`, `task.save`, `task.sync` и пакету.
   Без `position` задача встаёт в конец целевой колонки. Undo восстанавливает
   прежний серверный ключ по отдельным правилам ниже. Ключ из клиента не
   принимается.
5. Записать состояние, событие с `changes` и `record_revision`, результат в
   `operations`. После исполнения всей операции определить её `firstSeq` и
   `lastSeq`, включить их в ответ и конверт каждого её события. Закоммитить.
6. Разослать событие в открытые SSE-соединения.

`dryRun: true` проходит шаги 0, 2, 3 и 4 и откатывает транзакцию. Возвращает
предполагаемую запись и `changes`, событие и запись операции не создаёт. При
реальном исполнении предусловия проверяются заново.

Формат `changes`: объект по изменённым полям записи, для каждого `{ from, to }`.
Чеклист представлен одним полем `checklist` с полными списками пунктов `from` и
`to`. Для создания записи в `from` стоит `null`. Предметные поля задачи:
`area`, `projectId`, `title`, `status`, `note`, `due`, `waitingFor`, `followUp`,
`orderKey`, `focus`, `archived`, `checklist`, `originUrl`; проекта: `name`,
`color`, `description`; у существующего комментария меняется только `deletedAt`.
Совместимое слияние на шаге 2 и обычная инверсия Undo используют только
предметные поля. Технические метаданные `originVersion`, `ownerTouchedAt`,
`ownerFields`, атрибуция и время создания отражаются в событиях для
синхронизации, но не инвертируются. `originVersion` не уменьшается,
`ownerFields` только пополняется, первое `ownerTouchedAt` сохраняется;
`revision` и `updatedAt` вычисляются заново для каждого события. Проверки
жизненного цикла созданной записи описаны отдельно ниже.
Если не изменились ни предметные поля, ни отслеживаемые технические метаданные,
это успешный результат без события и без повышения `revision`.

`undo {seq}` строит из `changes` события обратную команду `to → from` и
исполняет её как обычную команду с `baseRevision`, равной `record_revision`
события. Отменяемы `task.update`, `task.save`, `task.move`, `task.archive`,
`task.restore`, `task.sync`, `checklist.*`, `project.update`, `comment.add`,
`comment.remove` и сам `undo`, то есть отмена Undo возвращает его предметный
эффект. Отмена `task.create` и создавшего задачу `task.sync` архивирует задачу;
обновивший задачу `task.sync` отменяется обычной инверсией предметных полей.
Создание комментария отменяется мягким удалением. Обязательные поля созданных
записей никогда не заменяются на `null`. После создания любое более позднее
предметное изменение этой записи вне отменяемой операции даёт `conflict`.
Отмена `project.create` и операции без отменяемого предметного эффекта
невозможна, ответ `not_undoable` с HTTP 409. Событие только технических
метаданных пропускается при построении инверсии и не запрещает отмену других
событий операции. Второй `undo` того же изменившего запись события получает
`conflict`: первое Undo уже изменило затронутые поля. Отмена сама записывается
в журнал.

Отмена перемещения восстанавливает прежние область, статус и серверный
`orderKey` из истории, поэтому без последующих изменений порядок `A,B,C`
после переноса B и Undo снова равен `A,B,C`. Если прежний ключ занят задачей,
которая не освобождает его в этой же отмене, вся отмена получает `conflict`
с указанием задачи и поля `orderKey`; автоматического переноса в конец нет.
Для нескольких записей уникальность проверяется на итоговом состоянии всей
отмены, а промежуточные перестановки ключей внутри транзакции не должны
нарушать UNIQUE. Клиент по-прежнему передаёт только `seq` или `operationId`.

`undo {operationId}` отменяет одну операцию целиком, обычно пакет, не по
событиям в обратном порядке, а по чистому эффекту на каждую запись, иначе
внутренние последовательные правки одного поля внутри пакета конфликтовали
бы сами с собой. Порядок в одной транзакции:

1. Собрать события операции и для каждой записи вычислить чистое изменение:
   `from` из первого события операции по предметному полю, `to` из последнего.
   Поля, у которых `from` равно `to`, из отмены исключаются. Сначала выделить
   записи, созданные внутри операции: для задачи, включая `task.sync`,
   обратный эффект это архивирование её итоговой записи, для комментария —
   мягкое удаление. Последующие изменения этой же записи внутри пакета не
   превращаются в инверсию `from: null`. Если созданная запись уже архивирована
   или комментарий уже удалён внутри того же пакета, этот эффект пуст.
2. Если среди событий есть неотменяемые, например `project.create`, вся
   отмена получает `not_undoable` до любых изменений.
3. Проверить права актора на каждое обратное изменение так же, как для
   прямой команды: ключ `tasks` не откатит `project.update`, агент не
   удалит чужой комментарий через отмену `comment.add`. Один запрещённый
   эффект отклоняет всю отмену с `forbidden`.
4. Проверить, что после завершения операции никто не менял затронутые поля
   этих записей; собственные события операции при этом не считаются. Любое
   такое изменение отклоняет всю отмену с `conflict`, в ответе перечислены
   записи и поля, чтобы владелец решил, что делать руками. Для отмены создания
   проверяются все предметные поля этой записи, как при `undo {seq}`.
5. Применить обратные изменения ко всем записям с правилами порядка выше,
   сохранить технические метаданные и наибольшую обработанную версию источника,
   записать события отмены и результат операции. Предметный эффект новой
   операции Undo впоследствии можно отменить по тем же правилам.

Те же проверки прав выполняет и `undo {seq}`. Один запуск агента может
состоять из нескольких операций, отмена одной не отменяет остальные; лента
активности показывает операции запуска рядом.

Комментарии не участвуют в `revision` и совместимом слиянии задачи.
`comment.add` пишет событие с `entity_kind = comment` и `record_revision`
комментария, у задачи в снапшоте и в записи меняется только `commentCount`.
`comment.remove` меняет только ещё не удалённый комментарий и отменяем через
`undo`; если комментарий уже удалён, это успешный результат без события.
`comment.add` отменяется удалением с теми же правами, что у `comment.remove`.

Актор берётся только из авторизации и хранится как стабильный `actor_id`:
`owner` для сессии владельца, `agent:<agent_id>` для API-ключа. Отображаемая
метка `actor_label` фиксируется в событии на момент записи, потому что имя
ключа может меняться и повторяться. Клиент актора не передаёт.

Ответ успеха один и тот же для команды и пакета:
`200 { ok: true, operationId, generation, firstSeq, lastSeq, results: [{ record, changes, existing?, applied?, skipped?, reason? }], events: [...] }`.
У обычной команды один элемент в `results`, у пакета по элементу на позицию.
Событий может быть ноль, одно или несколько, в том числе у одиночного
`undo {operationId}`. `firstSeq` и `lastSeq` это включительные границы всех
событий операции, обе `null` при их отсутствии. Конверт каждого события в
ответе, SSE и `since` включает те же границы операции; события идут в один
обработчик на клиенте. Любой окончательный успех без событий снимает pending
самим ответом, независимо от имени команды: например, `existing: true`,
`skipped: all`, повторное удаление комментария или отсутствие изменений.
Цель для `undo` это `events[].seq`, при пустом `events` её нет. Ответ
ошибки:

```json
{ "ok": false, "code": "conflict", "message": "Задача изменилась. Ваш текст остался в форме.",
  "retryable": false, "current": { ...актуальная запись... } }
```

| Код                  | HTTP | retryable | Когда                                                           |
| -------------------- | ---- | --------- | --------------------------------------------------------------- |
| `invalid`            | 400  | нет       | схема или лимиты                                                |
| `unauthorized`       | 401  | нет       | нет сессии или ключа                                            |
| `forbidden`          | 403  | нет       | ключ отозван, чужой Origin                                      |
| `not_found`          | 404  | нет       | нет записи                                                      |
| `conflict`           | 409  | нет       | несовместимое изменение, в ответе `current`                     |
| `operation_mismatch` | 409  | нет       | тот же `operationId`, другая команда                            |
| `generation_changed` | 409  | нет       | клиент с прежним поколением базы                                |
| `not_undoable`       | 409  | нет       | событие нельзя отменить                                         |
| `unavailable`        | 503  | да        | база недоступна или занята, либо запись закрыта на время деплоя |

Сообщения на русском, как в текущем приложении.

её сохранённый отказ находится в `result`. `ok: false` у такой записи не
означает ошибку самого GET. Клиенты различают запись операции и ответ ошибки
API по общей схеме; для ошибки API обязательны `code` и `retryable`.

Клиент: при старте снапшот, затем SSE. Первое подключение передаёт курсор
снапшота через `?generation=&since=`, потому что стандартному EventSource
начальный `Last-Event-ID` задать нельзя; браузер сам шлёт его при
переподключении. Все события, откуда бы они ни пришли, SSE, `since` или
ответ на свою команду, проходят через один обработчик `ingest`. Курсор `seq`
означает последнее последовательно применённое событие. Дубликаты не больше
курсора отбрасываются, остальные события буферизуются; разрыв последовательности
запускает догон через `since`. После получения непрерывного диапазона
`firstSeq…lastSeq` следующей операции все её события применяются к confirmed
за одно обновление store, затем курсор сдвигается на `lastSeq` и снимается
весь её оптимистичный слой. Первое событие пакета само по себе pending не
снимает. Для постраничного догона курсор полученных подряд событий учитывается
отдельно от курсора применённых: неполная операция может занимать несколько
страниц. Снапшот читается на границе транзакции и не содержит половину операции.
Сам HTTP-ответ курсор не двигает: его события идут в `ingest` как любые другие,
независимо от того, пришли они раньше SSE или позже. Разрыв соединения
восстанавливает EventSource сам, бэклог приходит по `Last-Event-ID`.
`generation_changed` и `event: reset` сбрасывают подтверждённое состояние и
запрашивают снапшот заново; конверты прежнего поколения автоматически с новым
поколением не отправляются, черновики сохраняются по правилам раздела 7.

Событий в первой версии не сжимают и не удаляют.

## 7. Клиент

Store: `{ confirmed: { projects, tasks }, seq, generation, pending: Operation[], drafts }`.
Отображаемое состояние это `pending.reduce(applyCommand, confirmed)`.
Операция в `pending` имеет состояние `sending`, `unknown` или `acked`.
Полностью применённый диапазон событий с её `operationId` снимает её с любого
состояния. Успешный ответ без событий снимает её сразу; успешный ответ с
событиями переводит в `acked` до их применения, не создавая pending заново,
если SSE уже завершил эту операцию. Окончательная ошибка с `retryable: false`
убирает операцию, показывает toast с текстом ошибки, а в редакторе сохраняет
черновик и предлагает актуальную версию. Обрыв сети, тайм-аут и ответ с
`retryable: true`, включая `503 unavailable` при `writes: held`, не завершают
операцию: конверт сохраняется, клиент повторяет ту же команду с тем же
`operationId` с нарастающей паузой до трёх раз, затем показывает «Изменение не
подтверждено» с кнопкой повтора всё с тем же `operationId`. Новый
`operationId` для того же намерения не создаётся никогда. Судьбу зависшей
операции можно выяснить через `GET /api/operations/:id`.
При неизвестном исходе состояние `unknown`; временный отказ сервера также
оставляет возможность повтора. `unavailable` не сохраняется как окончательный
результат в `operations`, иначе повтор после открытия записи навсегда вернул
бы прежний 503. Это правило одинаково для браузера и CLI.

Восстановление после перезагрузки вкладки. Конверт операции записывается в
localStorage под ключом `taskindex/ops/<operationId>` до отправки и удаляется
после подтверждённого успеха либо окончательной ошибки с `retryable: false`,
никогда по сетевой ошибке или `retryable: true`. При старте клиент для каждого
сохранённого конверта спрашивает `GET /api/operations/:id`: если операция
завершена, конверт удаляется, а её события придут через снапшот и `since`;
если сервер её не знает, конверт отправляется заново без изменений. Это
восстановление уже отправленной операции, а не офлайн-очередь.

Модули `src/web/app`: `shell` (сайдбар, шапка, тосты), `sidebar`, `board`,
`list`, `focus`, `search`, `editor`, `dialogs` (быстрое создание, проект),
`activity`, `store`, `sync`, `drafts`, `url`. Модуль `activity` это пункт
«Активность» в сайдбаре под Focus: список операций по времени, каждая одной
строкой с автором, временем, сутью и числом задач, раскрывается в список
событий, у операции и у события кнопка «Отменить». Пакет из 50 изменений
выглядит как одна раскрываемая строка. В редакторе карточки два
сворачиваемых блока под чеклистом: «Комментарии» с полем добавления и
«История» из `history` с отменой по событию. Ничего из этого не заменяет
доску как стартовый экран. Компоненты shadcn в `src/web/ui`, только
используемые: button, input, textarea, checkbox, select, tabs, dialog,
alert-dialog, sheet, dropdown-menu, collapsible, progress, skeleton, empty,
toast, sidebar и их внутренние зависимости.

URL: `/?area=agency&project=all|none|<id>&view=board|list&task=<id>&q=<текст>&focus=1&archive=1&today=1&archiveSearch=1`.
Область, проект, представление и открытая задача через pushState. Текст
поиска и переключатели через replaceState. Пустой `/` открывает последнее
место из localStorage, иначе `agency`, `all`, `board`.

Черновики в localStorage под ключом `taskindex/drafts/<scope>/<taskId>` со значением
`{ formatVersion, generation, baseRevision, fields }`. Идентификатор набора
черновиков вкладки хранится в sessionStorage; Web Lock удерживает за ним одного
писателя. Дублированная вкладка получает независимую копию. Перезагрузка
продолжает свой набор, новая вкладка может восстановить последний неиспользуемый
набор после закрытия прежней. Старые ключи `taskindex/draft/...` читаются как
отдельный совместимый набор с тем же исключительным владением. Сохранение
удаляет только черновик своей вкладки. При недоступности Web Locks создаётся
отдельная копия, исходные записи сохраняются.
Черновик быстрого создания и инлайн-ввода внутри одной вкладки общий:
`taskindex/drafts/<scope>/new/<area>/<project>/<status>`. Обе формы получают
уведомления об изменении и использовании черновика. Пустой текст комментария
удаляет его черновик. Черновик создания хранит
`operationId` и `id` будущей задачи с момента первой отправки, поэтому после
перезагрузки повтор идёт с теми же идентификаторами, а не заводит дубль.
Черновик удаляется после подтверждённого сохранения. Черновик с чужим `generation` не применяется
автоматически: редактор показывает его как «черновик от прежней версии базы»
с текстом для ручного переноса. Полноценная офлайн-очередь не обещается: без
сети операция остаётся в `unknown` по правилам выше, текст остаётся в
черновике.

Черновик редактирования проекта также хранит базовую запись и полученную
конфликтующую версию. При конфликте форма показывает актуальные поля и требует
«Совместить и проверить»: изменённые владельцем поля сохраняются, остальные
берутся из актуальной записи. Только после проверки доступно новое сохранение
с её ревизией; закрытие и повторное открытие не обходят этот шаг.

Перетаскивание: dnd-kit с датчиками указателя, касания и клавиатуры. Сброс
даёт `before` или `after` и вызывает `task.move`, ключ порядка присваивает
сервер. Перетаскивание недоступно в архиве, в поиске и в Focus, как сейчас.

## 8. Поведение, которое переносится один в один

### 8.1 Навигация и представления

- Три области: `agency` «Агентство», `development` «Разработка», `personal`
  «Личное» с текущими цветами, иконками и описаниями.
- Сайдбар: «Все задачи», затем проекты области с цветными точками, «Без
  проекта», создание и переименование проекта. На телефоне сайдбар как sheet.
- Доска из четырёх колонок `todo` «Очередь», `doing` «В работе», `waiting`

  представление. Переключатель «Сегодня»: задачи с `due` не позже сегодня и
  ожидающие с `followUp` не позже сегодня, кроме готовых. Переключатель
  архива.
- Focus по всем областям: группы «Выбрано мной», «Пора сделать», «Пора
  вернуться», каждая задача один раз, готовые и архивные исключены.
- Добавление сверх эталона: четвёртая группа Focus «Новое от агентов» для
  задач с `created_by` агента и пустым `owner_touched_at`, не готовых и не

  «от Клода», метка исчезает после первой команды владельца по задаче.
  В сайдбаре рядом с Focus счётчик таких задач. Каждая задача в Focus
  по-прежнему один раз, приоритет групп при пересечении: «Выбрано мной»,
  затем «Новое от агентов», затем «Пора сделать», затем «Пора вернуться».
- Глобальный поиск по всем областям: название, заметка, «чего ждём», имя
  проекта, текст пунктов чеклиста; все слова должны совпасть; отдельный
  переключатель поиска по архиву; готовые задачи включаются.
- Горячие клавиши: `N` открывает быстрое создание, `Cmd/Ctrl+K` фокусирует
  поиск. Инлайн-добавление в колонке.

### 8.2 Карточка и редактор

- Поля: название, проект, статус, заметка, срок, «чего ждём», дата возврата,
  чеклист с прогрессом, звезда Focus, архив и восстановление.
- «Переместить» в редакторе позволяет сменить область задачи; выбранный проект
  сбрасывается, затем можно выбрать проект новой области. `area` и `projectId`
  уходят в ту же атомарную `task.save`, что и остальные изменения.
- Кнопка «Сохранить» отправляет одну команду `task.save` со всеми
  изменёнными полями, статусом и чеклистом. Конфликт при сохранении
  показывает актуальную версию и оставляет текст владельца в форме, частично
  сохранённой карточки не бывает.
- Тост после изменения с кнопкой «Отменить» на 6,5 секунды, после создания с
  кнопкой «Открыть». Отмена идёт через команду `undo`.

- Уникальность имени в области без учёта регистра.
- Смена области проекта невозможна.

## 9. Авторизация

- Better Auth с адаптером Drizzle на той же базе. Маршруты библиотеки
  `/api/auth/*` монтируются в Hono отдельным обработчиком и открыты без
  сессии, как предусмотрено её интеграцией с Hono. Защищается сессией или
  ключом API данных `/api/*` кроме `/api/auth/*` и `/health`.
- Первый вход по паролю, затем регистрация passkey в настройках, далее
  passkey основной способ, пароль запасной. `disableSignUp: true`. Владелец
  создаётся командой `taskindex-admin create-owner`, пароль читается со stdin
  или из `op`. Восстановление доступа: `taskindex-admin reset-owner-password`
  на сервере, почтовых сценариев нет.
- Ограничение частоты попыток входа средствами Better Auth.
- Агент заводится отдельно от ключа: `taskindex-admin agent create --id claude-mac --label «Клод на маке»`. Ключи через плагин API-ключей Better Auth: `taskindex-admin agent-key create --agent claude-mac --scope read|tasks|write`, хранятся хешированными, отзываются командой `agent-key revoke`, у агента может быть несколько ключей. Актор `agent:<agent_id>`, метка из записи агента показывается в интерфейсе и в истории. Scope `read` только чтение, `tasks` команды над задачами, чеклистами и комментариями, `write` то же плюс проекты. Доверенный агент получает `write` и управляет проектами, ограничение до `tasks` это выбор владельца для отдельных агентов, а не правило.
- Изменяющие запросы с cookie-сессией проходят проверку Origin, чтение по
  GET без Origin не блокируется. Запросы с ключом идут с заголовком
  `Authorization: Bearer`, для этого у плагина настраивается извлечение
  ключа, потому что по умолчанию он читает `x-api-key`; второй заголовок тоже
  принимается. Без сессии и ключа API данных отвечает `unauthorized`.
- Права в первой версии: владелец и ключи со scope `write` имеют полный
  доступ к операциям пространства, тоньше трёх scope не делится. Операций с
  внешним эффектом в приложении нет. `dryRun` показывает последствия, но сам
  по себе подтверждением владельца не является: разрешение на действие
  определяется поручением владельца, приложение подтверждения не запрашивает.

## 10. Контекст для агентов и CLI

`GET /api/context` возвращает:

- `formatVersion`, `generation`, `seq`, `today`, `timezone`;
- области и статусы с русскими названиями, описаниями и цветами;
- проекты с описаниями и правило раскладки: задача попадает в проект по его
  описанию, при сомнении в область без проекта, а не в случайный проект;
- известные значения `origin.system` и правило «сначала поиск по origin,
  потом по тексту, потом создание»;
- описания полей записей из `.describe()` zod-схем;
- правила текстом: Focus, «Сегодня», порядок карточек, инварианты, лимиты,
  что означает конфликт и как его разрешать;
- перечень команд с JSON-схемами payload и краткими описаниями;
- счётчики: задачи по областям, статусам, архиву и Focus, проекты по областям;
- ссылки на `openapi.json`, `snapshot`, `events`, `export`.

CLI `taskindex`, тонкий клиент над API через типизированный `hc`:

```
taskindex context
taskindex snapshot
taskindex tasks [--area] [--project] [--status] [--archived] [--focus] [-q] [--limit] [--cursor]
taskindex task get|create|sync|update|save|move|archive|restore|focus|history <...>
taskindex operation get <operationId>
taskindex task find-origin --system <s> --ref <r>
taskindex checklist add|update|remove|reorder <...>
taskindex comment add|remove|list <...>
taskindex activity [--actor] [--since] [--limit]
taskindex digest [--since]
taskindex project list|create|update <...>
taskindex batch --file commands.json
taskindex focus
taskindex events --since N [--follow]
taskindex undo <seq> | --operation <operationId>
taskindex export [--out file.json]
```

Служебный `taskindex-admin` работает только на сервере с прямым доступом к
базе: `create-owner`, `reset-owner-password`, `agent create|list|disable`,
`agent-key create|list|revoke`, `migrate`, `mark-restored`, `open-writes`,
`import`.

Восстановление операций в CLI устроено так же, как в браузере. Конверт
пишется в `$XDG_STATE_HOME/taskindex/ops/<operationId>.json` до отправки и
удаляется только после подтверждённого успеха либо окончательной ошибки с
`retryable: false`. Временный `retryable: true` сохраняет конверт и повторяет
тот же запрос по правилам раздела 7; после исчерпания автоматических попыток
CLI печатает причину, `retryable: true` и `operationId` с кодом выхода 1.
При ошибке сети или тайм-ауте CLI печатает `operationId` в JSON-ответе с
`status: unknown` и кодом выхода 1.
Агент выясняет исход через `taskindex operation get` или повторяет ту же
команду с `--operation-id`, угадывать не приходится. При старте CLI
сообщает о незавершённых конвертах, `taskindex operation resume` досылает
их.

Общие флаги: `--json` (по умолчанию, если stdout не терминал), `--dry-run`,
`--operation-id`, `--base-revision`. Конфигурация через `TASKINDEX_URL` и
`TASKINDEX_TOKEN`, токен подставляется из 1Password через `op`. Коды выхода:
0 успех, 1 ошибка сервера или сети, 2 неверные аргументы, 3 конфликт с
выводом актуальной записи, 4 нет доступа.

Скилл `skills/taskindex/SKILL.md`, основной сценарий это создание и
повторная обработка задач из внешних источников: сначала `context`; для
источника с идентификаторами использовать `sync` с упорядоченной версией
самого источника; если её нет, не выдавать `observedAt`, ETag или хеш за
версию. При `freshness_unknown` существующая задача не перезаписывается;
осознанная правка по поручению выполняется через `task.update` или `task.save`
с актуальной `baseRevision`. Для остального `find-origin` и поиск по тексту,
затем `create` с проектом по описаниям; много задач за раз через `batch`; решения владельца
старше решений агента, при `conflict` перечитать и переоценить действие,
повторять свои поля автоматически можно только если новое состояние не
изменило смысл поручения; отчёты, находки и уточнения писать комментариями,
описание задачи редактировать только по явному поручению; `baseRevision` из
свежего `get` перед осознанной правкой; при `status: unknown` сначала
`operation get`, повтор только с тем же `operationId`; `--dry-run` перед
массовыми изменениями показывает последствия, разрешение на действие даёт
поручение владельца, а не сам факт `dryRun`; сессию начинать с `digest`, а
не со снапшота; как читать `current`, `existing`, `applied` и `skipped` в
ответах. Скилл это
продуктовый артефакт, его текст проверяется на этапе 5 вместе с CLI. Симлинк
в `~/.claude/skills/taskindex`.

## 11. Экспорт, резервные копии, восстановление

- `GET /api/export` и `taskindex export`: JSON с `formatVersion`,
  `exportedAt`, `generation`, `seq`, `settings`, `projects`, `tasks`,
  `checklistItems`, `comments`, `agents`, `events`, `operations`. Полный, без
  обрезания, все таблицы и курсор читаются в одной транзакции. Ключи доступа
  и сессии в экспорт не входят.
- `taskindex-admin import file.json` только в пустую базу или с `--replace`,
  проверяет формат, после импорта устанавливает новое `generation`. Таблиц
  авторизации в JSON нет, поэтому после импорта владелец и ключи агентов
  создаются заново командами из раздела 9, это часть процедуры.
- Litestream в отдельном контейнере реплицирует `/data/taskindex.db` в
  S3-совместимое хранилище, цель задаёт владелец. Retention 30 дней. Файл
  содержит и таблицы авторизации, физическое восстановление возвращает их.
- После любого физического восстановления обязателен
  `taskindex-admin mark-restored`: новое `generation`, чтобы открытые вкладки
  и агенты перезапросили снапшот. Команда запускается образом, который
  соответствует схеме восстановленной базы, а не последним неудачным релизом.
- Перед физической заменой файла базы останавливаются и приложение, и
  Litestream; admin-команды записи тоже не выполняются. Убедиться, что все
  соединения закрыты. Файл базы и его `-wal`/`-shm` рассматриваются как один
  набор: WAL от заменяемой базы нельзя оставлять рядом с восстановленным
  файлом. Старый набор сохраняется отдельно для диагностики, проверенная
  автономная копия устанавливается без чужих sidecar-файлов. Локальное
  состояние Litestream согласуется с восстановленной базой штатной процедурой
  закреплённой версии; прежняя история копий в S3 не удаляется. После
  `mark-restored` репликация возобновляется, проверяется создание и чтение
  новой подтверждённой точки с новым поколением базы. Отсутствие ошибок в
  логах само по себе успешным возобновлением не считается.
- Учебное восстановление до переключения и затем раз в квартал, процедура в
  `deploy/README.md`: остановить приложение с завершением текущих запросов,
  зафиксировать `generation`, `seq`, образ и схему, дождаться подтверждения
  этой точки репликой Litestream и остановить Litestream. Снять локальную
  автономную копию через `sqlite3 .backup`. Получить контрольный экспорт из
  временного экземпляра на этой копии до любых тестовых изменений. Записать
  точный идентификатор восстановления реплики средствами закреплённой версии
  Litestream; произвольное время снятия HTTP-экспорта такой точкой не является.
  Рабочее приложение и репликацию после фиксации можно возобновить.
  Восстановить именно подтверждённую точку S3 во второй временный путь,
  выполнить `PRAGMA integrity_check` и `foreign_key_check`, сравнить полный
  экспорт приложения с контрольным, включая комментарии, агентов, события и
  операции; отличается только время формирования экспорта. Затем подходящим
  образом выполнить `mark-restored`, поднять тестовый экземпляр, войти,
  выполнить команду и проверить `since`, SSE и смену поколения. Репликацию
  тестовой копии проверять в отдельной цели, чтобы два экземпляра не писали
  в один путь S3; возобновление после физической замены отдельно проверяется
  при репетиции отката деплоя.

## 12. Развёртывание и окружения

- `deploy/Dockerfile`: сборочная стадия на `node:24-bookworm` с компиляцией
  better-sqlite3, рантайм `node:24-bookworm-slim`, не root, `tini`. Alpine не
  использовать из-за нативного модуля. Сборка образа и запуск с файловой
  базой проверяются уже на этапе 3, а не при деплое.
- `deploy/compose.yml`: сервис `app` с портом `127.0.0.1:3100:3000` и томом
  `/data`, сервис `litestream` с тем же томом. Приложение само раздаёт
  `dist/web` с фолбэком на `index.html`, поэтому деплой это один образ.
- `deploy/nginx/taskindex.conf`: TLS через certbot, `proxy_pass` на
  `127.0.0.1:3100`, `client_max_body_size 4m`, для `/api/events/stream`
  `proxy_buffering off`, `proxy_read_timeout 1h`, `proxy_http_version 1.1`,
  пустой `Connection`.
- Переменные: `DATABASE_PATH`, `BASE_URL`, `BETTER_AUTH_SECRET`,
  `TIMEZONE`, `LOG_LEVEL`. Секреты подставляются из `op` при деплое, в
  репозитории не хранятся.
- Логи в JSON-строках с `operationId`, `actor`, `command`, `code`,
  `durationMs`. Диагностика прода через `/health` и `docker logs`.
- Миграции применяются явно, не при старте приложения: команда
  `taskindex-admin migrate` в контейнере. Образ несёт номер схемы, под
  которую собран, и при старте требует точного совпадения с базой: на
  неприменённой или более новой схеме приложение не запускается. Старый
  образ на новой базе не работает, совместимость схем не обещается, поэтому
  откат всегда возвращает согласованную пару «образ и копия базы».
- `deploy/deploy.sh` запускается из основного чекаута `main` на VPS и
  выполняет по порядку: `git checkout <коммит>`; сборка образа с тегом
  коммита; остановка приложения по SIGTERM: перестать принимать запросы,
  закрыть SSE, завершить текущие короткие запросы и закрыть соединение БД.
  После этого предметная запись закрыта. Дождаться подтверждённой репликой
  финальной точки и остановить Litestream; снять финальную копию базы через
  `sqlite3 .backup` в `/data/backups/<время>-<коммит>.db`. Рядом сохранить
  предыдущий тег образа, номер схемы, `generation`, `seq` и точку реплики.
  Затем `taskindex-admin migrate` в новом образе; запуск Litestream и приложения;
  ожидание `/health` с совпадающими `schemaVersion` и `build`. Запуск
  контейнера сам по себе готовностью не считается: приложение до привязки
  порта проверяет совпадение схемы с образом, открывает базу и выполняет
  пробную запись в `settings`, при любой ошибке завершается с ненулевым
  кодом, не начав слушать. Этого недостаточно: между привязкой порта и
  проверкой скриптом клиент уже мог что-то записать. Поэтому при деплое
  контейнер стартует с закрытой записью, `TASKINDEX_WRITES=held`: чтение,
  SSE и `/health` работают, а команды отвечают `unavailable` с
  `retryable: true`, что клиенты и CLI переживают по правилам повторов.
  Скрипт дожидается `/health` с `writes: held`, совпадающими
  `schemaVersion` и `build`, и только затем открывает запись командой
  `taskindex-admin open-writes` через `docker exec`. Открытие записи это
  граница: до неё автоматический откат с возвратом копии безопасен, после
  неё автоматическое восстановление базы запрещено. Пауза записи это время
  остановки, подтверждения реплики, копии, миграции и проверки; её длительность
  измеряется при учебном прогоне.
- Откат при неудачной проверке, автоматический: остановить и новый контейнер
  приложения, и Litestream; вернуть копию из `/data/backups` по правилам
  физического восстановления раздела 11, включая sidecar-файлы и локальное
  состояние репликации. Выполнить `mark-restored` предыдущим образом,
  соответствующим сохранённой схеме; запустить предыдущий тег с `writes: held`
  и Litestream, проверить `/health` и подтверждённую новую точку реплики,
  затем открыть запись. Старые резервные копии в S3 сохраняются.
  Откат после того, как новый релиз уже принимал запись, автоматическим не
  бывает: владелец либо выбирает
  возврат пары с потерей изменений за это окно, либо исправление вперёд.
  Пара «образ и копия базы» перед каждым деплоем хранится не меньше недели.
- Окружения: dev с `./data/dev.db`, тесты с `:memory:`, прод с томом.
  Тестовые записи в рабочую базу не попадают.

Обязательные сценарии исправленного контракта дополняют эту матрицу:

- API: атомарная смена `area` и `projectId` через `task.save`, отказ без
  частичного сохранения при проекте чужой области; Undo переноса возвращает
  `A,B,C`, занятый прежний ключ даёт конфликт всей отмены.
- API: Undo для создания и обновления через `task.sync`, для пакета
  `task.create → task.update` и создания комментария; последующая предметная
  правка блокирует отмену создания. После Undo та же версия источника
  получает `stale`, а более новая версия не затирает защищённые поля владельца.
  Неизвестная свежесть не изменяет существующую задачу; техническое продвижение
  версии не создаёт ложного конфликта с редактором и не откатывается через Undo.
- Store и CLI: `503 retryable` сохраняет конверт и после открытия записи
  выполняется с прежним `operationId`; любой успех без событий, включая
  повторное удаление комментария, завершает pending. Пакет применяется целиком
  и снимает оптимистичный слой только после последнего события, в том числе
  при разных порядках HTTP/SSE, пропуске события и разбиении догона на страницы.
- Shared и файловая БД: одинаковый бинарный порядок fractional keys в JS и
  SQLite; WAL и `synchronous=FULL` проверяются на пишущих соединениях
  приложения и admin-команд, а не только на `:memory:`.
- Развёртывание: репетиция неудачного релиза проверяет остановку обоих
  контейнеров, восстановление согласованной базы без чужого WAL,
  `mark-restored` подходящим образом и подтверждённую новую точку репликации
  при сохранении старой истории копий; учебный экспорт совпадает с выбранной
  подтверждённой точкой восстановления по полному содержимому.

`npm run check` обязателен на контрольных точках этапов и перед каждым PR;
`npm run e2e` — при завершении этапов 4 и 6 и перед итоговым мерджем.
