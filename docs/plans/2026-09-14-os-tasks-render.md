# План волны 2б и 2в: `/OS` читает задачи из TaskIndex

**Статус:** выполнено целиком 2026-09-15 (2б и 2в), карточка TI-090 закрыта: `/OS` `936eaee` + `0f9bed1`, прод 45 задач и 11 направлений, launchd установлен.
Дополнен 2026-09-14 по плану Codex из параллельной сессии: снимок вместо
постраничного чтения, файл свежести отдельно от git, текст кнопок Пульта (помечено «от Codex»). Решение владельца 2026-09-14 в
сессии Codex («окей»): launchd только обновляет локальный файл, без
автокоммита и push; коммитит и пушит обычная сессия `/OS` вместе со своими
правками. Пункты про git в §5.1 и §8 приведены к этому решению.

**Цель:** канон задач агентства переезжает в TaskIndex, а `/OS/TASKS.md`
остаётся файлом прежнего формата, который пишет скрипт, чтобы `validate.sh`,
Пульт задач и `weekly-os-audit` работали без правок. С этого
дня задачи закрываются и двигаются только на доске или через скилл
`taskindex`; сессия в `/OS` файл не редактирует.

**Спека:** `docs/specs/2026-09-12-owner-workflow.md`, разделы 8.1–8.6 и 5.1;
волны 2б и 2в из §10. Отклонения от спеки помечены ниже словом «Отклонение».

**База:** `main` `4609f82` (волна 2а: скилл, CLI и ключи на маке стоят).
Прод `fe1f8b0`, схема 6, на доске 0 задач и 0 направлений.

## 0. Что изменится для владельца, на примерах

1. **Сессия в `/OS` разбирает конфу и хочет дописать контекст к задаче**
   («инста: фидбек вендора 12.09»). Сегодня она правит строку в `TASKS.md`
   и коммитит вместе с карточками. После переключения она показывает
   изменение заметки задачи на доске, ждёт «да», пишет через
   `taskindex task update`; файл `TASKS.md` перерисует скрипт. По истории
   git за последние три недели так происходило почти в каждой сессии
   (20 из 20 последних коммитов `TASKS.md` сделаны агентом внутри
   `docs(...)`/`chore(...)` коммитов). Значит, после переключения каждая
   такая правка будет спрашивать «да». Это следствие выбранного строгого
   правила; если окажется утомительно, ослаблять правило, а не возвращать
   правки файла.
2. **Ты закрыл задачу на доске с телефона.** Через час launchd-задание на
   маке перерисовало локальный `TASKS.md` (без коммита). Пульт задач и
   аудит видят закрытие сразу, GitHub-копия обновится с ближайшей сессией
   `/OS`, которая закоммитит файл вместе со своими правками. Проблема из
   `PROBLEMS.md`, которую задача закрывала, остаётся до понедельника: аудит
   спросит «снять?».
3. **Понедельник, `weekly-os-audit`.** Первым шагом рендерит файл сам, потом
   всё как раньше. В отчёте появляется блок «завершённые задачи с `closes`
   на живые проблемы: снять, обновить `next:` или оставить?».
4. **Пульт задач** перед сборкой вызывает рендер; если TaskIndex недоступен,
   собирается на старом файле и пишет в шапке «TASKS.md не обновлён,
   последний рендер <дата коммита>».

## 1. Порядок работ: сначала инструменты, потом переключение одним днём

Спека делит работу на 2б (правило, скрипт, launchd) и 2в (направления,
импорт). На практике переключать `/OS` на сгенерированный файл раньше
импорта нельзя: доска пуста, рендер дал бы пустой `TASKS.md`. Поэтому:

| Шаг | Что | Где | Когда |
|---|---|---|---|
| 2б-1 | Скрипты `render_tasks_md.py` и `import_tasks_md.py`, прогон «туда и обратно» в sandbox на текущем `TASKS.md` | `/OS/scripts`, sandbox TaskIndex | сразу после обсуждения |
| 2б-2 | Тексты правил для `/OS/CLAUDE.md` и `AGENTS.md`, правка `render_tasks_panel.py`, шаги в `weekly-os-audit`, plist launchd | подготовлены в ветке `/OS`, не активны | вместе с 2б-1 |
| 2в-1 | Шесть направлений агентства на проде одним `batch` | прод, ключ `claude-mac` | по «да» |
| 2в-2 | Импорт `TASKS.md` на прод: таблица «строка → область, направление, приоритет, метки», «да», `batch` | прод | тот же день |
| 2в-3 | Первый рендер, `diff` с исходным файлом, коммит файла и правил, установка launchd (только обновление файла), правка промпта аудита | `/OS`, мак | тот же день, сразу после 2в-2 |

Между 2в-2 и 2в-3 никто не редактирует `TASKS.md` руками (окно в несколько
минут). До 2в-3 launchd не установлен и правила не переключены: старый
процесс работает как сегодня.

Ответы владельца 2026-09-15 (разбор по одной): «Три клика» — все три пункта

прямым обновлением в базе хаба), в перенос не идёт; «Запустить Ари Phase 1» —

«Lora TO-DO» — «Разработка», направление `todo-lora`, P3; «Аудит

Чатинг, P3; направление `chatters` переименовано в «Чатинг». Решения 1, 2,
3, 4, 6 приняты по рекомендации.

1. **Ключ для рендера.** Спека §8.2 говорит «ключ `claude-mac`». Рендер
   только читает, а launchd-задание это рутина, и по решению §2 рутины
   ключей с правом записи не получают. Предлагаю отдельный ключ `os-render`
   со scope `read`: даже ошибка в скрипте не сможет ничего записать, а в
   `taskindex-admin agent list` видно, что это рутина. Файл
   `~/.config/taskindex/os-render.env`, как остальные ключи.
2. **`[сегодня]` для просроченных.** Спека: тег, если `due` = сегодня.
   Задача с `due` вчера без тега выглядела бы как «не срочно». Предлагаю
   тег при `due` ≤ сегодня или `followUp` ≤ сегодня, как выборка
   «На сегодня» на доске.
3. **Метки моделей при импорте.** Спека §8.3 метки `lora`, `lily`, `ari` не
   упоминает. Предлагаю ставить метку, если название задачи содержит
   `[[lora]]`, `[[lily]]`, `[[ari]]` или слово «Лора/Лили/Ари», и показать это
   в таблице импорта: ты вычёркиваешь лишнее до «да».
4. **`[[wikilinks]]` в названиях.** В `TASKS.md` названия содержат

   покажет скобки буквально. Предлагаю хранить как есть: Пульт задач по ним
   строит ссылки на карточки сущностей, а чистить названия можно потом по
   одной.
5. **Направления для `[код]`-задач.** Их восемь строк: трафик-контроль

6. **Что делать с Done старше недели при импорте.** Спека: Done не

   переносить, как в спеке: git помнит.
7. **Git из launchd: решено 2026-09-14** (владелец в сессии Codex). Скрипт

   понедельникам коммитит обязательно. Цена: копия на GitHub отстаёт от

## 3. Модель отображения: TaskIndex → `TASKS.md`

Источник: `taskindex snapshot` (от Codex: один согласованный снимок с
задачами, архивом и проектами вместо постраничного `tasks --all` плюс
`context`, между которыми доска могла измениться) и `taskindex digest`
(`today` в `Europe/Moscow`, чтобы «сегодня» не зависело от часов мака).
Фильтр `area = agency`, `archived = false` применяется в скрипте.

| Из TaskIndex | В файл |
|---|---|
| `area` ≠ `agency` или `archived` | не попадает |
| `status: done`, `updatedAt` не старше 7 дней | `## Done`: `- [x] ~~**Название**~~ (YYYY-MM-DD) — заметка`, дата из `updatedAt`, без `closes`, порядок по `updatedAt` убыв. |
| `status: done` старше 7 дней | не попадает |
| `status: waiting` | `## Waiting On`, порядок по `followUp` (пустые в конец), затем `orderKey` |
| `status: todo\|doing`, `priority: p3` | `## Someday`, порядок по `orderKey` |
| `status: todo\|doing`, `priority: p1\|p2` | `## Active`, порядок по `orderKey` |
| `due` ≤ сегодня или `followUp` ≤ сегодня (решение 2) | `[сегодня]` первым тегом |
| метки `otvet`, `dengi`, `5-min` | `[ответ]`, `[деньги]`, `[5 мин]` в порядке каталога |
| направление `hiring` | `[найм]` последним тегом |
| метки `lora`, `lily`, `ari` | в файл не пишутся (Пульт и валидатор их не знают) |
| `closes` у незавершённой задачи | `; closes \`slug\`` в конце контекста |
| `note` | после ` — `; переводы строк → `; `; пустые строки схлопываются; `[[вики-ссылки]]` как есть |
| `waitingFor` | в начале контекста: `ждём: …; ` |
| `checklist`, комментарии, `focus`, `priority` P1/P2 | не пишутся (формат файла не различает) |

Строки таблицы применяются сверху вниз: статус решает секцию раньше
приоритета (`waiting` + P3 идёт в `Waiting On`). Название пишется как
`**[теги] Название**`; если у задачи нет заметки, нет и ` — `. Секции
печатаются всегда, даже пустые (`## Waiting On` сегодня пуст), чтобы
`validate.sh` и Пульт видели знакомую структуру.

Стабильность строк важна: Пульт считает «в списке с» и «движение» по git
истории строки. Рендер детерминирован (нет времени, нет случайных
порядков) и переписывает файл только если текст изменился, поэтому
нетронутые задачи сохраняют свои строки и возраст.

Свежесть отдельно от git (от Codex): если за час ничего не изменилось,
коммита нет, и дата коммита `TASKS.md` не говорит, что доска читалась.
Поэтому после каждого успешного чтения скрипт пишет
`~/Library/Application Support/gosling/os-tasks-render.json`: время,
`generation`, `seq`, хеш результата, был ли коммит. Пульт и аудит
показывают свежесть по этому файлу («доска прочитана <время>»), а при
сбое возраст последнего успешного чтения. Файл вне git.

Формат строки такой же, каким его читает `render_tasks_panel.py`
(`parse_tasks`: `^- \[( |x)\] (\*\*|~~)Название(\*\*|~~)\s*(—\s*)?контекст`).

## 4. Модель импорта: `TASKS.md` → команды (для 2в и для проверки 2б)

Обратная таблица; парсер тот же, что у Пульта.

| В файле | В TaskIndex |
|---|---|
| `## Active` | `status: todo`, `priority: p2` |
| `## Waiting On` | `status: waiting`; `ждём: …` из начала контекста → `waitingFor`, остальное → `note` |
| `## Someday` | `status: todo`, `priority: p3` |
| `## Done` | не переносится (решение 6) |
| `[ответ]`, `[деньги]`, `[5 мин]` | метки `otvet`, `dengi`, `5-min` |
| `[найм]` | направление `hiring`; остальные направления по описаниям §5.1, сомнительные строки в вопрос |
| `[код]` | область `development`, направление по имени репозитория (решение 5); в файл больше не возвращается |
| `[сегодня]` | `due` = день импорта |
| `closes \`slug\`` в контексте | поле `closes`, из `note` убирается |
| контекст целиком | `note` (лимит 16 000 символов, самая длинная строка сегодня ~1 600) |
| `[[lora]]`/`[[lily]]`/`[[ari]]` в названии | метка модели (решение 3) |
| порядок строк в секции | `orderKey` через `position` в `task.create`: каждая следующая после предыдущей |

Название хранится без тегов, с `[[вики-ссылками]]` (решение 4); лимит 240
символов, самое длинное сегодня 75. Скрипт `import_tasks_md.py` не пишет
сам: он печатает таблицу для владельца (markdown) и файл `commands.json`
для `taskindex batch --file`. Направления, которых нет, идут в тот же
пакет первыми (`project.create`), поэтому пакет атомарен.

## 5. Скрипты в `/OS/scripts`

Python 3 (на маке 3.14), только стандартная библиотека, вызов CLI через
`subprocess` (`taskindex` на PATH, ключ через обёртку по `TASKINDEX_AGENT`).

### 5.1. `render_tasks_md.py`

```
python3 scripts/render_tasks_md.py            # перерисовать TASKS.md, напечатать diff
python3 scripts/render_tasks_md.py --check    # только diff, файл не трогать; код 0 без изменений, 1 с изменениями
python3 scripts/render_tasks_md.py --stdout   # напечатать результат, файл не трогать (для тестов)
```

- Один запрос `taskindex snapshot`: задачи, архив, направления, `today` и
  `timezone` в одном согласованном ответе (от Codex; `context` и `digest`
  не нужны). Любая ошибка CLI (не 0, не JSON, `generation_changed`) → файл
  не тронут, сообщение в stderr, код 2.
- Проверка до замены (от Codex): результат пишется во временный файл рядом,
  проверяется формат (только `# `, `## `, `- [ ]`/`- [x]`, пустые строки,
  правило 6 валидатора) и `closes` против живых слагов `PROBLEMS.md`
  (правило 7); только потом атомарная замена `TASKS.md` через `os.replace`.
  Не прошёл проверку → файл не тронут, код 2, причина в stderr и в файле
  свежести.
- Защита от ручной правки (от Codex): файл свежести хранит хеш последнего
  записанного содержимого. Если текущий `TASKS.md` не совпадает ни с этим
  хешем, ни с новым результатом, значит файл правили руками: скрипт
  останавливается с кодом 3 и пишет «TASKS.md изменён вручную, рендер
  остановлен»; сессия `/OS` переносит правку на доску через скилл и
  запускает рендер снова. Первый запуск после переключения делается с
  `--adopt`, чтобы принять текущий файл как исходный.
- Без git: скрипт не коммитит и не пушит (решение 7). Коммит делает сессия
  `/OS`; pre-commit hook прогонит `validate.sh` как обычно.
- Файл-замок `~/Library/Application Support/gosling/os-tasks-render.lock`,
  чтобы час launchd, Пульт и ручной запуск не пересеклись.
- Файл свежести `~/Library/Application Support/gosling/os-tasks-render.json`:
  `checkedAt`, `generation`, `seq`, `hash`, `written` (bool), `error`
  (строка или null). Пульт и аудит читают его.

### 5.2. `import_tasks_md.py`

```
python3 scripts/import_tasks_md.py --out /tmp/import            # таблица + commands.json
python3 scripts/import_tasks_md.py --out /tmp/import --repo-map hub=Hub,...
```

Печатает таблицу «строка → область, направление, приоритет, метки, срок,
closes» и список вопросов (строки без уверенного направления, `[код]` без
репозитория). После «да» владельца агент выполняет
`taskindex batch --file /tmp/import/commands.json`.

### 5.3. Проверка «туда и обратно» (приёмка 2б)

В sandbox TaskIndex (`eval "$(npm run -s sandbox)"` из `~/code/taskindex`):
шесть направлений → `import_tasks_md.py` на текущем `TASKS.md` → `batch` →
`render_tasks_md.py --check` в копии `/OS` → `diff` с исходным файлом.
Ожидаемые отличия и только они: ушли 8 строк `[код]` (они в области
«Разработка») и 1 строка Done (не импортируется); у строк с контекстом в
скобках перед тире появилось ` — ` перед скобкой; `closes` переехал в конец
контекста; порядок тегов нормализован. Счёт (от Codex): 48 строк в файле →
47 задач на доске, из них 39 агентских в зеркале и 8 в разработке; текст,
`[[вики-ссылки]]` и `closes` каждой строки сохранены. Любое другое
отличие это дефект рендера или парсера. Потом `bash scripts/validate.sh` на
сгенерированном файле зелёный, `render_tasks_panel.py` собирается, число
задач и `closes`-ссылок совпадает с прежним минус `[код]`.

## 6. Правила в `/OS`

`CLAUDE.md` и `AGENTS.md` правятся одинаково (валидатор требует
идентичности).

1. Таблица канонов, строка «Задачи»:
   `| Задачи | TaskIndex (https://tasks.gosling-agency.ru), через скилл \`taskindex\`; \`TASKS.md\` — зеркало для чтения, пишет \`scripts/render_tasks_md.py\` |`
2. Write-rules, пункт «Задачи» целиком заменяется:
   «**Задачи:** ведутся в TaskIndex через скилл `taskindex` (область
   «Агентство», направления Найм/Контент/Чатинг/Трафик/Финансы/
   Организационное; любая запись после «да» владельца на показанную
   карточку). `TASKS.md` не редактировать: его пишет
   `scripts/render_tasks_md.py`, ручные правки теряются при следующем
   рендере (launchd раз в час). В файл попадает только область «Агентство»;

   проблему, несёт поле `closes` со slug; завершение задачи проблему не
   снимает — это делает сессия /OS по слову владельца (аудит спрашивает по
   понедельникам).»
3. Раздел «Пульт задач»: «Канон задач в TaskIndex; страница читает

## 10. Что не делаем

- Обратную синхронизацию из файла: правки `TASKS.md` руками пропадают.
- Перенос `[код]`-задач обратно в файл: они живут в области «Разработка».
- Перенос Done, `BACKLOG.md`, `issues.md` реп.
- Автоматическое снятие проблем в `PROBLEMS.md` при завершении задачи.
- Правки `validate.sh` и формата файла.

## 11. Риски

- **Много «да».** Каждая правка контекста задачи из сессии `/OS` теперь
  спрашивает подтверждение (пример 1 в §0). Смягчение: агент собирает
  правки задач в конце сессии одним списком, одно «да» на список (правило 3
  скилла).
- **Потеря ручной правки файла в окне переключения.** Смягчение: шаги
  2в-2 и 2в-3 в одной сессии подряд, файл перед импортом закоммичен.
- **Снятая проблема при живом `closes`**: проверка перед заменой не даёт
  записать файл, который завалит правило 7 валидатора; файл не обновляется,
  причина в файле свежести и в отчёте аудита, правка `closes` через скилл.
- **Возраст строк в Пульте** сбросится у строк, чей текст изменился при
  нормализации (скобки, порядок тегов). Разовый эффект в день переключения.
- **launchd без сети или без ключа**: файл не тронут, код 2, лог; аудит и
  Пульт назовут время последнего успешного чтения из файла свежести.
- **Ручная правка `TASKS.md` после переключения**: рендер останавливается,
  ничего не теряется, сессия `/OS` переносит правку на доску.

## 12. Приёмка волны

- 2б: прогон §5.3 зелёный; `validate.sh` на сгенерированном файле без FAIL;
  Пульт собирается; файл свежести пишется; тексты правил и plist лежат в

  используется каждый день (спека §10).
