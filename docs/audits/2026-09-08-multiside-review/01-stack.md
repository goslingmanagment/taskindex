Дата: 2026-09-08. Reviewer: Astra xhigh, направление «стек и эксплуатационная соразмерность».

**Вывод: стек выбран разумно; оснований для очередной переписки на другой framework или СУБД не найдено.** React SPA + Hono + SQLite хорошо соответствуют одному владельцу и нескольким агентам, которые ведут задачи через API. ## Существенные замечания

### S-01 — P2. Короткие API-операции зависят от всех задач, комментариев и всей истории

**Тип:** подтверждённая проблема производительности реализации. **Confidence: высокая** для причинной цепочки, средняя для момента, когда её заметит владелец: реальная будущая нагрузка и VPS не заданы.

**Сценарий и эффект.** Агенты долго ведут небольшую доску: появляются история, комментарии и архив. Даже изменение одной карточки загружает всю историю в JS внутри write transaction. UI, auth, health и другие запросы обслуживает тот же Node-процесс, поэтому затраты превращаются в общую задержку. Чтение одной операции после неизвестного исхода запроса также сканирует весь operations table и делает дополнительные SQL lookup заголовков. Архивирование задач не устраняет эту стоимость.

**Доказательства:**

- `/Users/dmitriy/code/taskindex/src/server/operations.ts:93-106`: `readState(db)`, `readEvents(db)` без limit, копия history при каждом элементе batch.
- `/Users/dmitriy/code/taskindex/src/server/db.ts:118-146`: полные SELECT задач, комментариев и чеклистов; для каждой задачи новые `items.filter` и `comments.filter`. Сложность сборки включает `T*I + T*C`.
- `/Users/dmitriy/code/taskindex/src/server/db.ts:191-195`: сравнение каждой задачи с `previous.tasks.find` и сериализацией, компонент `T²`. Аналогичный поиск/сериализация есть для projects/comments.
- `/Users/dmitriy/code/taskindex/src/server/db.ts:235-272`: `readOperations()` читает все результаты и делает до трёх дополнительных SQL-запросов на каждый result.
- `/Users/dmitriy/code/taskindex/src/server/app.ts:599-615`: получение одной задачи или origin тоже строит всё состояние; `:679-681` фильтрует всю историю; `:713-721` строит все операции до pagination; `:736-737` ищет один id после полной загрузки.
- `/Users/dmitriy/code/taskindex/src/server/app.ts:196-225`: пагинация хеширует полный массив и режет его после загрузки; лимит ответа не ограничивает серверную работу.
- `/Users/dmitriy/code/taskindex/src/server/app.ts:851`: первоначальный SSE backlog читается без limit; проверка размера очереди делается после enqueue полного массива (`:810-819`).

Это in-memory microbenchmark без HTTP, auth, сети и fsync. Промежуточный дешёвый шаг — `Map` по id и группировка items/comments одним проходом, но он не устраняет чтение всей истории. SSE backlog читать ограниченными порциями с backpressure. Закрепить небольшой бюджет задержки на репрезентативном долгоживущем архиве; не вводить retention, который сломает undo/idempotency, лишь ради маскировки сканов.

### S-02 — P1. Непрерывное резервирование не имеет постоянного внешнего сигнала о сбое

**Тип:** эксплуатационный пробел перед рабочим запуском, не доказанная потеря данных. **Confidence: высокая** для содержимого репозитория; внешний мониторинг владельца не проверен.

**Сценарий и эффект.** После успешного deploy истекают/отзываются S3 credentials, закрывается bucket или Litestream перестаёт успешно синхронизироваться. Приложение продолжает принимать изменения, `/health` остаётся зелёным. Владелец замечает проблему только при следующем ручном sync/restore либо после потери VPS; фактическое окно потери данных может значительно превысить ожидаемое.

**Доказательства:**

- `/Users/dmitriy/code/taskindex/deploy/compose.yml:26-37`: healthcheck только app; `:41-59`: Litestream имеет restart/log rotation, но нет проверки прогресса репликации и доставки сигнала владельцу.
- `/Users/dmitriy/code/taskindex/src/server/app.ts:408-423`: health проверяет локальную схему и локальную запись, данных реплики в ответе нет.
- `/Users/dmitriy/code/taskindex/deploy/litestream.yml:1-20`: нет `heartbeat-url` или metrics endpoint; control socket включён, но сам не выполняет наблюдение.
- `/Users/dmitriy/code/taskindex/deploy/common.sh:39-49`, `/Users/dmitriy/code/taskindex/deploy/deploy.sh:67-91`: confirmed sync используется в процедурах переключения. Периодического наблюдателя в `deploy/` нет.

**Рекомендация.** До принятия реальных данных подключить простейший внешний dead-man switch к health-gated heartbeat Litestream либо небольшой timer, который проверяет подтверждённый sync и давность успешной репликации и отправляет сигнал по согласованному каналу. [Litestream уже имеет встроенный heartbeat, который отправляется только при успешной синхронизации всех включённых баз](https://litestream.io/reference/config/#heartbeat-monitoring). Prometheus/Grafana для одной доски не обязательны. Если инфраструктурный мониторинг уже есть, достаточно задокументировать и проверить именно эту проверку и получателя.

Проверять полезно два независимых состояния: доступность приложения и пригодность удалённой копии. Не следует автоматически закрывать запись при каждом кратком S3-сбое без решения о допустимых RPO/доступности. Restore drill на выбранном S3, уже требуемый deployment README, остаётся необходимым; локальный file-backend drill его не заменяет.

### S-03 — P2. Собственный migrator учитывает имя файла, но не содержимое применённой миграции

**Тип:** защита жизненного цикла схемы; текущий drift не обнаружен. **Confidence: высокая**.

**Сценарий и эффект.** При следующей агентской правке меняют существующий `.sql`, сохраняя имя. На новой базе применяется новое содержимое, старая база эту миграцию пропускает. Обе могут получить одинаковый `schema_version` и пройти поверхностную проверку версии. Ошибка появляется уже в SQL-запросах или ограничениях после запуска; для нескольких локальных сред и дальнейших релизов это создаёт труднообъяснимое расхождение.

**Доказательства:** `/Users/dmitriy/code/taskindex/src/server/db.ts:69-87` создаёт ledger с единственным `name` и проверяет только наличие имени; `:93` без сверки структуры выставляет общую версию; `:98-103` runtime сравнивает только setting. README требует не менять применённые миграции, но машинной проверки этого условия нет.

**Рекомендация.** Хранить checksum неизменяемого SQL и отказывать при несовпадении уже применённого файла; проверять миграции от предыдущего release snapshot и на пустой базе. Для текущего первого baseline можно заранее закрепить digest, пока нет нескольких рабочих баз. Переход на штатный Drizzle migrator допустим ради уменьшения собственного кода, но нельзя считать, что любое штатное средство автоматически закрывает drift: конкретную проверку checksum при повторном запуске надо проверить отдельно. Не заменять SQL-миграции на schema push в production.

### S-04 — P2. Общие схемы есть, но web-клиент фактически доверяет произвольному `T`

**Тип:** пробел контрактов при будущих изменениях; не доказанный текущий mismatch ответа. **Confidence: высокая** для кода, средняя для конкретных будущих последствий.

**Сценарий и эффект.** Меняется поле snapshot/operation ответа, либо долго открытая вкладка продолжает работать после обновления API. HTTP 200 с неожиданной структурой проходит `request<Snapshot>` без проверки; ошибка проявляется в store/reconciliation как сломанная загрузка или неизвестное состояние операции. Компилятор не проверяет связь строкового URL и произвольно назначенного response type. Стек уже содержит средства для более сильной границы, но web ими не пользуется.

**Доказательства:**

- `/Users/dmitriy/code/taskindex/src/web/app/api.ts:13-16` допускает любой `T`; `:37-74` читает JSON и возвращает `value as T`.
- `/Users/dmitriy/code/taskindex/src/web/app/store.ts:170-176`: snapshot типизируется generic assertion; `/Users/dmitriy/code/taskindex/src/web/app/sync.ts:23-28`: SSE JSON передаётся в reducer без event schema parsing.
- `/Users/dmitriy/code/taskindex/src/cli/client.ts:49-64`, `:92-103`: `hc<AppType>` работает на двух mutation endpoints CLI, остальные пути обрабатываются общей request-функцией.
- `/Users/dmitriy/code/taskindex/src/server/app.ts:1072` экспортирует AppType; `/Users/dmitriy/code/taskindex/src/shared/domain-schemas.ts` уже содержит нужные transport schemas.

**Рекомендация.** Использовать один небольшой клиент поверх существующего `hc<AppType>` для статической связи endpoint/request/response, а на внешней границе применять существующие Zod schemas хотя бы для snapshot, operation response и SSE event. [Hono документирует этот способ получения типизированного клиента](https://hono.dev/docs/guides/rpc). Runtime parsing и RPC-type inference решают разные задачи; один не заменяет другой. Для несовместимого протокола нужен явный ответ/перезагрузка клиента с сохранением drafts/outbox. Добавлять tRPC/oRPC и второй набор контрактов не требуется.

### S-05 — P2. Основной браузерный путь телефона не входит в автоматическую матрицу проверки

**Тип:** ограничение проверки стека и критерий приёмки; это не утверждение, что Safari сломан. **Confidence: высокая**.

**Сценарий и эффект.** Chromium tests проходят, а специфичное поведение WebKit, touch drag, мобильной клавиатуры/viewport или passkey на телефоне остаётся неизвестным. Именно телефон является заявленным способом входа и просмотра доски; отсутствие серверной ошибки этого не проверяет.

**Доказательства:** `/Users/dmitriy/code/taskindex/tests/e2e/playwright.config.ts:9-13` задаёт единственный `Desktop Chrome`, projects WebKit/mobile нет. `/Users/dmitriy/code/taskindex/src/web/app/auth.tsx:24-33`, `:102-105` содержат реальный passkey flow. `/Users/dmitriy/code/taskindex/vite.config.ts:26` не задаёт явную browser policy, поэтому действует default Vite.

**Рекомендация.** Задать короткую поддерживаемую матрицу: актуальный Chrome на Mac и актуальный Safari/iOS владельца. Добавить несколько критических WebKit/touch E2E, а регистрацию/вход passkey и drag с открытой мобильной клавиатурой принять на реальном телефоне по короткому checklist. [Playwright предоставляет отдельные browser/device profiles](https://playwright.dev/docs/emulation); эмуляция не заменяет проверку реального authenticator.

Сами Vite/Tailwind 4 оставлять. Их нижние границы различаются: [Vite по умолчанию ориентируется на Chrome 111/Firefox 114/Safari 16.4](https://vite.dev/guide/build), [Tailwind 4 указывает Firefox 128 при тех же Chrome 111/Safari 16.4](https://tailwindcss.com/docs/compatibility). Это не повод обеспечивать древние браузеры: достаточно честно выбрать и проверить фактически нужные устройства. Ручная телефонная приёмка уже отмечена незавершённой в deployment README; не следует считать её закрытой результатом Chromium.

## Компромиссы, которые не надо записывать в баги

1. **Один VPS и остановка app на миграцию.** Это объявленная модель доступности. Полноценный zero-downtime deployment с миграциями назад/вперёд значительно дороже; требования на него нет.
2. **SQLite и synchronous FULL.** FULL — выбранная гарантия локально подтверждённой записи; ослаблять её ради красивой скорости без решения владельца не следует. SQLite `:memory:` не проверяет fsync, но отдельный file-backed тест существует (`tests/api/durability.test.ts:13-35`), и поэтому говорить «все тесты только в памяти» было бы неверно.
3. **События + projection + сохранённый ответ операции.** Это не бессмысленное тройное хранение: оно обеспечивает историю/undo, текущее чтение и безопасный повтор после разрыва. Оптимизировать следует запросы и representation по доказанному bottleneck, сохраняя контракт.
4. **Небольшие pure functions вместо выделенного доменного сервиса/очереди.** Полезны для parity UI/CLI и property tests. Сложность протокола обусловлена агентами и неизвестным исходом запросов; замена Zustand/Redux её не уберёт.
5. **Exact dependency pins и относительно свежие tools.** Установленные direct dependencies совпадают с package.json. Не найдено основания откатывать Vite, Hono, Base UI или Zod только потому, что они свежие. Полноценный vulnerability audit transitive graph и supply-chain attestation в этом направлении не выполнялся; отсутствие заявленного CVE здесь не означает доказанную безопасность всего дерева.
6. **Локальный Node в PATH.** В текущей сессии `node --version` даёт 26.7.0; фактический `/opt/homebrew/opt/node@24` также указывает не на нужный runtime по проверке координатора. Это локальное состояние инструментов, не ошибка продукта. Собственный probe выполнен абсолютным Node 24.20.0 из `/tmp/taskindex-v2-tools/node-v24.20.0-darwin-arm64/bin/node`. Разумно добавить раннюю понятную проверку версии к локальному bootstrap, но не пересобирать зависимости под 26 и не принимать такой запуск за проверку заявленного стека.
