## B-01. Отзыв ключа не закрывает уже открытый SSE

**P1, высокая уверенность; воспроизведено.** Это обход уже применённого отзыва чтения: клиент продолжает видеть новые данные, созданные после отзыва.

Основной участок: `/Users/dmitriy/code/taskindex/src/server/app.ts:810` — `send()` передаёт любое новое событие подписчику, проверяя только локальный флаг `closed`. Подписчик добавляется в общий набор на `/Users/dmitriy/code/taskindex/src/server/app.ts:847` и не содержит идентичности ключа/сессии. Авторизация выполняется один раз до создания потока на `/Users/dmitriy/code/taskindex/src/server/app.ts:305`. Отзыв ключа меняет запись БД на `/Users/dmitriy/code/taskindex/src/server/admin.ts:200`, но не влияет на подписчика.

Минимальный сценарий:

1. На пустой изолированной БД создать владельца, read-агента и write-агента через настоящий Better Auth/admin API.
2. Read-ключом открыть `/api/events/stream?generation=G&since=0`, прочитать начальный комментарий соединения.
3. Отозвать этот ключ через `revokeAgentKey`.
4. Убедиться, что новый GET `/api/snapshot` с тем же ключом получает **403**.
5. Write-агентом создать задачу `Private task written AFTER revocation`.
6. Прочитать уже открытый SSE read-агента.

**Факт:** поток передал полный event с названием новой задачи. Воспроизведение использует настоящий `auth.api.verifyApiKey`, а не тестовый `authorize` stub.

**Ожидается:** после отзыва доступ к новым данным прекращается, в том числе через существующие соединения. Нужна проверка актуальности прав в течение жизни соединения либо механизм гарантированного завершения подписок при отзыве. Поскольку admin работает отдельным процессом, одной локальной ссылки из `revokeAgentKey` на набор подписчиков недостаточно.

По той же причинной цепочке отключение агента и удаление/истечение сессии владельца не отслеживаются существующим SSE. Это вывод из кода, **отдельными сценариями в этой проверке не воспроизводился**. Новый запрос с отозванным ключом блокируется корректно; проблема относится именно к существующему потоку.

Доказательство: `03-probes.ts`, секция `revoked-key-keeps-live-sse-access`; `03-probe-results.json`:

```json
{
  "freshRequestStatus": 403,
  "mutationStatus": 200,
  "receivedPostRevocationTitle": true
}
```

## B-02. Более старый snapshot стирает уже принятый SSE при ручном refresh

**P2, высокая уверенность; воспроизведено.** Задачи/изменения визуально исчезают до следующего события или дополнительного обновления. SQLite при этом остаётся корректной.

Основной участок: `/Users/dmitriy/code/taskindex/src/web/app/store.ts:155` — `loadSnapshot()` безусловно очищает buffer и заменяет подтверждённое состояние/seq. На `/Users/dmitriy/code/taskindex/src/web/app/store.ts:175` применяется ответ ранее начатого асинхронного GET. В `/Users/dmitriy/code/taskindex/src/web/app/sync.ts:11` соединение при том же generation повторно не открывается. Пункт ручного обновления доступен в `/Users/dmitriy/code/taskindex/src/web/app/shell.tsx:520`.

Минимальная последовательность:

1. Store показывает снимок S0 с `seq=0`, соединение считается открытым.
2. Пользователь выбирает «Обновить данные». Сервер формирует S0, но HTTP-ответ задерживается.
3. Другой клиент создаёт задачу. SSE event `seq=1` приходит раньше HTTP и применяется: `seq=1`, одна задача.
4. Приходит старый HTTP snapshot S0.

**Факт:** store возвращается к `seq=0`, задач 0, `connected=true`. Применённый event потерян и из подтверждённого состояния, и из buffer. Сам `refresh` не вызывает `catchUp`. Существующий EventSource сохраняет тот же generation/соединение; его последний полученный SSE ID уже 1. Периодический catch-up включается только при `!connected` (`sync.ts:46`).

**Ожидается:** snapshot не должен откатывать уже принятый прогресс. Варианты исправления: сохранить/переиграть события новее snapshot, отбрасывать устаревший ответ того же поколения либо синхронно переоткрывать поток с курсора применённого снимка и догонять журнал.

Доказательство: `03-probes.ts`, секция `refresh-rolls-back-live-event`. Проверены порядок прихода и отсутствие автоматического запроса событий:

```json
{
  "afterEvent": { "seq": 1, "tasks": 1 },
  "afterSnapshot": { "seq": 0, "tasks": 0, "connected": true },
  "requests": ["/api/snapshot"]
}
```

Это детерминированное воспроизведение на настоящем `WorkspaceStore` с отложенным transport и событием настоящего исполнителя команд. UI-клик отдельно браузером в моём probe не воспроизводился; его соединение с `refresh` подтверждено кодом.

## B-04. `digest` / `operations?since=` теряют no-op и отклонённые операции

**P2, высокая уверенность; воспроизведено.** Агент, читающий сводку или инкрементальную активность, не видит окончательные отказы и успешные команды без предметного изменения.

Основные участки: `/Users/dmitriy/code/taskindex/src/server/app.ts:717` и `/Users/dmitriy/code/taskindex/src/server/app.ts:963`. Оба фильтруют операции по `(o.lastSeq ?? 0) > since`. У no-op и сохранённых отказов `lastSeq=null`, поэтому они не проходят даже при `since=0`. У `/api/digest` неуказанный `since` также превращается в 0.

Минимальный сценарий:

1. Создать задачу операцией `initial`.
2. Отправить точное повторное присваивание текущего title отдельной операцией `no-effect` — сохранённый успех без событий.
3. Создать ещё одну задачу с занятым ID отдельной операцией `rejected` — сохранённый 409.
4. Сравнить `/api/operations`, `/api/operations?since=0` и `/api/digest?since=0`.

**Факт:** обычная лента содержит `initial`, `no-effect`, `rejected`; оба инкрементальных ответа содержат только `initial`. Увеличение `since` не возвращает пропуски: значение для них всегда 0. `more`/`nextCursor` здесь не помогают, так как эти записи исключены до пагинации.

**Ожидается:** сводка/инкрементальная лента должна учитывать сохранённые операции независимо от наличия доменных событий. Для этого требуется собственный монотонный курсор операций или другой контракт, который позволяет дочитывать no-op/отказы. Подстановка текущего domain seq не решит несколько операций, возникающих между одинаковыми domain seq.

Доказательство: `03-probes.ts`, секция `digest-and-since-exclude-no-event-operations`:

```json
{
  "activityIds": ["rejected", "no-effect", "initial"],
  "filteredIds": ["initial"],
  "digestIds": ["initial"]
}
```

Обычная UI-лента без `since` получает эти операции корректно; SSE invalidation `event: operations` существует и не исправляет API-фильтр.

## B-08. Запрет `localStorage` разрешает отправку без durable outbox

**P2, высокая уверенность; воспроизведено.** При неизвестном исходе операция теряет автоматическое восстановление после перезагрузки.

Основной участок: `/Users/dmitriy/code/taskindex/src/web/app/store.ts:118` — `persist()` использует optional chaining и успешно завершается при `storage === undefined`. `browserStorage()` на `/Users/dmitriy/code/taskindex/src/web/app/drafts.ts:8` возвращает `undefined`, когда сам getter `localStorage` запрещён браузером и бросает `SecurityError`. `submit()` проверяет только исключение из `persist`, поэтому продолжает отправку.

Минимальный сценарий:

1. Getter `localStorage` бросает `SecurityError` — стандартный тип ошибки недоступного browser storage.
2. Store загружает нормальный snapshot.
3. Отправляется `task.create`; transport теряет ответы/возвращает retryable network error.
4. Пользователь перезагружает страницу, создаётся новый store и запускается `recover`.

**Факт:** до перезагрузки выполнено 4 POST с тем же ID, в памяти один pending; после перезагрузки pending 0, конверта для recovery нет. Probe не утверждает, что задача в БД потеряна: доказана потеря сохранённого запроса и механизма выяснения/повтора неизвестного исхода.

**Ожидается:** если гарантия «сначала сохранить конверт, затем отправить» обязательна, полностью недоступное хранилище должно блокировать отправку с понятным сообщением так же, как ошибка `setItem`. Альтернатива требует явного ограниченного режима и другого сохраняемого outbox; молчаливой деградации недостаточно.

**Не путать с quota:** когда объект `localStorage` доступен, но `setItem` бросает ошибку квоты, `submit` уже корректно отказывает до сетевого запроса. Находка касается раннего превращения недоступного хранилища в `undefined`.

`DraftStorage.write()` также молча остаётся только в памяти при недоступном storage; новый экземпляр не восстанавливает текст. Это связанное проявление той же деградации. Не заявляю несуществующий текст UI «сохранено на устройстве»: в текущем UI найдено лишь «Черновик сохранится при закрытии» и «Закрыть с черновиком», которые могут относиться к закрытию формы. Сам outbox-дефект от этой формулировки не зависит.

Доказательство: `03-storage-probe.ts`, `03-storage-probe-result.json`:

```json
{
  "storageGetter": "SecurityError",
  "resolvedStorage": "undefined",
  "postCount": 4,
  "beforeReloadPending": 1,
  "afterReloadPending": 0,
  "draftPersistedAcrossInstance": false
}
```

## Воспроизведение и границы проверки

Все три скрипта выполнены успешно на Node **v24.20.0**, с реально установленным better-sqlite3 этого дерева. Команды из корня репозитория:

```sh
/tmp/taskindex-v2-tools/node-v24.20.0-darwin-arm64/bin/node --import tsx docs/audits/2026-09-08-multiside-review/03-probes.ts
/tmp/taskindex-v2-tools/node-v24.20.0-darwin-arm64/bin/node --import tsx docs/audits/2026-09-08-multiside-review/03-id-probes.ts
/tmp/taskindex-v2-tools/node-v24.20.0-darwin-arm64/bin/node --import tsx docs/audits/2026-09-08-multiside-review/03-storage-probe.ts
```

Абсолютный путь Node относится к текущему review-окружению; в другом окружении нужен совместимый Node 24. Это не требование продукта хранить runtime в `/tmp`.

Probes утверждают наблюдаемый дефект, поэтому на текущем дереве заканчиваются с exit 0. После исправления соответствующие assertions должны перестать выполняться; переносить их в регрессионные тесты нужно с ожидаемым исправленным результатом. Они не входят в общий `npm check`, исходники `tests/` не менялись.

Прочитаны и проверены по причинным цепочкам:

- Все модули `src/server`, включая транзакции, сохранение событий/ответов, idempotency, revocation, SSE, чтение и cursor pagination, owner/admin, export/import и `mark-restored`.
- Общие схемы, `applyCommand`, merge по revision, `task.sync`, сохранение owner fields, порядок задач, Undo и `applyEvent`.
- CLI parsing, отправка/повтор/`operation get`/`resume`, outbox publication; admin CLI и обработка ошибок.
- Store, sync, API transport, drafts, редактор, быстрое/инлайн-создание, комментарии и активность, URL, действия карточек и основные UI-фильтры.
- Скрипты deployment/rollback/backup, Compose, Nginx и Dockerfile — статически, без выполнения инфраструктурных действий.

Собственных новых подтверждённых дефектов не найдено в атомарном rollback пакета, разделении комментариев и task revision, бинарном сравнении fractional keys, области проекта/задачи, source-version high-water mark, запрете Undo поверх поздних пересекающихся предметных изменений, синхронной проверке импортируемого event/state и изоляции replica prefix при rollback. Это ограниченный результат чтения, не доказательство отсутствия других ошибок.

Не выполнялись мной: общий `npm check/build/e2e` (их независимо запускал координатор), реальные browser clicks и mobile/passkey-проверки, S3/VPS/production, crash/power-loss испытания SQLite/CLI fsync, стресс-тесты растущей истории, Nginx TLS и реальная сеть. Поэтому root-cause/impact выше не расширены на эти непроверенные условия. Непроверенные дополнительные гипотезы не представлены отдельными подтверждёнными багами.

Все находки относятся к текущему активному v2, не к удалённому старому приложению. Проблема локального ABI Node 26 / better-sqlite3 не включена в продуктовые дефекты: probes использовали Node 24.
