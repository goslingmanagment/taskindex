Код устроен осмысленно: общая предметная логика действительно вынесена из UI и HTTP, транзакционный исполнитель отделён от правил, сложные сценарии повторов и восстановления проверяются настоящей SQLite и авторизацией. В этом отчёте нет самостоятельной находки P1. Это не означает отсутствия функциональных P1: конкретные дефекты выделены отдельным reviewer в отчёт о багах. Готовность рабочего запуска нельзя выводить из одного отчёта о maintainability.

### Q-01. После валидации теряется связь имени команды и payload

**Место:** [src/shared/commands.ts:230](/Users/dmitriy/code/taskindex/src/shared/commands.ts:230), строка 231; ветвление через `startsWith` — строки 387, 422, 453; catch-all обработки checklist — строки 600–635. Вспомогательные списки полей: [commands.ts:39](/Users/dmitriy/code/taskindex/src/shared/commands.ts:39), [use-workspace.ts:5](/Users/dmitriy/code/taskindex/src/web/lib/use-workspace.ts:5).

`parseCommand` возвращает полезный `Command` с discriminated union, но следующая строка преобразует payload в `Record<string, unknown>`. Дальше правила читают поля через `as string`, `as number`, `as Task` и выбирают семантику по префиксам имени. Компилятор уже не может проверить, что конкретный payload подходит конкретному обработчику.

Последствия для следующего изменения вполне конкретны:

1. Если добавить команду в общую Zod-схему, отсутствие её обработчика не даст compile-time ошибки. Новая `project.*` попадёт в ветку update, новая `comment.*` — в remove, другая команда — в task/checklist fallback. Не каждая такая ошибка приведёт к неправильной записи: часть будет отклонена рантаймом. Но пропущенная реализация обнаружится только тестом или запросом.
2. При переименовании или изменении типа payload-поля старый доступ через `p.field as ...` продолжит компилироваться. Польза строгих схем сохранится на HTTP-границе, но исчезнет в месте, где принимаются предметные решения.
3. Перечни редактируемых/предметных полей передаются как свободные строки. Опечатка в таком списке не связана типом с `Task`; этот же список влияет на merge, ручную защиту и Undo.

**Реалистичное исправление:** оставить одну чистую функцию `applyCommand`, внутри использовать `switch (command.command)` с `assertNever` в конце и извлекать payload уже после narrowing. Выделить несколько функций по предметной ответственности — например, `applyTaskSave`, `applyTaskSync`, `applyUndo`, `applyChecklist` — с аргументами `Extract<Command, { command: ... }>['payload']`. Общими оставить merge, вычисление изменений и эмиссию событий. Списки полей проверять через `satisfies` и `keyof`, не строить универсальный динамический command framework.

**Что даст:** новая команда и изменение её схемы потребуют явного решения в обработчике; уменьшится число ручных приведения типов в наиболее критичном коде; сложный `sync` будет читаться отдельно от создания/чеклистов/Undo. Это рефакторинг сохранения поведения, не обвинение всех текущих casts в runtime-дефекте.

**Dedup:** архитектурная тема A-05 совпадает с этим корнем; каноническая quality-находка — Q-01.

### Q-02. Для неожиданной ошибки сервер оставляет только имя класса

**Место:** [src/server/app.ts:259](/Users/dmitriy/code/taskindex/src/server/app.ts:259), особенно строка 285. Лог запроса ограничен командами: [app.ts:327](/Users/dmitriy/code/taskindex/src/server/app.ts:327). Неиспользуемая настройка: [deploy/compose.yml:15](/Users/dmitriy/code/taskindex/deploy/compose.yml:15).

Ветка неожиданной ошибки записывает `{"code":"internal","error":error.name}`. Для обычного исключения это всего лишь `{"code":"internal","error":"Error"}`; для TypeError — только слово `TypeError`. Нет stack, безопасной причины, SQLite error code, request ID или маршрута. Клиент при этом получает общий повторяемый 503.

У POST есть отдельный лог длительности и operation ID, но он не привязан к записи об исключении общим ID. У неожиданной ошибки GET нет и такого контекста. После первого runtime-сбоя можно узнать, что произошёл `Error`, но нельзя понять, сломался ли snapshot, event processing, сериализация или драйвер. Повторять запрос с тем же ID разумно для неизвестного исхода, однако без серверной причины это превращается в плохо диагностируемый цикл.

**Подтверждение:** probe намеренно бросает `Error('AUDIT_ONLY_EXPECTED_DIAGNOSTIC')` при чтении snapshot. HTTP возвращает 503; единственная запись ошибки — `{"code":"internal","error":"Error"}`. Сообщение и стек потеряны. Это проверка диагностического пути, а не попытка вызвать настоящую поломку базы.

**Реалистичное исправление:** назначать `requestId` в начале middleware и сохранять его в context; один небольшой `logError` пишет request ID, метод, pathname, operation ID/actor при наличии, имя/код ошибки и stack с безопасной обработкой сообщения. Не логировать Authorization, cookies, пароль, конверт команды и полный текст задач. Вернуть request ID клиенту для сопоставления. `LOG_LEVEL` либо подключить к этому logger, либо убрать из compose как неработающую настройку.

**Что даст:** `docker logs` станет пригоден для нахождения причины без повторной сборки с отладочным выводом. Внешние ответы можно оставить короткими и без внутренних подробностей. Внешний error tracker для этого не обязателен.

### Q-03. Property-тесты не полностью независимы от проверяемых правил

**Место:** [tests/property/undo.test.ts:56](/Users/dmitriy/code/taskindex/tests/property/undo.test.ts:56), проверка строк 100–105; [tests/property/commands.test.ts:14](/Users/dmitriy/code/taskindex/tests/property/commands.test.ts:14), генерация/выбор команд в строках 73–111. Требования — [план, раздел 13](/Users/dmitriy/code/taskindex/docs/plans/2026-09-08-taskindex-v2.md:804).

Самое существенное — ожидаемые поля Undo определяются production-функцией `isSubjectField`, которой пользуется сам алгоритм отмены. Если при следующем изменении из списка предметных полей случайно исчезнет, например, `note`, реализация перестанет восстанавливать note, а property-test одновременно перестанет сравнивать note. Тесту будет нечего возразить именно против такого вида регрессии.

Есть и ограничение генераторов: оба используют owner, актуальный `baseRevision`, три заранее созданные задачи. Первый генерирует note, move без соседей, archive/restore, focus, comment.add и checklist.add. Второй меняет note/status/due/title и отменяет их общий effect. В нём вообще не генерируются создание через sync, отмена создания, продвижение source watermark, чужие ручные правки, invalid/rejected/no-op/повторные операции. Утверждение про монотонность revision проверяет только `>=`, а время постоянно; это не проверяет точное увеличение revision/updatedAt при предметном изменении.

В API-тестах уже есть много хороших примеров этих сценариев. Находка не означает, что `sync`, Undo или конфликты вообще не тестируются. Ограничение в том, что random sequences пока не проверяют сочетания наиболее сложных правил, ради которых этот слой и добавлен.

**Реалистичное исправление:** сначала сделать ожидаемое состояние независимым: в Undo property сравнивать явно оговорённые поля fixture/model, не импортировать production predicate для исключения сравниваемых полей. Затем добавить один небольшой model-based генератор вокруг настоящего `executeOperation`: owner/agent, stale/current base, create/sync/save/move/undo, успешная и отвергнутая batch. Проверять отдельно конечные данные, число событий и неизменность state на отказе. Время продвигать детерминированно; не увеличивать просто `numRuns` нынешнего узкого генератора.

**Что даст:** property-тест сможет поймать ошибку определения Undo-полей, а также неожиданное взаимодействие sync/ручных правок/повтора, которого нет в отдельных сценариях. Существующие API-примеры и тест совпадения event projection стоит сохранить.

### Q-04. Сохранённая локальная структура не получает runtime-проверку

**Приоритет и тип:** P3, optional improvement. Усиление границы восстановления перед дальнейшими изменениями формата; не основание останавливать рабочий запуск само по себе.

**Место:** [src/web/app/drafts.ts:34](/Users/dmitriy/code/taskindex/src/web/app/drafts.ts:34), [src/web/app/store.ts:379](/Users/dmitriy/code/taskindex/src/web/app/store.ts:379), [src/cli/outbox.ts:61](/Users/dmitriy/code/taskindex/src/cli/outbox.ts:61). Использование поля сразу после чтения — [src/web/app/dialogs.tsx:52](/Users/dmitriy/code/taskindex/src/web/app/dialogs.tsx:52).

`DraftStorage.read<T>` проверяет только `formatVersion === 1`, после чего обещает вызывающему `Draft<T>`. Ни generation/baseRevision, ни наличие/форма `fields`, ни сохранённый submission не проверяются. `WorkspaceStore.recover` принимает JSON, если в нём truthy `operationId` и `generation`. CLI Outbox проверяет несколько метаполей, но не сам envelope. Поэтому типизированный код восстановления начинает работу с типами, которые он фактически не доказал.

Probe показывает узкую границу: `{"formatVersion":1,"generation":"g","baseRevision":1,"fields":null}` принимается как draft; последующее чтение `fields.title`, применяемое формой, бросает исключение. Невалидная запись остаётся в storage и принимается вновь. Текущий корректный writer такую запись не создаёт; это сценарий повреждённого/несовместимого сохранённого состояния, а не доказательство поломки нормального ввода.

**Реалистичное исправление:** добавить схемы для общего envelope draft и отдельных payload форм (либо `readDraft(id, schema)`); существующие `commandEnvelopeSchema`/`batchEnvelopeSchema` использовать для queued операций. Неподдерживаемое содержимое сохранять как доступный для ручного восстановления raw draft, но не смешивать с полями редактора и не отправлять автоматически. Добавить по одному тесту malformed JSON, правильной версии с неправильной формой и старой версии. Не удалять молча потенциально ценный текст.

**Что даст:** следующие изменения черновиков/очереди смогут иметь явную миграцию или понятное восстановление; одна плохая запись не будет повторно ломать открытие формы. Это самостоятельная локальная граница; проверка HTTP/SSE-ответов и потеря CLI outbox после произвольного JSON 200 уже учтены другими reviewer.

### Q-05. Drill обходит deployment entrypoint, в котором находится выбор отката

**Место:** [deploy/local-drill.sh:79](/Users/dmitriy/code/taskindex/deploy/local-drill.sh:79), прямой вызов rollback в строке 95; тестируемый не напрямую обработчик — [deploy/deploy.sh:44](/Users/dmitriy/code/taskindex/deploy/deploy.sh:44). Статические checks — [package.json:15](/Users/dmitriy/code/taskindex/package.json:15).

Drill хорошо проверяет репликацию, backup, restore, несовместимую схему, новое поколение и запрет возврата после открытия записи. Но неудачный candidate создаётся самим drill, а `rollback.sh` вызывается вручную. Сам `deploy.sh` не исполняется. Не проверяются его `ERR`-trap, переходы `phase`, передача rollback context, порядок текущего release manifest и отметки `opened`, ветка ошибки до миграции и фактический вызов rollback после нужной ошибки.

Иными словами, тест доказывает работоспособность rollback-функции при правильно переданных входах. Он ещё не доказывает, что deployment-процесс выберет её и передаст эти входы правильно при неудаче. Это особенно важно, потому что именно orchestration решает, допустим ли возврат базы. В текущем `npm run check` deployment JavaScript и shell scripts также не проходят собственный статический check. Успех общего check эту область не покрывает.

**Реалистичное исправление:** добавить отдельный изолированный Linux harness, который запускает настоящий `deploy.sh` на временном git-репозитории и отдельном compose project/volume. Использовать уже предусмотренные `TASKINDEX_FAIL_AT=after-migrate` и `health`, а также отказ до checkpoint и неопределённый исход открытия записи. Проверять вызов/запрет rollback, сохранённую фазу и соответствие image/schema/generation. Быстрый слой может подменять `docker/git/curl` fixture-командами только внутри harness для проверки ветвления; он дополняет существующий настоящий Docker drill. Добавить `bash -n` и проверку `deploy/database.mjs`; ShellCheck полезен, но не обязателен для этого исправления.

**Что даст:** подтверждение автоматического выбора безопасного действия при падении релиза. До такого теста корректная формулировка результата — «проверены восстановление и rollback helper», без утверждения, что полностью отрепетирован production deploy entrypoint. Отсутствие такого теста само по себе не доказывает ошибку текущего shell-кода.

## Что написано хорошо и стоит сохранить

1. **Чистая предметная функция с явными зависимостями.** В `applyCommand` время, actor, ID generator и история передаются явно. Clone на входе позволяет отклонить правило без частичного изменения исходного state. Вычисление запросов и Focus также не зависит от React/HTTP.
2. **Одна атомарная точка записи.** `executeOperation` фиксирует state, events и сохранённый response в одной immediate transaction; generation проверяется до использования прошлого результата. Это удачная локализация ответственности, её не следует размазывать по отдельным route handlers.
3. **Фактическая защита данных в слоях ниже UI.** Проверки scope, проекта/области, origin, owner fields и Undo выполняются на сервере; UNIQUE/FK SQLite поддерживают предметные инварианты. UI не является единственным местом валидации.
4. **Хорошая дисциплина повторяемых операций.** CLI публикует outbox-файл атомарным no-overwrite link после fsync, хранит старый envelope и не переписывает его произвольно. Web store отдельно держит confirmed/pending, буферизует полный диапазон событий операции и учитывает epoch при догоне. Эти решения сложнее обычного fetch-and-setState, но оправданы требованиями.
5. **Разделение коротких пользовательских ошибок и внутренних операций.** `DomainError` и русские сообщения дают устойчивый способ отказывать ожидаемым случаям. Улучшать нужно конкретно неожиданные ошибки и сохранение их диагностики, а не заменять всю модель исключений.
6. **Сильная проверка импорта.** `validateExport` сверяет избыточные таблицы, непрерывность событий, акторов/границы операций и replay результата. Это значительно лучше, чем просто Zod-parse JSON и INSERT. Атомарную проверку перед заменой следует сохранить.
7. **Тесты используют реальные зависимости там, где это важно.** Auth tests и agent cycle проходят настоящий Better Auth; API tests используют тот же SQLite driver и migrations; есть file reopen, реальные e2e, проверки конфликтов и потерянного ответа. Нет необходимости всё переписывать на mocks или добиваться формального 100% coverage.
8. **UI уже разделён по предметным экранам.** Доска, карточка, редактор, обсуждение, диалоги и sidebar находятся отдельно. Наличие длинного JSX файла само по себе не дефект; стандартные UI primitives не требуют собственной доменной архитектуры.
9. **Явная граница восстановления после релиза.** Shell scripts удерживают запись, сохраняют независимый checkpoint, используют новый replica prefix и отмечают опасную границу до вызова open-writes. Это правильная дисциплина; Q-05 просит проверить orchestration, а не убрать её.

## Необязательный рефакторинг после исправления реальных дефектов

**Q-06 — P3, optional improvement, confidence высокий:** объединить только повторяющийся жизненный цикл создания/отправки формы. Сейчас QuickCreate, InlineCreate, ProjectDialog и TaskDiscussion отдельно управляют draft key, entity ID, operation ID, busy/error, сохранением intent и его завершением. Примеры: [dialogs.tsx:61](/Users/dmitriy/code/taskindex/src/web/app/dialogs.tsx:61), [board.tsx:145](/Users/dmitriy/code/taskindex/src/web/app/board.tsx:145), [activity.tsx:326](/Users/dmitriy/code/taskindex/src/web/app/activity.tsx:326).

Это не довод в пользу универсального form engine. Полезен небольшой controller/hook для состояний «редактируется → отправляется → исход неизвестен → подтверждено/отклонено», с общим правилом сохранения прежнего envelope. Разметку и правила конфликта оставить у конкретных форм. Сейчас различия terminal-error reset заметны прямо в обработчиках: QuickCreate создаёт новый operation ID при definitive ApiError, InlineCreate обнуляет ref, TaskDiscussion сохраняет intent. Частота и пользовательская достижимость конкретного сбоя требуют отдельной проверки; здесь фиксируется дублирование важной политики, не заявляется новый подтверждённый функциональный баг.

Также стоит со временем использовать отдельные типы формы/создания вместо заполнения `Task` фиктивными `revision: 0` и пустыми timestamps в [makeTask](/Users/dmitriy/code/taskindex/src/web/lib/workspace.ts:9). Это улучшит читаемость границы draft/сохранённой сущности, но не требует срочного изменения текущего API.

## Пересечения и порядок дальнейшей работы

- Массовое чтение/клонирование state/history, блокировка event loop и цена pagination — архитектурная находка; здесь не выдаётся за отдельное качество кода.
- Web `request<T>`/SSE без проверки схем и произвольный JSON 200, закрывающий CLI outbox, — одна клиентская contract-тема с конкретным багом. Здесь не создан её дублирующий ID.
- Отправка при полностью недоступном browser storage — отдельная функциональная находка другого reviewer. Q-04 о проверке формы уже сохранённых данных, а не доступности хранилища.

Рекомендуемая последовательность: сначала подтвердить и исправить функциональные дефекты из bug report; затем Q-02 для нормальной диагностики и Q-05 до заявления о полной репетиции деплоя; далее Q-01 вместе с независимыми проверками Q-03. Q-04 и Q-06 можно привязать к следующему изменению очереди/черновиков. Смена стека, state library, ORM или UI-библиотеки для этих улучшений не требуется.
